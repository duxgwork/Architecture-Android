## Q1: RecyclerView 的缓存机制是什么？

RecyclerView 的核心就是**四级缓存**，从近到远依次是：

### 第一级：mAttachedScrap

就是**当前屏幕上还看得到的那些 ViewHolder**。比如你滑动的时候，有些 item 暂时被移出了屏幕但还没被"真正回收"，它们就存在这里。重新滑回来的时候，直接从这取，**不需要重新 bind**，因为数据没变。

### 第二级：mChangedScrap

存的是**数据发生了变化的、但还在屏幕上的 ViewHolder**。比如调了 `notifyItemChanged()` 的那些 item。重新显示的时候需要**重新 bind**，因为数据变了。

### 第三级：mCachedViews

当 item **刚滑出屏幕**的时候，会被放进这个缓存。默认容量是 **2 个**。它的特点是：

- **不需要重新 bind**，拿过来直接用，跟第一级一样
- 但它是有位置的，通过 **position** 来匹配，只有滑回原来的位置才能复用
- 如果位置不对，就会被踢到第四级去

可以理解为"最近刚用过的、还热乎的"。

### 第四级：RecycledViewPool

这是**最终的缓存池**，容量默认无上限。特点是：

- 按 **viewType** 分类存放
- 拿出来的时候**需要重新 bind**（会调 `onBindViewHolder`）
- 不区分位置，任何位置的相同 viewType 都能复用
- 相当于一个"万能替补席"

### 查找流程

当 RecyclerView 需要一个 ViewHolder 的时候，查找顺序是：

> **mAttachedScrap → mChangedScrap → mCachedViews → RecycledViewPool → 都没有就重新 create**

从最近的缓存一级一级往下找，找到就用，找不到就创建新的。

### 一句话总结

四级缓存的核心设计思想就是——**离得越近的缓存，复用成本越低**。屏幕上的直接拿来用，刚滑出去的不重新 bind 直接用，远一点的按 viewType 复用但要重新 bind。这样既**避免了频繁创建 View**，又**减少了不必要的 bind 操作**，性能自然就上去了。

### 补充要点

- `mCachedViews` 的大小可以通过 `Recycler.setViewCacheSize()` 调整，列表频繁来回滑的场景可以适当调大
- `RecycledViewPool` 可以通过 `setMaxRecycledViews(viewType, max)` 限制每个 viewType 的缓存上限
- 如果 `onViewRecycled()` 里做了释放资源的操作，那从 RecycledViewPool 取出来的 ViewHolder 一定要确保 `onBindViewHolder` 里做了完整的重新赋值，不然会显示脏数据

## Q2: 使用 RecyclerView 加载大列表数据时如何提高性能？

大列表优化我一般从这几个维度来做：

### 1. 局部刷新 — DiffUtil / AsyncListDiffer

千万不要一有数据变化就 `notifyDataSetChanged()`，这会导致**全量刷新**，所有可见的 ViewHolder 都会重新 bind。

正确做法是用 **DiffUtil** 或者更方便的 **AsyncListDiffer**，它会在后台线程计算新旧列表的差异，然后只刷新变化的部分。比如只插入了3条数据，那就只 bind 那3个 item，其他完全不动。

### 2. 开启 setHasStableIds

给 Adapter 设置 `setHasStableIds(true)`，然后重写 `getItemId()`，给每个 item 返回一个**唯一稳定的 ID**。

这样做的好处是 RecyclerView 在数据变化时，能通过 ID 识别出哪些 ViewHolder 可以复用，**减少不必要的 create 和 bind**。

### 3. 分页加载 / 无限滚动

不要一次性把所有数据都塞进去。用**分页加载**，比如每次加载 20 条，滑到底部再加载下一页。

配合 **Paging 3 库**来做，它帮你处理了分页逻辑、预加载、占位符这些，省心很多。

### 4. 预取 — prefetch

RecyclerView 有个 **LinearLayoutManager.setPrefetchCount()**，默认是4。意思是当 item 快滑出屏幕时，提前在后台准备好后面几个 ViewHolder。

对于滑动速度很快的场景，可以适当调大这个值，让滑动更流畅。

### 5. onBindViewHolder 里千万别做耗时操作

`onBindViewHolder` 是在**主线程**执行的，这里面只能做简单的数据绑定。

- **不要**在这里做图片解码
- **不要**在这里做数据库查询
- **不要**在这里做复杂的字符串拼接

图片加载用 Glide/Coil 这种异步库，复杂数据提前在后台处理好，bind 的时候直接 set 就行。

### 6. RecycledViewPool 预热

如果是打开页面就需要大量数据展示的场景，可以提前**预热缓存**。在数据准备好之后，先手动创建一批 ViewHolder 放进 RecycledViewPool，这样列表渲染的时候直接从缓存取，不用临时 create。

### 7. setItemViewCacheSize

调大 `RecyclerView.setItemViewCacheSize()` 的值，让 mCachedViews 能缓存更多刚滑出屏幕的 ViewHolder。这些 ViewHolder 回来时**不需要重新 bind**，对频繁来回滑动的场景效果很明显。

### 一句话总结

大列表优化的核心思路就是三个词：**少刷新、快复用、轻绑定**。用 DiffUtil 做局部刷新减少不必要的 bind，用缓存机制和预热加速复用，把 onBindViewHolder 里的操作压到最轻。再配合分页加载控制数据量，基本就能保证大列表的流畅性了。

## Q3: Glide 的缓存机制是什么？

Glide 的核心也是**四级缓存**，从内存到磁盘，层层递进：

### 第一级：Active Resources（活跃资源）

就是**当前正在屏幕上显示的、还没被回收的图片资源**。它用一个弱引用（WeakReference）的 Map 来维护。

- 只要这个图片还在被某个 ImageView 使用，就会一直缓存在这里
- 一旦 View 被回收或者图片不再被引用，就会被**自动清除**
- 取的时候**零成本**，直接拿内存里的 Bitmap 用

### 第二级：Memory Cache（内存缓存）

当图片**不在屏幕上显示**了，但还没被 LRU 淘汰，就存在这里。

- 用的是 **LruCache**，基于最近最少使用算法，内存不够的时候自动淘汰最久没用的
- 取的时候也很快，直接从内存拿 Bitmap
- 默认大小是**当前设备可用内存的 1/8**，可以自定义

> 第一级和第二级合起来就是 Glide 的**内存缓存层**。Active Resources 是"正在用的"，Memory Cache 是"刚用完还没扔的"。

### 第三级：Disk Cache（磁盘缓存）

内存缓存被 LRU 淘汰后，或者图片之前加载过但内存里已经没了，就会去磁盘缓存找。

- 存在**磁盘文件**里，默认路径是 `InternalCacheDir` 下的 `image_manager_disk_cache` 目录
- 默认大小 **250MB**，也是 LRU 策略，超过就淘汰最旧的
- 这里存的是**已经经过变换（transform）后的最终图片**，比如缩放、裁剪后的版本
- 取的时候需要**磁盘 IO + 解码**，比内存慢但比网络快

### 第四级：Remote（远程/网络）

前三级都没有的话，就**发起网络请求**去下载。

- 下载完成后，先写入磁盘缓存
- 再解码到内存缓存
- 最后交给 ImageView 显示

### 完整的查找流程

> **Active Resources → Memory Cache → Disk Cache → Network**

一级一级往下找，找到就返回，找不到就走下一级。

### 缓存策略 — DiskCacheStrategy

Glide 提供了 5 种磁盘缓存策略：

| 策略 | 原始数据 | 变换后数据 | 说明 |
|------|---------|-----------|------|
| `ALL` | ✅ | ✅ | 原始数据和变换后的都缓存 |
| `DATA` | ✅ | ❌ | 只缓存原始数据 |
| `RESOURCE` | ❌ | ✅ | 只缓存变换后的数据 |
| `NONE` | ❌ | ❌ | 不缓存磁盘 |
| `AUTOMATIC` | 根据来源自动选择 | — | 本地文件只缓存变换后数据，远程数据两个都缓存（**默认**） |

### 内存管理的关键设计

Glide 的内存管理有几个比较巧妙的设计：

1. **生命周期绑定**：Glide 会在当前 Activity/Fragment 上绑定一个不可见的 Fragment 来监听生命周期。页面销毁了，请求自动取消，内存缓存自动清理。这就是为什么 Glide 不容易 OOM。

2. **内存警告监听**：Glide 注册了 `ComponentCallbacks2`，当系统发出低内存警告时，会自动清理内存缓存。

3. **Bitmap 复用**：Glide 4.x 之后支持 **Bitmap 对象池**，通过 `inBitmap` 复用已有的 Bitmap 内存，避免频繁 GC。

### 一句话总结

Glide 的四级缓存核心思想就是**就近获取**：正在用的直接拿、刚用完的从内存拿、之前加载过的从磁盘拿、都没有才去网络下载。配合生命周期绑定和 LRU 淘汰策略，既保证了加载速度，又控制了内存占用，不容易 OOM。

## Q4: ARouter 的路由表是如何加载到内存的？

ARouter 的路由表加载，核心思路就是**编译时生成 + 运行时懒加载**，分两个阶段：

### 一、编译时 — APT 生成路由表

在编译阶段，ARouter 通过自定义的 **AnnotationProcessor** 扫描所有带有 `@Route` 注解的类（Activity、Fragment 等），然后自动生成对应的 Java 源文件。

生成的文件有两类：

**1. `ARouter$$Root$$模块名` — 分组索引表**

这个类记录的是"我这个模块有哪些分组"。它实现了 `IRouteRoot` 接口，在 `loadInto` 方法里把分组名和对应的 Group 类注册进去：

```java
public void loadInto(Map<String, Class<? extends IRouteGroup>> routes) {
    routes.put("order", ARouter$$Group$$order.class);
    routes.put("user", ARouter$$Group$$user.class);
}
```

**2. `ARouter$$Group$$分组名` — 分组路由表**

这个类记录的是"这个分组下有哪些路由"。它实现了 `IRouteGroup` 接口，在 `loadInto` 方法里把路径和路由信息注册进去：

```java
public void loadInto(Map<String, RouteMeta> atlas) {
    atlas.put("/order/detail", RouteMeta.build(
        RouteType.ACTIVITY, OrderDetailActivity.class, "/order/detail", "order", ...));
}
```

> 简单说就是：**Root 文件管"有哪些分组"，Group 文件管"每个分组下有哪些路由"**。编译完就全生成好了，运行时不需要反射，性能很好。

### 二、运行时 — 懒加载到内存

运行时的核心类是 **`LogisticsCenter`** 和 **`Warehouse`**。`Warehouse` 是路由表的存储中心，里面有几个关键的 Map：

```java
// 存储分组索引：groupName → Group 类的 Class 对象
static Map<String, Class<? extends IRouteGroup>> groupsIndex = new HashMap<>();

// 存储具体路由：path → RouteMeta
static Map<String, RouteMeta> routes = new HashMap<>();
```

加载流程分两步：

#### 第一步：init 时加载 Root 分组索引

调用 `ARouter.init(application)` 的时候，会走到 `LogisticsCenter.init()`，这里面做的事情就是：

1. 找到所有模块生成的 `ARouter$$Root$$xxx` 类
2. 通过反射调用它们的 `loadInto` 方法
3. 把分组信息注册到 `Warehouse.groupsIndex` 中

```java
// 伪代码
Class rootClass = Class.forName("com.alibaba.android.arouter.routes.ARouter$$Root$$app");
IRouteRoot rootInstance = (IRouteRoot) rootClass.newInstance();
rootInstance.loadInto(Warehouse.groupsIndex);
```

> 注意：这一步**只加载了分组索引**，还没加载具体的路由信息。

#### 第二步：按需懒加载 Group 路由表

当真正要跳转某个路径（比如 `/order/detail`）的时候，`LogisticsCenter.completion()` 会去 `Warehouse.routes` 里找：

- **找到了** → 直接用，返回 `RouteMeta`
- **没找到** → 说明这个分组还没加载过，去 `Warehouse.groupsIndex` 里找到对应的 Group 类，反射实例化后调用 `loadInto`，把该分组下的所有路由加载到 `Warehouse.routes` 中

```java
// 伪代码
if (routes.get(path) == null) {
    // 从分组名找到 Group 类
    Class groupClass = groupsIndex.get(groupName);
    IRouteGroup groupInstance = groupClass.newInstance();
    // 加载该分组的所有路由
    groupInstance.loadInto(Warehouse.routes);
}
// 再次获取
RouteMeta meta = routes.get(path);
```

> 这就是**懒加载**——用到的时候才加载，不用的分组不加载，节省内存和启动时间。

### 完整流程总结

```
编译时：
  @Route 注解 → APT 扫描 → 生成 ARouter$$Root$$xxx + ARouter$$Group$$xxx

运行时 init：
  ARouter.init() → LogisticsCenter.init()
    → 反射调用所有 Root 类的 loadInto()
    → 分组索引写入 Warehouse.groupsIndex

运行时跳转：
  navigation("/order/detail") → LogisticsCenter.completion()
    → 查 Warehouse.routes，有就直接用
    → 没有就反射加载对应的 Group 类 → loadInto → 写入 Warehouse.routes
    → 再查 Warehouse.routes，拿到 RouteMeta
    → 根据 RouteMeta 里的 Class 信息启动目标页面
```

### 一句话总结

ARouter 的路由表加载就是**编译时生成、运行时懒加载**。编译阶段通过 APT 生成 Root 和 Group 两类映射文件，避免运行时反射扫描注解的性能问题；运行时 init 只加载分组索引，具体路由表在第一次跳转时才按需加载，兼顾了**启动速度**和**内存占用**。

## Q5: ARouter 的页面跳转和接口通信，二者底层原理分别是什么？

ARouter 的这两个功能，底层原理差别挺大的。页面跳转走的是**路由表 + 拦截器链**，接口通信走的是**依赖注入 + 单例缓存**。

### 一、页面跳转的底层原理

#### 1. 发起跳转

调用 `ARouter.getInstance().build("/app/MainActivity").withString("key", "value").navigation()` 之后，会创建一个 **`Postcard`** 对象，它封装了这次跳转的所有信息：路径、参数、标志位等。

#### 2. 拦截器链处理

在进入真正的跳转逻辑之前，会先经过**拦截器链**。ARouter 有一个全局的拦截器列表 `Warehouse.interceptors`，按优先级排序。

流程是这样的：

```
navigation() → _navigation()
  → LogisticsCenter.completion(postcard)  // 补全路由信息
  → 有拦截器？→ 进入拦截器链
    → 拦截器1.handle() → callback.onContinue() → 拦截器2.handle() → ... → 最终跳转
    → 某个拦截器 callback.onInterrupt() → 中断，不跳转
```

每个拦截器可以实现 `IInterceptor` 接口，比如做登录校验、权限判断这些。

#### 3. 路由信息补全

`LogisticsCenter.completion()` 做的事情就是之前 Q4 说的那个流程——从 `Warehouse.routes` 里查 `RouteMeta`，没有就懒加载 Group 路由表。补全之后，`Postcard` 里就有了目标页面的 Class 信息、类型（Activity/Fragment/Service 等）。

#### 4. 根据类型执行跳转

拿到 `RouteMeta` 之后，根据 `type` 走不同的逻辑：

- **ACTIVITY** → 构建 Intent，把参数塞进去，调 `context.startActivity()`
- **FRAGMENT** → 直接实例化 Fragment，设置参数
- **CONTENT_PROVIDER** → 通过 ContentResolver 操作
- **IProvider** → 走接口通信的逻辑（下面说）

```java
// 伪代码
switch (type) {
    case ACTIVITY:
        Intent intent = new Intent(context, postcard.getDestination());
        // 把 withString/withInt 等参数都塞进 intent
        intent.putExtras(postcard.getExtras());
        context.startActivity(intent);
        break;
    case FRAGMENT:
        Class fragmentClass = postcard.getDestination();
        BaseFragment fragment = fragmentClass.newInstance();
        fragment.setArguments(postcard.getExtras());
        // 通过 FragmentManager 添加
        break;
}
```

#### 5. 回调

跳转完成后，通过 `NavigationCallback` 回调通知调用方：

- `onFound(Postcard)` — 找到路由
- `onLost(Postcard)` — 没找到路由
- `onArrival(Postcard)` — 到达目标
- `onInterrupt(Postcard)` — 被拦截器拦截

### 二、接口通信（IProvider）的底层原理

ARouter 除了跳页面，还能做**接口级别的通信**，本质上就是一个轻量级的**依赖注入框架**。

#### 1. 定义接口和实现

```java
// 定义接口，继承 IProvider
public interface IUserService extends IProvider {
    String getUserName();
}

// 实现类，用 @Route 标注
@Route(path = "/service/user")
public class UserServiceImpl implements IUserService {
    @Override
    public void init(Context context) {
        // 初始化逻辑
    }
    
    @Override
    public String getUserName() {
        return "张三";
    }
}
```

#### 2. 编译时 — APT 生成 Provider 映射

编译时 APT 除了生成 Root 和 Group 文件，还会生成 **`ARouter$$Providers$$模块名`** 文件，记录接口和实现类的映射关系：

```java
public void loadInto(Map<String, Class<? extends IProvider>> providers) {
    providers.put(IUserService.class.getName(), UserServiceImpl.class);
}
```

#### 3. 运行时 — 获取实例

调用 `ARouter.getInstance().navigation(IUserService.class)` 的时候，底层流程：

```java
// 伪代码
public <T> T navigation(Class<T> service) {
    // 1. 先从缓存里找
    IProvider provider = Warehouse.providers.get(service.getName());
    if (provider != null) {
        return (T) provider;  // 有就直接返回，单例
    }
    
    // 2. 没有的话，从 providers 映射表里找实现类
    Class<? extends IProvider> implClass = Warehouse.providersIndex.get(service.getName());
    
    // 3. 反射创建实例
    IProvider instance = implClass.newInstance();
    
    // 4. 调用 init 初始化
    instance.init(context);
    
    // 5. 缓存起来，下次直接返回
    Warehouse.providers.put(service.getName(), instance);
    
    return (T) instance;
}
```

> 关键点：**IProvider 是单例的**。第一次获取的时候创建实例并缓存，后面再获取直接返回缓存的实例。

#### 4. 存储结构

```java
// Warehouse 中的关键 Map
// 接口全限定名 → 实现类的 Class 对象
static Map<String, Class<? extends IProvider>> providersIndex = new HashMap<>();

// 接口全限定名 → 实现类的单例实例
static Map<String, IProvider> providers = new HashMap<>();
```

### 三、两者的核心区别

| 维度 | 页面跳转 | 接口通信 |
|------|---------|----------|
| **入口** | `navigation(path)` | `navigation(Class)` |
| **查找方式** | 通过路径查 `Warehouse.routes` | 通过接口名查 `Warehouse.providersIndex` |
| **执行逻辑** | 构建 Intent → 拦截器链 → startActivity | 反射创建实例 → init → 缓存 |
| **结果** | 打开一个新页面 | 返回一个接口实现类的**单例** |
| **拦截器** | 支持 | 不支持 |
| **本质** | 路由导航 | 依赖注入（DI） |

### 一句话总结

页面跳转的本质是**路径 → RouteMeta → Intent → startActivity**，中间经过拦截器链做各种拦截逻辑；接口通信的本质是**接口 Class → 实现类 Class → 反射实例化 → 单例缓存**，是一个轻量级的依赖注入。两者共用同一套 APT 生成机制和 `Warehouse` 存储，但运行时的处理逻辑完全不同。

## Q6: BlockCanary 的底层原理？

BlockCanary 的核心就一句话：**利用 Looper 的 Printer 机制，监听主线程每条消息的执行耗时，超时了就采集堆栈上报**。

### 一、核心原理 — Looper 的 Printer 机制

Android 主线程的消息循环在 `Looper.loop()` 里，源码里有这么一段：

```java
public static void loop() {
    final Looper me = myLooper();
    final MessageQueue queue = me.mQueue;
    
    for (;;) {
        Message msg = queue.next(); // 取消息，可能阻塞
        if (msg == null) return;
        
        // ★ 关键：消息处理前打印
        Printer logging = me.mLogging;
        if (logging != null) {
            logging.println(">>>>> Dispatching to " + msg.target + " " + msg.callback + ": " + msg.what);
        }
        
        // ★ 真正执行消息（Activity 的 measure/layout/draw 等都在这里）
        msg.target.dispatchMessage(msg);
        
        // ★ 关键：消息处理后打印
        if (logging != null) {
            logging.println("<<<<< Finished to " + msg.target + " " + msg.callback);
        }
    }
}
```

每条 Message 处理前后，都会调 `Printer.println()`。BlockCanary 就是利用了这个机制。

### 二、BlockCanary 怎么检测卡顿

#### 1. 安装自定义 Printer

BlockCanary 在初始化的时候，通过 `Looper.getMainLooper().setMessageLogging(printer)` 把自己的 `BlockPrinter` 装上去。

#### 2. BlockPrinter 的核心逻辑

```java
class BlockPrinter implements Printer {
    private long mStartTime = 0;
    
    @Override
    public void println(String x) {
        if (mStartTime != 0) {
            // 第二次调用 = 消息处理结束
            long costTime = System.currentTimeMillis() - mStartTime;
            mStartTime = 0;
            
            // 超过阈值（比如 500ms），判定为卡顿
            if (costTime >= mBlockThreshold) {
                // 触发卡顿上报！
                notifyBlockEvent(costTime);
            }
        } else {
            // 第一次调用 = 消息处理开始
            mStartTime = System.currentTimeMillis();
        }
    }
}
```

> 逻辑很简单：**两次 println 之间的时间差就是这条消息的执行耗时**。超过设定的阈值（默认 500ms），就认为发生了卡顿。

#### 3. 卡顿发生后做什么

一旦检测到卡顿，BlockCanary 会在**监控线程**上做以下事情：

- **采集主线程堆栈**：通过 `Looper.getMainLooper().getThread().getStackTrace()` 获取当前主线程的调用栈，精确定位到是哪个方法导致的卡顿
- **采集 CPU 信息**：读取 `/proc/stat` 获取 CPU 使用率
- **采集进程信息**：内存占用、进程状态等
- **记录卡顿信息**：耗时、堆栈、时间戳等，写入日志文件
- **通知开发者**：弹出一个通知，点击可以查看详细的卡顿分析报告

### 三、完整的检测流程

```
初始化：
  BlockCanary.install(context, listener).start()
    → Looper.getMainLooper().setMessageLogging(BlockPrinter)
    → 启动监控线程

运行时：
  主线程处理每条 Message：
    → println(">>>>> Dispatching...") → 记录开始时间
    → 执行消息（measure/layout/draw/网络回调等）
    → println("<<<<< Finished...") → 计算耗时
    
    → 耗时 < 阈值 → 正常，不管
    → 耗时 ≥ 阈值 → 卡顿！
      → 采集主线程堆栈
      → 采集 CPU/内存信息
      → 写入日志
      → 弹出通知

停止监控：
  BlockCanary.stop()
    → Looper.getMainLooper().setMessageLogging(null)
    → 停止监控线程
```

### 四、为什么能精确定位卡顿原因？

因为卡顿发生的时候，主线程一定还在执行那条耗时的 Message。这时候去 `getStackTrace()` 拿到的堆栈，就是**正在执行的那段代码的调用链**。

比如堆栈显示：

```
com.xxx.MyActivity.onMeasure(MyActivity.java:128)
  → com.xxx.HeavyComputation.doCalc(HeavyComputation.java:45)
    → ...
```

那一看就知道是 `onMeasure` 里做了耗时计算导致的卡顿。

### 五、BlockCanary vs LeakCanary

| 维度 | BlockCanary | LeakCanary |
|------|------------|------------|
| **检测目标** | UI 卡顿 / 主线程阻塞 | 内存泄漏 |
| **核心原理** | Looper Printer + 耗时监控 | WeakReference + ReferenceQueue + GC |
| **监控线程** | 有，用于堆栈采集和日志写入 | 有，用于 GC 触发和泄漏检测 |
| **对主线程影响** | 极小（Printer 本身很快） | 极小（检测在后台线程） |

### 一句话总结

BlockCanary 的原理就是**监听主线程 Looper 的 Printer 回调**，通过两次 println 的时间差判断消息执行耗时。超时了就采集主线程堆栈，精确定位到卡顿的代码位置。本质上就是利用了 Android 框架层预留的一个"钩子"——`Looper.setMessageLogging()`。

## Q7: LeakCanary 的底层原理？

LeakCanary 的核心就是**弱引用 + 引用队列 + 堆转储分析**，用来检测 Activity/Fragment 的内存泄漏。

### 一、前置知识 — WeakReference + ReferenceQueue

LeakCanary 的原理基于 JVM 的两个机制：

- **WeakReference**：弱引用持有的对象，当没有强引用指向它时，下次 GC 就会被回收
- **ReferenceQueue**：当弱引用的对象被回收后，这个弱引用本身会被自动加入到引用队列中

```java
ReferenceQueue queue = new ReferenceQueue();
WeakReference ref = new WeakReference(activity, queue);

// 如果 activity 被 GC 回收了，ref 会被加入 queue
// 如果 queue 里没有 ref，说明 activity 还没被回收 → 可能泄漏了
```

> 这就是 LeakCanary 判断"有没有泄漏"的核心手段。

### 二、完整的检测流程

#### 1. 监听生命周期

LeakCanary 在初始化的时候，会注册 **Activity 和 Fragment 的生命周期监听**：

```java
// 伪代码
application.registerActivityLifecycleCallbacks(new ActivityLifecycleCallbacks() {
    @Override
    public void onActivityDestroyed(Activity activity) {
        // Activity 销毁了，开始检测
        watchActivity(activity);
    }
});
```

> 关键点：**只在 Activity/Fragment 销毁的时候才开始检测**。因为销毁了还被引用着，那就是泄漏。

#### 2. 创建弱引用 + 加入引用队列

当 Activity 被 `onDestroy` 之后：

```java
// 伪代码
void watchActivity(Activity activity) {
    // 1. 创建弱引用，关联引用队列
    KeyedWeakReference ref = new KeyedWeakReference(activity, activity.getClass().getName(), queue);
    
    // 2. 存到 watchedReferences 中，方便后续查找
    watchedReferences.put(ref.key, ref);
    
    // 3. 延迟几秒后检查
    checkForLeakLater(ref);
}
```

> 为什么要延迟几秒？因为 Activity 销毁后可能还有一些异步操作没完成（比如动画、Handler 消息），给它们一点时间释放引用。

#### 3. 检查是否被回收

几秒之后，检查引用队列：

```java
// 伪代码
void checkForLeak(KeyedWeakReference ref) {
    // 手动触发 GC
    Runtime.getRuntime().gc();
    
    // 检查引用队列 —— 被回收的弱引用会出现在这里
    Reference removedRef = queue.poll();
    
    while (removedRef != null) {
        // 从 watchedReferences 中移除已回收的
        watchedReferences.remove(removedRef.key);
        removedRef = queue.poll();
    }
    
    // 如果 ref 还在 watchedReferences 里，说明没被回收 → 泄漏了！
    if (watchedReferences.containsKey(ref.key)) {
        // 确认泄漏，进行堆转储分析
        heapDumpAndAnalyze(ref);
    }
}
```

> 这里会**主动调一次 GC**，确保该回收的都回收了。如果 GC 之后还在，那基本就是泄漏了。

#### 4. 堆转储 + 分析引用链

确认泄漏之后，LeakCanary 会做两件事：

**第一步：HeapDump（堆转储）**

把当前 JVM 的堆内存快照导出成一个 `.hprof` 文件。这个文件里包含了所有存活对象的实例和它们的引用关系。

**第二步：分析引用链**

用 **Shark** 库（早期版本用 HAHA）解析 hprof 文件，从 **GC Roots** 出发，找到一条到达泄漏对象的最短引用路径。

比如分析结果可能是：

```
com.xxx.MyActivity
  ↑ 被引用自
com.xxx.MyPresenter.mActivity
  ↑ 被引用自
com.xxx.MyFragment.mPresenter
  ↑ 被引用自
android.app.Fragment.mFragment
```

> 一看就知道：Fragment 里的 Presenter 持有了 Activity 的引用，Fragment 销毁了但 Presenter 没释放，导致 Activity 泄漏。

#### 5. 展示结果

LeakCanary 会把分析结果以**通知**的形式展示出来，点击可以看到完整的泄漏引用链，开发者一看就知道哪里出了问题。

### 三、核心类关系

```
Application
  → Activity/Fragment 生命周期监听
    → onDestroy 触发
      → KeyedWeakReference(activity, queue)
        → 延迟 5 秒
          → 检查 queue 里有没有这个 ref
            → 没有 → 泄漏！
              → HeapDump → Shark 分析 → 展示泄漏链
```

### 四、LeakCanary 2.x 的改进

LeakCanary 2.x 相比 1.x 有几个重要改进：

1. **零配置**：不需要手动在 Application 里初始化，利用 `ContentProvider` 在 App 启动时自动初始化
2. **自动检测 Fragment**：1.x 需要手动在 Fragment 里调 `watch()`，2.x 自动监听
3. **更小的体积**：用 Shark 替代了 HAHA，分析速度更快、包体积更小
4. **更多检测类型**：除了 Activity/Fragment，还能检测其他对象的泄漏

### 五、LeakCanary vs BlockCanary

| 维度 | LeakCanary | BlockCanary |
|------|-----------|------------|
| **检测目标** | 内存泄漏 | UI 卡顿 / 主线程阻塞 |
| **核心原理** | WeakReference + ReferenceQueue + HeapDump | Looper Printer + 耗时监控 |
| **检测时机** | Activity/Fragment 销毁后 | 每条 Message 执行时 |
| **分析方式** | 堆转储 + Shark 分析引用链 | 采集主线程堆栈 |
| **性能影响** | 堆转储时会有短暂卡顿 | 极小 |

### 一句话总结

LeakCanary 的原理就是：在 Activity/Fragment 销毁时给它创建一个**弱引用**并关联**引用队列**，等几秒后看弱引用有没有被回收到队列里。没有就说明泄漏了，于是做一次**堆转储**，用 Shark 分析出从 GC Roots 到泄漏对象的**完整引用链**，让开发者一目了然。

## Q8: 如何做电量优化？

电量优化说白了就是**减少不必要的唤醒和资源占用**。Android 手机耗电的大头就是 CPU 不让睡、网络频繁请求、GPS 一直开着这些。

### 一、先搞清楚电是怎么耗的

| 硬件模块 | 耗电程度 | 典型场景 |
|---------|---------|----------|
| **屏幕** | 最高 | 一直亮着 |
| **CPU 唤醒** | 很高 | WakeLock 没释放、后台服务不停跑 |
| **网络** | 高 | 频繁请求、长连接保活 |
| **GPS** | 高 | 持续定位 |
| **传感器** | 中 | 加速度计、陀螺仪一直开着 |
| **震动** | 中 | 频繁震动反馈 |

> 核心原则：**能不让 CPU 醒着就不醒着，能批量做的就别一个一个做，能延迟的就延迟。**

### 二、WakeLock 优化

WakeLock 是电量优化的**重中之重**。

#### 1. 尽量减少 WakeLock 的使用

能用其他方式解决的，就别用 WakeLock：

- 用 `WorkManager` / `JobScheduler` 替代自己持 WakeLock 的后台任务
- 用 `FCM` 推送替代长连接保活

#### 2. 必须用的时候，注意几点

```java
// ★ 正确用法
PowerManager pm = (PowerManager) getSystemService(POWER_SERVICE);
PowerManager.WakeLock wakeLock = pm.newWakeLock(
    PowerManager.PARTIAL_WAKE_LOCK,  // 只保持 CPU 运行，不亮屏
    "myapp:my_tag"                    // 一定要加 tag，方便调试
);
wakeLock.acquire(30 * 1000L);  // ★ 设置超时时间！最多 30 秒
// 用完立刻释放
wakeLock.release();
```

- **一定要设置超时时间**，别用无参的 `acquire()`，万一忘了 release 就永远不释放了
- **用完立刻 release**，别等页面销毁才释放
- 用 `PARTIAL_WAKE_LOCK`，只保持 CPU，不要亮屏
- 用 `try-finally` 确保释放

### 三、网络请求优化

网络模块是耗电大户，因为每次建立网络连接都要唤醒无线电模块。

#### 1. 合并请求

不要一个数据一个请求，尽量**批量获取**。比如列表数据一次性拉 20 条，别一条一条请求。

#### 2. 利用连接复用

同一个域名尽量复用 TCP 连接（HTTP/2、OkHttp 的连接池）。频繁建连会反复唤醒无线电模块，非常耗电。

#### 3. 用系统调度

用 **JobScheduler** 或 **WorkManager** 来调度网络请求，让系统帮你选择合适的时机执行：

```java
// 伪代码：用 WorkManager 调度
Constraints constraints = new Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)  // 有网络时才执行
    .setRequiresCharging(true)                       // 充电时才执行（非紧急任务）
    .build();

WorkRequest request = new PeriodicWorkRequest.Builder(
    SyncWorker.class, 15, TimeUnit.MINUTES)
    .setConstraints(constraints)
    .build();

WorkManager.getInstance(context).enqueue(request);
```

> 系统会把多个 App 的任务攒在一起批量执行，减少无线电模块的唤醒次数。

#### 4. 避免频繁心跳

长连接的心跳间隔不要太短。建议 **3~5 分钟**以上，能不用长连接就不用。

### 四、定位优化

GPS 模块非常耗电，尤其是高精度定位。

```java
// ★ 根据实际需求选择定位精度
LocationRequest request = LocationRequest.create();

// 不需要精确到米级别？用 BALANCED_POWER
request.setPriority(LocationRequest.PRIORITY_BALANCED_POWER);

// 不需要实时更新？降低频率
request.setInterval(60 * 1000);  // 1 分钟一次就够了，别 5 秒一次

// 不需要后台持续定位？用单次定位
LocationServices.getFusedLocationProviderClient(context)
    .getCurrentLocation(...);
```

- 能用 **基站/WiFi 定位** 就别用 GPS
- 能用 **单次定位** 就别用持续监听
- 能用 **被动定位**（`PASSIVE_PRIORITY`）就别主动请求

### 五、后台任务优化

#### 1. 用 WorkManager 替代 Service

后台 Service 会一直跑，非常耗电。非必须的场景都应该用 WorkManager：

| 场景 | 推荐方案 |
|------|----------|
| 必须立刻执行的 | Foreground Service |
| 可以延迟的 | WorkManager |
| 定时重复的 | WorkManager (PeriodicWorkRequest) |
| 系统空闲时做的 | WorkManager + setRequiresDeviceIdle(true) |

#### 2. 适配 Doze 模式

Android 6.0+ 的 Doze 模式会在设备闲置时限制网络、CPU 等活动。App 应该**顺应**这个机制，而不是对抗它：

- 用 FCM 高优先级推送来突破 Doze（仅限紧急消息）
- 非紧急任务用 WorkManager，系统会在 Doze 退出后统一执行

### 六、UI 层面优化

- **减少过度绘制**：去掉不必要的背景色，减少 overdraw
- **减少布局层级**：用 ConstraintLayout，减少 measure/layout 的 CPU 开销
- **动画优化**：避免持续运行的动画，页面不可见时暂停
- **列表优化**：用 RecyclerView 的缓存机制，减少滑动时的 CPU 负载

### 七、检测工具

#### 1. Battery Historian

Google 官方工具，导出 bugreport 后上传分析，可以看到：

- 各个硬件模块的唤醒时间线
- 哪个 App 的 WakeLock 占用最多
- 网络、GPS、CPU 的使用情况

```bash
# 导出 bugreport
adb bugreport > bugreport.zip

# 上传到 https://bathist.ef.lc/ 分析
```

#### 2. adb 命令

```bash
# 查看电量统计
adb shell dumpsys batterystats

# 重置电量统计
adb shell dumpsys batterystats --reset

# 查看 WakeLock 使用情况
adb shell dumpsys power | grep -i wakelock
```

#### 3. Android Studio Energy Profiler

AS 自带的电量分析工具，可以直观看到 CPU、网络、WakeLock 的使用情况。

### 一句话总结

电量优化的核心就是三个原则：**少唤醒**（减少 WakeLock、控制后台任务）、**少请求**（合并网络请求、降低定位频率）、**晚执行**（用 WorkManager/JobScheduler 让系统调度，顺应 Doze 模式）。配合 Battery Historian 做定量分析，找到耗电大户针对性优化。

## Q9: 在 App 中如何监测 Native Crash，如何利用 Native Crash 堆栈分析来定位系统级崩溃根源？

Native Crash 是 Android 开发中最难排查的一类崩溃——发生在 native 层，没有 Java 异常栈，进程直接死亡。分**崩溃类型、监测方案、堆栈分析定位根源**三块来说。

### 一、Native Crash 的常见类型

Native Crash 本质上是进程收到了**致命信号**或触发了**运行时错误**，分几类：

#### 1. 信号类崩溃 — 最常见

| 信号 | 含义 | 典型原因 |
|------|------|----------|
| **SIGSEGV (11)** | 段错误，访问了非法内存地址 | 空指针解引用、野指针、已释放内存访问 |
| **SIGABRT (6)** | 主动 abort | `__builtin_trap()`、double free、堆损坏检测触发 |
| **SIGBUS (7)** | 总线错误 | 内存对齐错误、mmap 文件访问越界 |
| **SIGFPE (8)** | 算术异常 | 除零、整数溢出 |
| **SIGILL (4)** | 非法指令 | 执行了非法的 CPU 指令（so 损坏或架构不匹配） |

崩溃时的日志长这样：

```
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0000000000000000
  #00 pc 0x00012345 /lib/xxx.so (some_function+123)
  #01 pc 0x00056789 /lib/xxx.so (another_function+456)
  #02 pc 0x000abcde /system/lib64/libart.so (art_quick_generic_jni_trampoline+114)
```

> 关键信息：**signal 编号**告诉你崩溃类型，**pc 地址**告诉你崩溃发生在 so 的哪个位置，**fault addr** 告诉你访问的非法地址。

#### 2. JNI 检测类崩溃

ART 虚拟机在运行时会做各种 JNI 检查，检测到违规直接 abort：

- **JNI 全局引用/局部引用误用**：跨线程使用局部引用
- **JNI 函数调用顺序错误**：比如在 GetPrimitiveArrayCritical 和 ReleasePrimitiveArrayCritical 之间调了其他 JNI 函数
- **JNIEnv 指针跨线程使用**：JNIEnv 是线程绑定的，不能跨线程传递

崩溃日志通常带有：

```
JNI DETECTED ERROR IN APPLICATION: use of deleted global reference
    from void com.xxx.MyClass.nativeMethod()
```

#### 3. ANR 导致的 Native 层超时

主线程在 native 层执行耗时操作（比如 IO、锁等待），导致 ANR。虽然不算严格意义的 Native Crash，但排查时需要看 native 堆栈：

```
"main" prio=5 tid=1 Blocked
  | group="main" sCount=1 dsCount=0 flags=1 obj=0x...
  native: #00 pc 0x0007a84c /apex/.../libc.so (syscall + 28)
  native: #01 pc 0x000abcde /lib/xxx.so (native_lock_wait + 200)
```

### 二、监测方案

#### 1. 系统级 — Tombstone 日志

Android 系统在 native crash 时会自动生成 **tombstone** 文件（`/data/tombstones/tombstone_XX`），这是最权威的崩溃现场记录：

```bash
# 查看最新的 tombstone
adb shell cat /data/tombstones/tombstone_00

# 列出所有 tombstone
adb shell ls -la /data/tombstones/
```

tombstone 里包含的关键信息：

```
*** *** *** *** *** *** *** *** *** *** *** *** *** *** *** ***
Build fingerprint: 'google/...'
Revision: '...'
ABI: 'arm64'
pid: 12345, tid: 12345, name: main  >>> com.example.app <<<
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0
    x0  0000000000000000  x1  0000000000000001
    
backtrace:
    #00 pc 0x00012345  /lib/xxx.so (crash_function+123)
    #01 pc 0x00056789  /lib/xxx.so (caller_function+456)
    #02 pc 0x000abcde  /system/lib64/libart.so (...)
```

> 关键看 **signal**（崩溃类型）、**fault addr**（非法地址）、**backtrace**（调用栈）、**寄存器状态**。

#### 2. 应用级 — 注册信号处理器

在 native 层注册信号处理器，在进程崩溃前抢救现场信息：

```c
#include <signal.h>
#include <unistd.h>

void crash_handler(int sig, siginfo_t *info, void *context) {
    // ★ 在信号处理器中只能做最少的事（async-signal-safe）
    // 不能调 malloc、printf、log 等非安全函数
    
    // 方案一：写文件（用 write 系统调用，是 async-signal-safe 的）
    int fd = open("/data/data/com.example.app/crash.log", O_WRONLY | O_CREAT);
    char buf[256];
    int len = snprintf(buf, sizeof(buf), 
        "signal=%d, fault_addr=%p\n", sig, info->si_addr);
    write(fd, buf, len);
    close(fd);
    
    // 方案二：设置标志位，下次启动时读取上报
    // 不要用全局变量直接赋值，用 sig_atomic_t
}

void install_crash_handler() {
    struct sigaction action;
    action.sa_sigaction = crash_handler;
    action.sa_flags = SA_SIGINFO | SA_ONSTACK;  // SA_ONSTACK 使用备用栈
    sigemptyset(&action.sa_mask);
    
    sigaction(SIGSEGV, &action, NULL);
    sigaction(SIGABRT, &action, NULL);
    sigaction(SIGBUS, &action, NULL);
    sigaction(SIGFPE, &action, NULL);
    sigaction(SIGILL, &action, NULL);
}
```

> 注意：信号处理器里**只能调 async-signal-safe 的函数**（`write`、`open`、`close`、`_exit` 等），不能调 `malloc`、`printf`、`LOG` 这些，否则可能死锁或二次崩溃。

#### 3. 第三方崩溃监控 SDK（推荐）

实际项目中不会自己写信号处理器，直接用成熟的 SDK：

| 工具 | 特点 |
|------|------|
| **Firebase Crashlytics** | Google 官方，自动捕获 native crash，支持符号化，免费 |
| **Bugly** | 腾讯，国内用得多，native crash 符号化做得好，有符号表管理后台 |
| **Sentry** | 开源，支持 native 符号化，可自建服务器 |
| **Matrix (微信)** | 腾讯开源，除了崩溃监控还有内存/卡顿检测 |

这些 SDK 的底层原理都差不多：

1. 注册信号处理器，捕获 native crash
2. 在信号处理器中采集当前线程的 native 堆栈（用 `backtrace` 或 `libunwindstack`）
3. 同时采集 Java 堆栈、寄存器状态、内存映射等上下文
4. 写入本地文件，下次启动时上报到服务器
5. 服务端做**符号化**，把 pc 地址翻译成函数名和行号

#### 4. logcat 中的崩溃信息

native crash 发生时，logcat 也会记录关键信息：

```bash
# 实时查看 native crash 日志
adb logcat -b crash

# 过滤特定进程
adb logcat -b crash | grep "com.example.app"
```

### 三、堆栈分析 — 定位崩溃根源

拿到 Native Crash 堆栈后，最关键的一步是**把 pc 地址翻译成可读的函数名和行号**，这就是符号化。

#### 1. 符号化前提 — 保留符号表

编译 native 代码时，需要生成并保留**符号表文件**（带 debug info 的 so）：

```groovy
// build.gradle
android {
    buildTypes {
        release {
            // 保留符号表，不要 strip
            // 或者 strip 后单独保存符号表
            packagingOptions {
                jniLibs {
                    keepDebugSymbols += ['**/*.so']
                }
            }
        }
    }
}
```

> 没有符号表的 so 文件，堆栈里只有 `pc 0x00012345`，完全看不出是哪个函数。符号表是分析 Native Crash 的**前提条件**。

#### 2. ndk-stack — 最常用的符号化工具

NDK 自带的工具，直接把崩溃日志喂给它就能符号化：

```bash
# 方式一：管道输入
adb logcat -b crash | ndk-stack -sym /path/to/symbol_dir/

# 方式二：处理 tombstone 文件
ndk-stack -sym /path/to/symbol_dir/ < tombstone_00

# 方式三：指定多个符号目录（多个 so 来自不同模块）
ndk-stack -sym /path/to/app/symbols -sym /path/to/sdk/symbols < crash.log
```

符号化后的效果：

```
// 符号化前
#00 pc 0x00012345 /lib/xxx.so

// 符号化后
#00 pc 0x00012345 /lib/xxx.so (MyClass::processData(char const*)+123)
           /path/to/src/MyClass.cpp:45
```

> 直接定位到了**源文件和行号**，这就是定位崩溃根源的关键一步。

#### 3. addr2line / llvm-symbolizer — 精确到行号

如果只有单个 pc 地址需要查，用 `addr2line` 或 `llvm-symbolizer` 更方便：

```bash
# addr2line（传统工具）
aarch64-linux-android-addr2line -e /path/to/libxxx.so -f -C 0x00012345
# 输出：
# MyClass::processData(char const*)
# /path/to/src/MyClass.cpp:45

# llvm-symbolizer（推荐，更准确）
llvm-symbolizer --obj=/path/to/libxxx.so 0x00012345
# 输出：
# MyClass::processData(char const*)
# /path/to/src/MyClass.cpp:45:12
```

> `-f` 显示函数名，`-C` 反修饰 C++ 函数名（显示参数类型）。`llvm-symbolizer` 比 `addr2line` 更准确，特别是处理内联函数时。

#### 4. 处理内联函数 — 堆栈可能不完整

编译器优化（`-O2`/`-O3`）会做**函数内联**，导致堆栈中缺少被内联的函数。解决方法：

```bash
# llvm-symbolizer 能自动识别内联函数
llvm-symbolizer --obj=/path/to/libxxx.so --inlines 0x00012345
# 输出：
# inner_function()
# /path/to/src/inner.cpp:20:5
# (inlined by) outer_function()
# /path/to/src/outer.cpp:45:12
```

> 加了 `--inlines` 参数后，会把被内联的函数也展开显示出来，堆栈更完整。

#### 5. 混淆/Strip 后的 so 怎么分析

如果发布的 APK 里 so 已经被 strip（去掉了符号信息），但保留了符号表文件，照样能分析：

```bash
# 用未 strip 的符号表 so 做符号化
ndk-stack -sym /path/to/unstripped_symbols/ < crash.log

# 注意：符号表 so 和发布 so 必须是同一次编译的产物
# 不同编译版本的地址布局可能不同，符号化结果会错
```

> 如果连符号表都丢了，那就**没法符号化**了。所以一定要在 CI/CD 流程中**自动归档符号表**。

#### 6. 常见崩溃模式的堆栈特征

| 堆栈特征 | 可能的原因 |
|----------|------------|
| `fault addr 0x0` + 某个函数开头 | 空指针解引用，对象为 null |
| `fault addr` 是一个很小的地址（如 `0x10`） | 访问了 null 指针的成员变量/偏移量 |
| `signal SIGABRT` + `JNI DETECTED ERROR` | JNI 使用违规，看具体错误描述 |
| `signal SIGABRT` + `double free` | 同一块内存被 free 了两次 |
| 堆栈里出现 `malloc`/`free` 相关函数 | 堆内存损坏，可能是 use-after-free 或 buffer overflow |
| 堆栈很深 + `signal SIGSEGV` | 可能是栈溢出（递归太深或局部变量太大） |
| 随机地址崩溃，堆栈无法解析 | so 文件损坏，或地址被覆写（安全攻击） |

#### 7. 进阶 — 本地复现与调试

如果堆栈分析不够明确，需要在本地复现：

```bash
# 用 ndk-gdb / lldb 附加到进程调试
ndk-gdb --launch

# 或者用 lldb 附加
lldb-server gdb-remote 5039

# 在调试器中崩溃时，能看到完整的寄存器和内存状态
(lldb) bt          # 查看调用栈
(lldb) reg read    # 查看寄存器
(lldb) mem read $x0  # 查看内存内容
```

### 四、预防与最佳实践

```
编译期预防：
  ✓ 开启编译器警告（-Wall -Wextra），修复所有警告
  ✓ 使用 AddressSanitizer (ASan) 做本地测试，检测内存越界和 use-after-free
  ✓ 使用 ThreadSanitizer (TSan) 检测数据竞争
  ✓ 编译时保留符号表，CI/CD 自动归档

运行期防护：
  ✓ JNI 层做好空指针检查、异常检查
  ✓ JNIEnv 不要跨线程传递，局部引用不要跨 JNI 调用保存
  ✓ Critical section 之间不调其他 JNI 函数
  ✓ 用智能指针（shared_ptr/unique_ptr）管理 native 内存

监测与定位：
  ✓ 接入 Crashlytics/Bugly 等 SDK，自动捕获和符号化
  ✓ 保留 tombstone 日志
  ✓ 符号化堆栈，定位到源文件和行号
  ✓ 结合代码 review 分析崩溃上下文
```

### 一句话总结

Native Crash 监测靠**第三方 SDK（Crashlytics/Bugly）+ tombstone 日志 + logcat**，核心是捕获崩溃信号并保留现场。定位根源的关键是**堆栈符号化**——用 **ndk-stack** 或 **llvm-symbolizer** 把 pc 地址翻译成函数名和行号，前提是**编译时保留符号表并归档**。根据堆栈的 signal 类型、fault addr、调用链特征，就能判断出是空指针、内存越界、JNI 违规还是堆损坏，从而精准定位崩溃根源。

## Q10: LiveData 底层原理是什么？

LiveData 的核心就是**观察者模式 + 生命周期感知**。它能在数据变化的时候通知 UI 更新，而且只在页面可见的时候才更新，不会在页面销毁后还去操作 View。

### 一、核心类结构

LiveData 涉及三个核心角色：

| 角色 | 职责 |
|------|------|
| **LiveData** | 数据持有者，维护观察者列表，数据变化时通知观察者 |
| **Observer** | 观察者，接收数据变化的回调 |
| **LifecycleOwner** | 生命周期拥有者（Activity/Fragment），告诉 LiveData 当前页面的生命周期状态 |

### 二、observe 注册流程

调用 `liveData.observe(owner, observer)` 的时候，底层做了这几件事：

```java
// 伪代码
public void observe(LifecycleOwner owner, Observer<T> observer) {
    // 1. 创建一个包装类，把 Observer 和生命周期绑定
    LifecycleBoundObserver wrapper = new LifecycleBoundObserver(owner, observer);
    
    // 2. 存到观察者 Map 中
    mObservers.putIfAbsent(observer, wrapper);
    
    // 3. 把 wrapper 注册到 Lifecycle 上，监听生命周期变化
    owner.getLifecycle().addObserver(wrapper);
}
```

> 关键点：**Observer 被包装成了 LifecycleBoundObserver**，它同时是一个 LifecycleObserver，能感知页面的生命周期。

### 三、数据更新流程

#### 1. 主线程 — setValue

```java
// 伪代码
protected void setValue(T value) {
    // 必须在主线程调用
    assertMainThread("setValue");
    
    // 版本号 +1
    mVersion++;
    mData = value;
    
    // 通知所有观察者
    dispatchingValue(null);
}
```

#### 2. 子线程 — postValue

```java
// 伪代码
protected void postValue(T value) {
    synchronized (mDataLock) {
        mPendingData = value;
    }
    
    // 通过 Handler 切到主线程执行 setValue
    ArchTaskExecutor.getMainThreadExecutor().execute(() -> {
        T value = mPendingData;
        mPendingData = NOT_SET;
        setValue(value);
    });
}
```

> `postValue` 本质上是把值暂存起来，然后通过 Handler 切到主线程再调 `setValue`。如果短时间内多次 `postValue`，只有**最后一次**会生效。

#### 3. 通知观察者

```java
// 伪代码
private void dispatchingValue(...) {
    for (Map.Entry<Observer, LifecycleBoundObserver> entry : mObservers) {
        LifecycleBoundObserver wrapper = entry.getValue();
        
        // ★ 关键：检查生命周期状态
        if (!wrapper.shouldBeActive()) {
            continue;  // 不是 Active 状态，不通知
        }
        
        // ★ 关键：版本号检查，避免重复通知
        if (wrapper.isNewData(mVersion)) {
            wrapper.activeStateChanged(true);  // 触发回调
        }
    }
}
```

### 四、生命周期感知 — 核心设计

这是 LiveData 最巧妙的地方。`LifecycleBoundObserver` 实现了 `GenericLifecycleObserver`，能感知生命周期变化：

```java
// 伪代码
class LifecycleBoundObserver implements GenericLifecycleObserver {
    
    @Override
    public void onStateChanged(LifecycleOwner source, Lifecycle.Event event) {
        // 页面销毁了，自动移除观察者
        if (source.getLifecycle().getCurrentState() == DESTROYED) {
            removeObserver(mObserver);
            return;
        }
        
        // 根据生命周期状态决定是否激活
        boolean shouldBeActive = shouldBeActive();
        if (shouldBeActive != mActive) {
            mActive = shouldBeActive;
            activeStateChanged(shouldBeActive);
        }
    }
    
    // Activity/Fragment 在 STARTED 或 RESUMED 状态时算 Active
    boolean shouldBeActive() {
        return mOwner.getLifecycle().getCurrentState().isAtLeast(STARTED);
    }
}
```

> 这就是为什么 LiveData 不会在页面不可见时更新 UI——只有 `STARTED` 或 `RESUMED` 状态才会触发回调。

### 五、粘性事件 — observe 时立即回调

调用 `observe` 之后，如果 LiveData 里已经有数据了，会**立即触发一次回调**：

```java
// 伪代码
public void observe(...) {
    // ...
    // 注册完成后，如果已经有数据，立即通知
    if (mData != null) {
        wrapper.activeStateChanged(true);
    }
}
```

> 这个特性有时候有用（比如屏幕旋转后恢复数据），有时候会造成问题（比如重复请求）。如果需要避免，可以用 `SingleLiveEvent` 或者 `Event` 包装类。

### 六、线程安全

LiveData 内部用了一些机制保证线程安全：

- **`mVersion`**：每次 `setValue` 版本号 +1，观察者通过版本号判断是否需要更新
- **`synchronized`**：`postValue` 里的 `mPendingData` 用锁保护
- **`assertMainThread`**：`setValue` 强制在主线程调用，避免并发问题

### 七、LiveData 的优缺点

| 优点 | 缺点 |
|------|------|
| 生命周期感知，不会内存泄漏 | 数据可变，不适合复杂状态管理 |
| 自动在页面销毁时取消订阅 | 粘性事件可能导致重复操作 |
| 配置变更（屏幕旋转）后自动恢复数据 | 只能单线程操作（主线程 setValue） |
| 始终保证 UI 和数据一致 | 不支持背压、操作符少 |

> 如果需要更复杂的状态管理，建议用 **StateFlow** 或 **SharedFlow** 替代 LiveData。

### 一句话总结

LiveData 的核心原理就是**观察者模式 + 生命周期感知**。数据变化时通过版本号机制通知所有观察者，但只有生命周期处于 `STARTED` 或 `RESUMED` 状态的观察者才会收到回调。页面销毁时自动移除观察者，避免内存泄漏。`setValue` 必须在主线程调用，`postValue` 通过 Handler 切到主线程执行。

## Q11: ViewModel 底层原理是什么？

ViewModel 的核心就是**利用 Activity 的 NonConfigurationInstances 机制，在配置变更（比如屏幕旋转）时保留数据不丢失**。

### 一、ViewModel 的核心作用

- **配置变更时数据不丢失**：屏幕旋转、语言切换等导致 Activity 重建，ViewModel 里的数据还在
- **跨组件共享数据**：多个 Fragment 可以共享同一个 ViewModel
- **解耦 UI 和数据**：数据逻辑放 ViewModel，UI 逻辑放 Activity/Fragment

### 二、核心类结构

| 类 | 职责 |
|----|------|
| **ViewModel** | 数据持有者，开发者继承它来存业务数据 |
| **ViewModelStore** | 存储 ViewModel 实例的容器（内部是个 HashMap） |
| **ViewModelStoreOwner** | 接口，Activity/Fragment 实现它，提供 ViewModelStore |
| **ViewModelProvider** | 工厂类，负责创建或获取 ViewModel 实例 |
| **ViewModelProvider.Factory** | ViewModel 的工厂接口，决定怎么创建 ViewModel |

### 三、ViewModel 的创建和获取

调用 `ViewModelProvider(this).get(MyViewModel::class.java)` 的时候，底层流程：

```java
// 伪代码
public <T extends ViewModel> T get(Class<T> modelClass) {
    String canonicalName = modelClass.getCanonicalName();
    
    // 1. 先从 ViewModelStore 里找
    ViewModel viewModel = store.get(canonicalName);
    
    // 2. 找到了就直接返回
    if (modelClass.isInstance(viewModel)) {
        return (T) viewModel;
    }
    
    // 3. 没找到，用 Factory 创建
    viewModel = factory.create(modelClass);
    
    // 4. 存到 ViewModelStore 里
    store.put(canonicalName, viewModel);
    
    return (T) viewModel;
}
```

> 关键点：**ViewModel 是单例的**（在同一个 ViewModelStoreOwner 范围内）。第一次调用 `get()` 创建，后面再调直接返回缓存的。

### 四、ViewModelStore 的存储结构

```java
public class ViewModelStore {
    // 内部就是个 HashMap，key 是类名，value 是 ViewModel 实例
    private final HashMap<String, ViewModel> mMap = new HashMap<>();
    
    final void put(String key, ViewModel viewModel) {
        ViewModel oldViewModel = mMap.put(key, viewModel);
    }
    
    final ViewModel get(String key) {
        return mMap.get(key);
    }
    
    // 清理所有 ViewModel
    public final void clear() {
        for (ViewModel vm : mMap.values()) {
            vm.onCleared();  // 回调清理方法
        }
        mMap.clear();
    }
}
```

### 五、核心原理 — NonConfigurationInstances 机制

这是 ViewModel 能在配置变更时存活的关键。

#### 1. Activity 重建时的数据保留

当 Activity 因为配置变更（屏幕旋转）被销毁时，系统会调用 `onRetainNonConfigurationInstance()`：

```java
// Activity 源码
@Override
public final Object onRetainNonConfigurationInstance() {
    // ★ 关键：把 ViewModelStore 保存起来
    Object retained = mNonConfigurationInstances;
    if (retained == null && mViewModelStore != null) {
        NonConfigurationInstances nci = new NonConfigurationInstances();
        nci.viewModelStore = mViewModelStore;  // ★ 把 ViewModelStore 塞进去
        retained = nci;
    }
    return retained;
}
```

> 系统会把这个返回值保存起来，等 Activity 重建后，新的 Activity 实例可以通过 `getLastNonConfigurationInstance()` 拿回来。

#### 2. 新 Activity 恢复 ViewModelStore

```java
// Activity 重建时
NonConfigurationInstances nci = getLastNonConfigurationInstance();
if (nci != null) {
    // ★ 从旧 Activity 拿回 ViewModelStore
    mViewModelStore = nci.viewModelStore;
} else {
    // 第一次创建，新建一个空的
    mViewModelStore = new ViewModelStore();
}
```

> 所以屏幕旋转后，虽然 Activity 是新的，但 ViewModelStore 是旧的，里面的 ViewModel 自然也在。

#### 3. 什么时候真正清理？

只有 Activity **真正 finish**（不是配置变更）的时候，才会清理 ViewModelStore：

```java
// Activity onDestroy
if (isChangingConfigurations()) {
    // 配置变更，不清理，保留给新 Activity 用
} else if (isFinishing()) {
    // 真正关闭，清理 ViewModelStore
    mViewModelStore.clear();
}
```

### 六、ViewModelProvider.Factory

默认情况下，ViewModel 必须有**无参构造函数**。如果需要传参，就得自定义 Factory：

```kotlin
class MyViewModelFactory(private val userId: String) : ViewModelProvider.Factory {
    override fun <T : ViewModel> create(modelClass: Class<T>): T {
        if (modelClass.isAssignableFrom(MyViewModel::class.java)) {
            @Suppress("UNCHECKED_CAST")
            return MyViewModel(userId) as T
        }
        throw IllegalArgumentException("Unknown ViewModel class")
    }
}

// 使用
val viewModel = ViewModelProvider(this, MyViewModelFactory("user123"))
    .get(MyViewModel::class.java)
```

> AndroidX 还提供了 `SavedStateViewModelFactory`，支持带 `SavedStateHandle` 参数的 ViewModel，能在进程被杀后恢复数据。

### 七、Fragment 之间的数据共享

多个 Fragment 可以共享同一个 ViewModel，只要它们属于同一个 Activity：

```kotlin
// Fragment A
val sharedViewModel = ViewModelProvider(requireActivity()).get(SharedViewModel::class.java)

// Fragment B
val sharedViewModel = ViewModelProvider(requireActivity()).get(SharedViewModel::class.java)

// 两个 Fragment 拿到的是同一个 ViewModel 实例
```

> 关键点：`ViewModelProvider` 的第一个参数传的是 `requireActivity()`，这样两个 Fragment 共享的是 Activity 级别的 ViewModelStore。

### 八、ViewModel 的生命周期

```
Activity 创建
  → ViewModelStore 创建
  → ViewModelProvider.get() 创建 ViewModel

屏幕旋转（配置变更）
  → Activity 销毁
  → onRetainNonConfigurationInstance() 保存 ViewModelStore
  → 新 Activity 创建
  → 恢复旧的 ViewModelStore
  → ViewModelProvider.get() 返回同一个 ViewModel

Activity finish（真正关闭）
  → ViewModelStore.clear()
  → 所有 ViewModel 的 onCleared() 被调用
  → ViewModel 被销毁
```

### 九、ViewModel vs Activity 的 onSaveInstanceState

| 维度 | ViewModel | onSaveInstanceState |
|------|-----------|---------------------|
| **存储位置** | 内存 | Bundle（磁盘/系统进程） |
| **配置变更** | ✅ 保留 | ✅ 保留 |
| **进程被杀** | ❌ 丢失 | ✅ 保留 |
| **数据大小** | 任意大小 | 有限制（~1MB） |
| **数据类型** | 任意对象 | 必须是 Parcelable/Serializable |

> 最佳实践：**ViewModel 存业务数据**（列表、用户信息），**SavedStateHandle 存少量需要持久化的状态**（搜索关键词、滚动位置）。

### 一句话总结

ViewModel 的核心原理是利用 Activity 的 **`NonConfigurationInstances` 机制**：配置变更时，系统通过 `onRetainNonConfigurationInstance()` 把 `ViewModelStore` 保存下来，新 Activity 重建时通过 `getLastNonConfigurationInstance()` 恢复，从而让 ViewModel 里的数据"活过"Activity 的重建。只有 Activity 真正 finish 时才会调用 `clear()` 清理所有 ViewModel。

#### 3. TraceView / Method Trace

TraceView 是 Android 提供的**方法级性能分析工具**，能记录应用运行期间每个方法的调用次数、耗时、调用链，生成可视化的时间线图和调用统计表。虽然已经被 Perfetto 逐步替代，但在**方法级耗时分析**场景下依然非常实用。

##### （1）代码插桩 — 手动打点

在代码中指定要分析的区段：

```kotlin
// ★ 开始记录，参数是 trace 文件名（不含后缀）

// ... 要分析的代码 ...

// ★ 停止记录，生成 .trace 文件
Debug.stopMethodTracing()
```

> trace 文件默认保存在 `/sdcard/Android/data/<package_name>/files/` 目录下。

如果需要更细粒度的控制，可以用 `startMethodTracingSampling` 采样模式（开销更小）：

```kotlin
// 采样模式，每 100 微秒采样一次
Debug.startMethodTracingSampling("my_trace", 8 * 1024 * 1024, 100)
// ... 要分析的代码 ...
Debug.stopMethodTracing()
```

##### （2）命令行方式 — 无需改代码

不需要改代码，直接用 adb 命令对正在运行的 App 进行 trace：

```bash
# 开始 trace（--sampling 采样模式，对性能影响小）
adb shell am profile start --sampling <package_name> /sdcard/trace.trace

# 操作 App ...

# 停止 trace
adb shell am profile stop <package_name>

# 拉到本地分析
adb pull /sdcard/trace.trace .
```

> 注意：`am profile start` 等价于代码里的 `Debug.startMethodTracing`，生成的文件格式一样。

##### （3）分析 Trace 文件

**方式一：Android Studio CPU Profiler（推荐）**

直接在 AS 中打开 `.trace` 文件，会展示：

- **Top Down 视图**：从调用者到被调用者的树形展开，看每个方法的子方法耗时
- **Bottom Up 视图**：从被调用者向上看谁调用了它，快速定位最耗时的方法
- **Flame Chart（火焰图）**：横轴是时间，纵轴是调用栈，直观看整个执行过程

**方式二：命令行 dmtracedump**

```bash

# 生成方法耗时排序

```

##### （4）TraceView 的关键指标

| 指标 | 含义 |
|------|------|
| **Wall Clock Time** | 方法从开始到结束的总时间（包含等待、阻塞时间） |
| **Thread Time** | 方法实际占用 CPU 的时间（排除等待时间） |
| **Self Time** | 方法自身执行耗时（不包含调用子方法的时间） |
| **Inclusive Time** | 方法总耗时（包含所有子方法调用） |
| **Call Count** | 方法被调用的次数 |

> 重点关注 **Self Time** 高的方法 — 这些是真正耗时的瓶颈，而不是那些只是调了一堆子方法的"壳方法"。

##### （5）TraceView 的优缺点

| 优点 | 缺点 |
|------|------|
| 方法级精度，能精确定位哪个函数慢 | **性能开销大**，开启 trace 后 App 会变慢 2~10 倍 |
| 支持代码插桩和命令行两种方式 | 不适合分析帧率、卡顿等系统级问题（用 Perfetto） |
| AS 的 Flame Chart 可视化效果好 | 只能分析 Java/Kotlin 层（native 层用 Simpleperf） |
| 支持采样模式降低开销 | 采样模式可能漏掉执行很短的方法 |

##### （6）TraceView vs Perfetto 选择建议

| 场景 | 推荐工具 |
|------|----------|
| 定位某个操作里哪个方法最耗时 | **TraceView** |
| 分析帧率、CPU 调度、系统级卡顿 | **Perfetto** |
| 分析启动流程中各方法的耗时 | **TraceView**（方法级）+ Perfetto（系统级） |
| 分析 native so 库的性能 | **Simpleperf** |

> 一句话：**TraceView 看方法，Perfetto 看系统**。两者互补，不是替代关系。

## Q13: Kotlin 的 async 在不调用 await 时也会执行吗？

是的，`async` 创建的协程**默认会立即开始执行**，不需要调用 `await` 才会执行。`await` 只是用来**等待结果并获取返回值**的。

### 一、默认行为 — 立即执行

```kotlin
fun main() = runBlocking {
    println("1. 开始")
    
    val deferred = async {
        println("3. async 内部开始执行")
        delay(1000)
        println("4. async 内部执行完毕")
        "result"
    }
    
    println("2. async 创建完毕，但还没调 await")
    
    // 即使不调用 await，async 里的代码也会执行
    delay(2000)
    println("5. 主协程等待完毕")
    
    // 这时候再调 await，结果早就准备好了
    val result = deferred.await()
    println("6. 拿到结果: $result")
}
```

输出：

```
1. 开始
2. async 创建完毕，但还没调 await
3. async 内部开始执行
4. async 内部执行完毕
5. 主协程等待完毕
6. 拿到结果: result
```

> 可以看到，`async` 创建后**立刻就执行了**，跟 `await` 没关系。

### 二、await 的作用

`await` 的作用不是"启动"协程，而是：

1. **挂起当前协程**，等待 async 的结果
2. **返回结果值**
3. 如果 async 里抛了异常，`await` 会**把异常抛出来**

```kotlin
val deferred = async {
    delay(1000)
    "hello"
}

// await 之前，async 已经在跑了
// await 只是等它跑完，拿到结果
val result = deferred.await()  // result = "hello"
```

### 三、如果想延迟执行 — CoroutineStart.LAZY

如果确实想让 async **等到调 await 时才开始执行**，需要传 `CoroutineStart.LAZY`：

```kotlin
fun main() = runBlocking {
    println("1. 开始")
    
    val deferred = async(start = CoroutineStart.LAZY) {
        println("3. async 内部开始执行（只有调 await 才会到这里）")
        delay(1000)
        "result"
    }
    
    println("2. async 创建完毕，但 LAZY 模式，还没执行")
    
    delay(500)
    println("2.5 过了 500ms，async 还是没执行")
    
    // ★ 只有调了 await（或 start()），async 才会真正开始执行
    val result = deferred.await()
    println("3. 拿到结果: $result")
}
```

输出：

```
1. 开始
2. async 创建完毕，但 LAZY 模式，还没执行
2.5 过了 500ms，async 还是没执行
3. async 内部开始执行（只有调 await 才会到这里）
3. 拿到结果: result
```

> `CoroutineStart.LAZY` 模式下，async 会等到第一次 `await()` 或 `start()` 调用时才开始执行。

### 四、对比 launch

`launch` 和 `async` 一样，默认也是立即执行的：

```kotlin
// 默认立即执行
launch { /* 立刻跑 */ }

// LAZY 模式，调 start() 或 join() 才执行
launch(start = CoroutineStart.LAZY) { /* 等调用才跑 */ }
```

### 五、实际开发中的建议

#### 1. 并行请求场景 — 默认就够用

```kotlin
suspend fun loadAllData() {
    val startTime = System.currentTimeMillis()
    
    // 两个 async 同时开始执行
    val deferred1 = async { fetchUserData() }   // 耗时 1s
    val deferred2 = async { fetchOrderData() }  // 耗时 1s
    
    // 等两个都完成
    val user = deferred1.await()
    val order = deferred2.await()
    
    // 总耗时 ≈ 1s（并行），而不是 2s（串行）
    println("总耗时: ${System.currentTimeMillis() - startTime}ms")
}
```

> 这种场景下，两个 async 创建后**立刻并行执行**，最后 `await` 拿结果，非常高效。

#### 2. 注意异常处理

async 里的异常不会立刻抛出，而是在 `await` 时才抛出：

```kotlin
val deferred = async {
    throw RuntimeException("出错了")
}

// 异常在 await 时才抛出来
try {
    deferred.await()
} catch (e: RuntimeException) {
    println("捕获异常: ${e.message}")
}
```

> 如果不调 `await`，异常会被"吞掉"（在 SupervisorJob 下），或者导致父协程取消（在普通 Job 下）。

### 一句话总结

`async` 创建的协程**默认立即执行**，`await` 只是用来等待结果和获取返回值的。如果想延迟到 `await` 时才执行，需要传 `CoroutineStart.LAZY`。实际开发中并行请求的场景，默认行为就够用了——多个 async 同时跑，最后各自 await 拿结果，效率最高。

## Q14: 请说一个你过往项目中遇到的最难的事情以及如何解决的？

### 难点背景

在 OSL 主导合约项目的实时数据架构设计时，遇到了一个多问题交织的核心难题。合约业务的特点是服务端通过 WebSocket 高频推送行情数据，需要在本地完成增量合并、公式计算，再稳定渲染到 UI 上，对数据时效性和连接稳定性要求极高。三个问题同时存在：

1. **连接不稳定**：用户网络切换、进隧道断网、WiFi 切蜂窝、前后台切换，任何一种场景都可能导致 WebSocket 断开，而合约场景对实时性要求极高，断几秒用户就可能亏钱
2. **多业务各自建连，资源浪费严重**：每个业务频道独立维护一条 WebSocket 连接，连接数多、服务端压力大、手机端耗电严重
3. **数据计算逻辑散落各处**：服务端下发的原始数据需要经过复杂公式计算才能渲染，计算逻辑耦合在各业务模块里，维护成本高，且服务端下发数据量大

### 解决方案（分三步）

#### 第一步：单连接多路复用

设计了一套**订阅注册表 + 路由键（channel + mainKey）的分发机制**：

- 所有业务频道的订阅请求统一走一条 WebSocket 连接
- 消息进来后根据路由键分发到对应的 MessageListener
- 再写入各自的 StateFlow 或 callbackFlow
- 利用 callbackFlow 的 awaitClose 实现订阅生命周期自动绑定和释放

**成果**：连接数直接砍了 50%

#### 第二步：三层断连自愈机制

这是最花精力的部分，三层协作覆盖六类触发场景：

| 层级 | 机制 | 作用 |
|------|------|------|

## Q16: 说一个印象最深的 bug 以及如何解决的？

### 现象

OSL 合约项目上线后收到用户反馈：持仓数据不变化了，但下单、行情都正常。重启 App 就恢复。运维查服务端日志，连接一直在，心跳也没断。问题复现不规律，有时几个小时，有时一两天才出现一次。

### 排查过程

在本地加了全链路日志，把每条 WebSocket 消息的收发、每个频道的订阅状态全部打出来。抓了两天终于复现。

### 根因

**客户端与服务端的订阅状态不一致**：

- 用户短暂切后台（比如切出去回个微信，不到 3 秒就回来），前后台退订的 3 秒防抖没有触发退订，TCP 连接一直活着
- 但服务端在连接空闲一段时间后，**静默清理了部分频道的订阅关系**
- 客户端以为订阅还在，服务端已经不推了
- 心跳只检测 TCP 连接是否存活，不检测订阅关系是否还有效，所以心跳完全正常

本质上是——**连接活着 ≠ 业务活着**。

### 修复方案

做了两件事：

1. **前台恢复时强制重新订阅**：不管连接是否断开，每次从后台回前台都重新发送一次全量订阅请求，而不是假设之前的订阅还有效。订阅请求是幂等的，服务端收到重复订阅不会有副作用。

2. **增加订阅级健康检查**：在三层自愈机制里加了一层“订阅巡检”——定时向服务端查询当前连接的订阅状态，和本地订阅注册表做比对，发现不一致的频道自动补发订阅。

### 结果

修复后该问题再未出现。

### 教训

做长连接架构时，不能只检测 TCP 层是否连通，还要保证业务层的订阅关系、会话状态这些“软状态”是一致的。尤其是客户端和服务端对同一个状态的理解可能不同，**一定要有一个对账/校准机制**。

### 一句话总结

印象最深的 bug 是 WebSocket **连接活着但业务层订阅状态不一致**导致数据不更新，修复方法是前台恢复时强制重新订阅 + 增加订阅级健康巡检，核心教训是**连接活着 ≠ 业务活着**。

## Q18: Kotlin 协程构建器的作用是什么？底层做了什么？为什么 GlobalScope 不建议使用？

### 一、协程构建器的作用

协程构建器本质上是**把一个 suspend 函数“启动起来”的入口函数**。suspend 函数自己不会执行，必须依附于一个协程，构建器就是负责创建协程、绑定作用域、启动执行的“启动器”。

| 构建器 | 返回值 | 特点 | 典型场景 |
|--------|--------|------|----------|
| `launch` | `Job` | 发射即忘，不返回结果 | 后台任务、UI 更新 |
| `async` | `Deferred<T>` | 有返回值，通过 `await()` 获取结果 | 并行请求、需要结果的异步任务 |
| `runBlocking` | `T` | **阻塞当前线程**直到协程完成 | main 函数入口、测试代码 |
| `withContext` | `T` | 不创建新协程，只切换上下文 | 切到 IO 线程做计算再切回来 |
| `coroutineScope` | `T` | 创建子作用域，**等待所有子协程完成**后才返回 | 并行执行多个子任务并汇总 |

---

### 二、底层做了什么

以 `launch` 为例，调用 `launch { ... }` 时底层做了这几件事：

#### 1. 构建 CoroutineContext

把 CoroutineScope 自带的 context 和传入的 context 做合并：

```kotlin
// 简化逻辑
val context = this.context + givenContext  // 比如 Dispatchers.IO + Job + CoroutineName
```

合并后的 context 包含：调度器（决定在哪个线程执行）、Job（协程的生命周期节点）、异常处理器等。

#### 2. 创建协程对象（状态机）

通过 `createCoroutine` 把 suspend 函数体包装成一个协程对象。编译器在编译期把 suspend 函数体改写成了**状态机**：

```kotlin
// 你写的代码
launch {
    val a = fetchData()    // 挂起点 1
    val b = processData(a) // 挂起点 2
    saveData(b)
}

// 编译器生成的状态机（简化）
when(label) {
    0 -> {
        // 执行到 fetchData()，保存状态，挂起
        label = 1
        fetchData(continuation)
    }
    1 -> {
        // 从 fetchData 恢复，a = result
        // 执行到 processData()，保存状态，挂起
        label = 2
        processData(a, continuation)
    }
    2 -> {
        // 从 processData 恢复，b = result
        saveData(b)
    }
}
```

每个挂起点都会把当前执行状态保存到 `Continuation` 对象里，挂起后线程可以去干别的事，恢复时从上次的位置继续执行。

#### 3. 启动协程

调用 `startCoroutine`，根据启动模式决定是**立即执行**还是**调度到指定线程后执行**：

- `Dispatchers.Main` → 通过 Handler post 到主线程
- `Dispatchers.IO` → 提交到线程池
- 遇到第一个挂起点时，协程挂起，控制权交还给调度器

#### 4. Job 层级关系

每个构建器启动时都会创建一个 `Job`，这个 Job 是父 Scope 的 Job 的子节点，形成一棵 **Job 树**。这就是结构化并发的基础——父协程取消时，所有子协程自动取消。

---

### 三、为什么不建议使用 GlobalScope

`GlobalScope` 是一个全局的、顶级的 CoroutineScope，它的 Job 跟应用生命周期一样长，永远不会被主动取消。

#### 1. 无法取消 → 资源泄漏

```kotlin
// 危险写法
fun loadData() {
    GlobalScope.launch {
        val data = api.fetchData()  // 网络请求可能要 10 秒
        updateUI(data)
    }
}
// 如果用户在 10 秒内离开了页面（Activity 销毁），
// 协程还在跑，请求还在发，回来更新 UI 时可能崩溃
```

用 `lifecycleScope` 或 `viewModelScope` 的话，页面销毁时协程自动取消。

#### 2. 破坏结构化并发

结构化并发的核心是：**子协程的生命周期不能超出父作用域**。GlobalScope 没有父作用域，它启动的协程是“孤儿”——没人管它什么时候该结束，也没人等它完成。

```kotlin
GlobalScope.launch { taskA() }
GlobalScope.launch { taskB() }
// 没有任何机制能等待这两个都完成，也没有机制能统一取消它们
```

#### 3. 异常处理失控

GlobalScope 启动的协程如果抛异常，会沿着 Job 树向上传播，但 GlobalScope 没有父 Job，最终会走到默认的 `CoroutineExceptionHandler`，如果没设置就直接崩溃。

#### 推荐做法

| 场景 | 推荐 Scope |
|------|------------|
| ViewModel 中 | `viewModelScope` |
| Activity/Fragment 中 | `lifecycleScope` |
| 主函数入口 | `runBlocking` |
| 需要自定义生命周期 | `CoroutineScope(SupervisorJob() + Dispatchers.Main)` |

Kotlin 1.8 之后，`GlobalScope` 已被标记为 `@DelicateCoroutinesApi`，IDE 会直接给出警告。

### 一句话总结

协程构建器是 suspend 函数的启动器，底层通过**状态机 + Continuation** 实现挂起和恢复，通过 **Job 树**实现结构化并发。GlobalScope 因为没有生命周期边界、无法取消、破坏结构化并发，所以不推荐使用。
