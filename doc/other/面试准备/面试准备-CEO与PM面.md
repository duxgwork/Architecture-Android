# 面试准备 — CEO & PM 面

> **核心人设**：同时担任 App 架构师与业务小组长，既能做顶层技术设计，也能带团队把事落地交付。

---

## 一、面试开场白

两位面试官好，我是杜显国。做 Android 开发十多年了，后面又加了 Flutter，也做了五年多。之前在饿了么、滴滴、小红书、KuCoin、OSL 这几家公司都待过，一直做核心业务开发和架构设计，有些项目 DAU 是千万级的。

简单说一下我自己怎么定位吧。我觉得我做的事情可以用一句话串起来：**架构师负责把方向选对，小组长负责把事做成**。我在 OSL 就是同时干这两件事——一边做合约项目的整体架构设计，WebSocket 实时数据、模块化分层这些；一边管着团队的任务分配、进度把控和向上汇报。说白了就是，既要保证技术底座撑得住业务长远发展，又要带着人把东西按时交出来。

这两个角色其实挺互补的。因为我自己做架构，分任务的时候能判断出哪里风险大、哪里复杂度高，排期不容易翻车；反过来说，因为我在带团队，做架构的时候就不会闷头画图纸，会先想"这个方案兄弟们能不能落地"、"业务等不等得起"。

如果要说我比较擅长什么的话，可能就是**把技术上的事情用业务语言讲清楚**。举个例子，我在 OSL 做了一套 WebSocket 实时数据的架构，听起来好像很技术对吧？但它的实际效果是——每天 50 万条以上的消息稳定处理，连接可用性从 95% 拉到了 99.5%，用户基本感觉不到网络抖动。这些数字背后就是用户体验和业务口碑。

很期待今天跟两位老师聊聊，谢谢。

## 二、架构决策 × 业务价值（架构师视角）

> 这部分重点展示：技术选型不是自嗨，每一个架构决策都要回答"它为业务解决了什么问题"。

### 问题1：你遇到过最大的技术/业务挑战是什么？

**回答（OSL WebSocket 实时数据架构）：**

- **S（背景）**：合约业务对实时性要求极高，行情数据、仓位变化、订单状态都需要毫秒级推送给用户。原有方案是每个业务模块各自维护一条 WebSocket 连接，连接数多、资源消耗大，且断连后恢复慢，用户经常看到数据"卡住"。

- **T（任务）**：作为架构师，我需要设计一套统一的实时数据架构，既要降低连接资源消耗，又要保证断连后快速恢复，同时让业务层对底层通信完全无感。

- **A（行动）**：我做了三件事——
  1. **单连接多路复用**：通过订阅注册表 + 路由键，所有业务共享一条 WebSocket 连接，消息按频道分发。连接数减少了 50%。
  2. **三层断连自愈机制**：WebSocket 层自愈 + 进程级巡检 + 前后台订阅管理，覆盖 6 类断连场景，连接可用性从 95% 提升到 99.5%。
  3. **QuickJS 本地公式计算**：服务端下发计算公式，本地用 QuickJS 引擎批量计算，减少 60% 的数据下发量，降低服务端压力。

- **R（结果）**：合约上线后获得公司最高荣誉——卓越贡献奖。

**架构师视角总结**：这套方案的核心设计哲学是**"基础设施下沉"**——把通用的通信能力收拢到平台层，业务层只需关注自身逻辑。这不仅解决了当下的问题，也为后续新业务接入提供了可复用的基础能力。

**PM 视角补充**：如果 PM 追问业务影响——"这个方案的核心价值是**用户几乎感知不到网络波动**，对合约交易这种对时效性极度敏感的场景来说，这直接减少了用户因数据延迟导致的交易损失投诉。"

### 问题2：你是如何做架构决策的？如何权衡方案？

**回答（KuCoin 支付架构重构）：**

在 KuCoin 做支付模块时，原有代码耦合严重，每接入一个新支付渠道需要 2 周。作为架构师，我做了两件事：

1. **组件化分层**：把支付模块拆成基础设施层 → 基础业务层 → 业务层 → 应用层，每层职责清晰，新渠道只需在业务层实现接口。
2. **策略模式重构**：抽象支付策略接口，每种支付方式独立实现，新增渠道不影响已有逻辑。

结果是接入周期从 2 周缩短到 3-5 天。

**我的架构决策原则是：架构服务于业务节奏**。

- 业务处于**快速探索期**：不过度设计，用最小可演进的结构支撑试错；
- 业务进入**稳定期**：提前做架构储备，降低后续迭代的边际成本；
- 业务面临**规模化阶段**：抽象通用能力，建设平台化基础设施。

判断业务处于哪个阶段，正是我作为小组长的优势——我比纯架构师更清楚业务下一步要往哪走。

### 问题3：你做过性能优化吗？效果如何量化？

**回答（滴滴 IM 消息列表优化）：**

滴滴 IM 消息列表在 5000+ 条消息时出现明显卡顿，帧率只有 42fps。我做了几个关键优化：

1. **DiffUtil 异步差分**替代全量刷新，避免无效 ViewHolder 重建。
2. **Realm 事务优化**：消息插入和会话摘要更新放同一事务，减少 IO 次数。
3. **已读回执节流上报**：debounce 300-500ms，避免高频网络请求。

帧率从 42fps 提升到 58fps，首屏加载耗时降低 50%。

**架构师视角**：性能优化不是一次性的救火，而是需要建立**可度量的性能基线**。我习惯在优化前先建立基准数据，优化后持续监控回归——这套方法论后来在 OSL 也复用了。

**小组长视角**：量化指标是说服业务方投入优化资源的关键。PM 不关心帧率是多少，但如果你告诉他"用户流失中有 15% 是因为体验卡顿"，优先级立刻就不一样了。

## 三、团队落地 × 交付保障（小组长视角）

> 这部分重点展示：再好的架构方案，如果团队执行不了、交付不了，就是零。

### 问题4：作为小组长，你如何进行任务分工？

我的任务分工遵循三个原则：

1. **按能力梯度分配**：核心链路（如支付、交易）交给经验丰富的人，边界清晰的新模块可以给成长中的同学，既是挑战也是培养机会。
2. **按业务域划分 Owner**：每个人负责一个完整的业务域（如行情、订单、资产），而不是按技术层切分。这样每个人对自己模块的端到端质量负责，减少"三不管地带"。
3. **预留 Buffer**：每个迭代预留 15-20% 的时间应对紧急需求和线上问题，避免排满导致计划频繁被打乱。

**架构师加持**：因为我自己做架构设计，所以在任务拆解时能准确判断哪些模块涉及核心架构变更、哪些是纯业务逻辑，从而更合理地评估复杂度和风险。纯管理背景的小组长往往在这个环节容易失真。

具体操作上，我会在迭代启动会上和团队一起拆解需求、评估工时，确保每个人清楚自己的交付物和验收标准。

---

### 问题5：你如何进行向上汇报？

我的汇报原则是**"结论先行，数据支撑，带着方案提问题"**。

1. **定期同步**：每周以周报形式同步进度，重点说三件事——本周完成了什么、下周计划做什么、有哪些风险需要协调。
2. **里程碑汇报**：关键节点（如架构方案确定、核心功能联调完成）主动同步，不等领导来问。
3. **风险前置**：如果发现进度可能延期，第一时间同步并附上我的应对方案，比如"X 功能可能延期 2 天，我的方案是先上线核心链路，次要功能下个迭代补齐"。

**双角色协同**：作为架构师，我能准确判断技术方案的进度和风险点，不会给出模糊的"快好了"；作为小组长，我能把技术语言翻译成管理层听得懂的业务语言。比如在 OSL 合约项目期间，我会把 WebSocket 可用性、消息处理量等技术指标，转化为"用户体验稳定性"这样的业务语言同步给管理层。最终项目获得卓越贡献奖，也和这种透明的沟通机制有关。

---

### 问题6：你如何进行向下管理？如何处理团队成员表现不佳的情况？

我的管理理念是**"明确预期 + 过程关注 + 及时反馈"**。

1. **明确预期**：任务分配时说清楚交付标准和时间节点，避免"我以为你理解的不一样"。
2. **过程关注**：不是微观管理，而是在关键节点做 Check。比如开发到一半时做一次 Code Review，提前发现问题而不是等到提测时才发现方向偏了。
3. **及时反馈**：做得好的及时认可，做得不好的私下沟通。

对于表现不佳的情况，我的做法是**先诊断原因再给方案**：

- 如果是**能力问题**，安排 Mentor 带教或者给更合适的任务；
- 如果是**态度问题**，直接沟通了解原因，是个人状态还是对任务不认同；
- 如果是**信息不对称**，反思是不是自己的任务描述不够清晰。

**架构师加持——用制度保障质量**：在小红书时，我推动了 Git 分支规范和 Code Review 机制；在 OSL，我把架构规范沉淀为文档和模板，让新成员能快速上手，降低因人员流动带来的质量波动。**好的架构不只是代码层面的，也包括团队协作层面的"架构"**。

## 四、高频追问准备

| 追问 | 回答要点 |
|------|----------|
| 你和产品/设计有分歧怎么处理？ | 先理解对方的业务目标，用数据说话（如 A/B 测试），最终对齐到用户价值。作为架构师，我会评估不同方案的技术成本和可演进性，给出"既满足业务需求、又不过度消耗技术资源"的折中方案 |
| 你既是架构师又是小组长，精力怎么分配？ | 不是 50/50 的切分，而是根据项目阶段动态调整。架构设计期偏架构侧，落地交付期偏管理侧。同时通过培养团队骨干、沉淀架构文档来降低对个人的依赖 |
| 你为什么离开上一一家公司？ | 聚焦成长和发展空间，不抱怨前公司 |
| 你的缺点是什么？ | 说一个真实的、正在改进的缺点，如"有时过于追求技术方案完美，现在会更多从 ROI 角度权衡——这也是从小组长视角学到的，技术完美主义要服务于业务交付节奏" |
| 你期望的薪资范围？ | 可以反问"贵司这个岗位的预算范围是多少"，或者给一个合理区间 |

## 五、核心建议

### 面对 CEO
- 多讲**业务价值和结果**，用数据量化贡献
- 突出"架构决策 → 业务收益"的因果链
- 展示战略思维：技术布局如何支撑业务发展方向

### 面对 PM
- 多讲**协作流程和交付保障**，展示项目管理能力
- 突出"架构能力 → 交付效率"的正向循环
- 展示同理心：理解业务节奏，技术方案服务于产品迭代

### 双角色叙事主线
- **架构师**证明"能做对"：技术选型准确、架构可演进、风险可控
- **小组长**证明"能做成"：团队能交付、进度可预期、质量有保障
- **两者结合**证明"能持续做对、持续做成"：不只是解决一个问题，而是建立一套可持续的方法论
