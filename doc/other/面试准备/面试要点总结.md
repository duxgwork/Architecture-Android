#### QuickJS 本地公式计算详解（业务动机）

**业务场景**：合约页面有大量实时数据（标记价格、未实现盈亏、强平价格、资金费率等），这些数据需要根据用户的持仓、杠杆、开仓价做**个性化计算**

**原方案（服务端计算）**：服务端为每个用户单独算好结果再下发
- 问题1：数据下发量随用户数线性增长，带宽成本高
- 问题2：服务端要为每个用户维护计算状态，CPU压力大
- 问题3：新增指标要改服务端逻辑，客户端被动等待

**新方案（本地QuickJS计算）**：服务端只下发原始数据 + JS公式脚本，客户端用QuickJS引擎本地计算
- 本质：**把个性化计算从服务端下沉到客户端**
- 原始数据是通用的，但计算结果因人而异 → 让客户端自己算更合理

**业务价值**：

| 维度 | 原来 | 现在 |
|------|------|------|
| 下发量 | 算好所有结果下发，量大 | 只下发原始数据+公式，**-60%** |
| 服务端压力 | 为每用户单独计算 | 只维护原始数据源，计算压力转移 |
| 扩展性 | 新增指标改服务端 | 下发新公式即可，**客户端零发版** |
| 实时性 | 受限于服务端排队 | 本地即时计算，延迟更低 |

**追问：为什么不用原生Kotlin写？**
→ 公式由服务端动态下发，原生代码改公式要发版。JS脚本下发，服务端改公式客户端即时生效，运营灵活性远高于原生

**追问：1000ms采样周期怎么定的？**
→ 人眼对1秒内变化感知有限，1000ms在保证"足够实时"的同时避免每帧计算的性能浪费，是用户体验和性能的平衡点

**追问：对UI层透明是什么意思？**
→ UI层不关心数据是服务端算的还是本地算的，只消费最终结果。底层计算引擎切换对上层业务代码零侵入

#### 单连接多路复用详解（业务动机）

**业务场景**：合约页面同时订阅多个业务频道的实时数据（标记价格、挂单/持仓、杠杆配置、资产组合、深度行情等）

**原方案（每业务独立连接）**：每个业务模块各自维护一条WebSocket
- 问题1：6个频道=6条连接，多合约切换时连接数成倍增长
- 问题2：每条连接独立心跳/握手，内存和电量浪费大
- 问题3：各模块各自管理重连，策略不统一，出问题难排查
- 问题4：服务端连接数 = 用户数×频道数，规模上去后压力巨大

**新方案（单连接多路复用）**：所有业务频道共享一条WebSocket，通过路由机制分发

```
                    ┌─ 标记价格 Listener → StateFlow
WebSocket ──路由分发──┼─ 挂单/持仓 Listener → StateFlow
(单连接)            ├─ 杠杆配置 Listener → callbackFlow
                    └─ 资产组合 Listener → callbackFlow
```

- **订阅注册表**：记录频道与Listener的映射
- **路由键（channel/mainKey）**：消息到达时按频道标识找到对应Listener
- **callbackFlow + awaitClose**：Flow生命周期与订阅自动绑定/释放，页面销毁自动退订

**业务价值**：

| 维度 | 原来 | 现在 |
|------|------|------|
| 连接数 | 每业务一条，N业务=N条 | 所有业务共享1条，**-50%** |
| 资源消耗 | 每条独立心跳/握手 | 只维护1条，省电省内存 |
| 管理复杂度 | 各模块各自管理 | 统一管理，重连一处搞定 |
| 服务端压力 | 用户数×频道数 | 用户数×1，**服务端连接数减半** |
| 生命周期 | 容易泄漏 | Flow自动绑定释放，零泄漏 |

**一句话总结**：把多条独立WebSocket合并成一条，通过路由分发到各业务模块。就像多车道合并成高速公路，出口再分流。

**追问：为什么叫1对N多路复用？**
→ 1条物理连接，N个业务频道复用。业务层只需订阅对应Flow，不关心底层连接管理

**追问：callbackFlow和StateFlow为什么混用？**
→ StateFlow适合"最新状态"语义（如持仓），新订阅者立即拿最新值；callbackFlow适合"事件流"语义（如逐笔成交），订阅时建连，取消时自动释放

**追问：awaitClose解决什么问题？**
→ 解决订阅泄漏。页面销毁时自动执行退订逻辑，把生命周期管理交给框架，不依赖开发者手动处理

**追问：分线程策略是什么？**
→ 不同频道消息放不同线程，避免高频数据（行情）阻塞低频重要数据（订单状态），保证关键消息不被抢占

#### 三层断连自愈机制详解（业务动机）

**业务场景**：合约交易对实时性极度敏感，断连=用户看不到行情=可能遭受真金白银损失，用户对“断线”容忍度极低

**难点**：断连不是单一原因，6类场景各有特点，不能用同一种策略处理

| 断连场景 | 特点 |
|----------|------|
| 心跳超时 | 服务端长时间没收到响应，主动断开 |
| 链路堵塞 | 连接还在，但消息堆积，数据“卡住” |
| 网络切换 | WiFi↔蜂窝，底层IP变了，旧连接失效 |
| 前后台切换 | 进后台系统可能回收连接 |
| 服务端断开 | 服务端重启、负载均衡切换 |
| 弱网环境 | 信号差，连接时断时续 |

**三层协作设计**：

```
第一层：WebSocket连接自愈（最快响应，毫秒级）
  ├─ 心跳超时 → 指数退避重连(1s/2s/5s)
  ├─ 链路堵塞 → refresh()轻量恢复（不断开，刷新通道）
  └─ 网络切换 → 强制重连

第二层：进程级巡检（兜底保障）
  └─ 定时检查连接状态，覆盖第一层没捕获的边缘情况（如连接“假活”）

第三层：前后台订阅管理（省电+防误触）
  ├─ 进后台 → 退订（省电，避免无效推送）
  └─ 回前台 → 恢复订阅（3s防抖，防短暂切后台误触发）
```

**业务价值**：

| 维度 | 原来 | 现在 |
|------|------|------|
| 连接可用性 | 95%（每天约1小时断连） | **99.5%**（每天约7分钟） |
| 用户断线感知 | 经常感知数据不更新 | **显著下降** |
| 覆盖场景 | 可能只处理部分 | **6类全覆盖** |
| 后台耗电 | 后台还在收无用推送 | 退订省电，回前台快速恢复 |

**追问：为什么指数退避而不是固定间隔？**
→ 固定间隔在网络恢复时会造成“重连风暴”。指数退避(1s→2s→5s)既保证快速恢复，又避免服务端压力

**追问：refresh()和重连有什么区别？**
→ 重连要断开旧连接+重新握手，开销大。refresh()在现有连接上刷新通道，更轻量更快，适用于“连接还在但数据不通”的场景

**追问：3s防抖怎么考虑的？**
→ 用户可能只是短暂切后台（弹权限弹窗、看通知），立即退订再恢复反而增加开销。3s后还在后台才真正退订，平衡省电和恢复速度

**追问：三层之间会不会冲突？**
→ 不会。职责边界清晰：第一层处理明确断连事件（回调触发），第二层处理“静默异常”（定时检查），第三层处理前后台生命周期（系统回调）。各自独立，互不干扰

#### 前后台省电策略详解（业务动机）

**业务场景**：合约行情推送频率极高（日均50万+条），用户切后台时连接还在持续收数据，但用户根本看不到

**矛盾点**：
- 后台不退订 → 费电、手机发烫、容易被系统杀进程
- 后台直接断连 → 回前台要重新建连，恢复慢，体验差

**方案：退订不断连 + 3s防抖**

```
前台 ──[进后台]──→ 退订（停止收数据，TCP不断）
                        │
                   3s 防抖判断
                   ├─ <3s 回前台 → 没真正退订，无感恢复
                   └─ >3s 还在后台 → 确认退订生效，持续省电
                        │
后台 ──[回前台]──→ 恢复订阅（TCP还在，秒恢复）
```

- **退订 ≠ 断连**：退订是应用层协议（告诉服务端不推数据），TCP连接还活着。回前台只需重新订阅，无需重新握手
- **3s防抖**：覆盖绝大多数短暂切后台场景（权限弹窗、看通知），避免频繁退订/恢复的开销

**业务价值**：

| 维度 | 不退订 | 直接断连 | 你的方案 |
|------|--------|---------|----------|
| 后台耗电 | 高 | 低 | **低** |
| 回前台恢复 | 无需恢复 | 慢（重新建连） | **快（秒恢复）** |
| 被杀进程风险 | 高 | 低 | **低** |
| 短暂切后台体验 | 无影响 | 有感知 | **无感** |
| 服务端资源 | 浪费 | 节省 | **节省** |

**追问：为什么3s不是1s或5s？**
→ 1s太短，很多系统弹窗超过1s，会频繁触发退订。5s太长，省电效果来得太慢。3s是实测覆盖绝大多数短暂切后台场景的平衡点

**追问：退订和断连的区别？**
→ 退订=应用层告诉服务端不推数据，TCP还在。断连=传输层TCP断开，要重新握手+TLS。退订开销远小于断连

**追问：后台待很久，回前台数据会不会过时？**
→ 会。回前台恢复订阅后触发一次全量数据刷新，补齐后台期间错过的数据，确保用户看到最新状态

#### 项目工程化建设详解（业务动机）

**背景**：合约业务是从零搭建的新业务线，没有现成基础设施，业务迭代快，多人并行开发，没有工程化支撑代码会迅速腐化

**核心矛盾**：业务要求快速上线 vs 工程质量不能妥协

**四项建设**：

| 建设项 | 解决的核心问题 | 一句话价值 |
|--------|---------------|----------|
| CI多泳道 | 环境切换靠手动，易出错 | 多环境并行，零配置切换 |
| 多语言动态更新 | 改文案要发版 | 文案热更新，零发版 |
| 万能路由 | 跳转逻辑分散，耦合严重 | 一处注册，处处跳转 |
| 基础组件封装 | 重复造轮子，风格不统一 | 开箱即用，统一体验 |

**详细说明**：

- **CI多泳道**：通过Header透传X-Lane信息，自动路由到对应环境。开发/测试切换环境零手动配置，多环境并行测试缩短联调周期
- **多语言动态更新**：文案从服务端动态下发，App启动时拉取并缓存。改文案无需发版，支持按地区/语言动态切换，满足区域合规
- **万能路由**：所有跳转通过路由URL分发，支持原生/H5/Push/DeepLink。新增页面只需注册路由，Push跳转服务端配置即可，客户端零改动
- **基础组件封装**：统一封装网络请求基类、通用UI组件、列表封装、埋点基类。新业务开箱即用，风格统一，新人上手快

**本质**：把重复的事情标准化，把容易出错的事情自动化，把分散的事情统一化。不直接产出功能，但是业务能**快速、稳定、规模化迭代**的基础

**面试话术（30秒）**：
> 合约业务从零搭建，工程化基础设施需要自己建设。CI多泳道让多环境并行成为可能；多语言动态更新让运营不改版就调整文案；万能路由统一所有跳转逻辑；基础组件封装让新业务开箱即用。这些是团队能**快速迭代、稳定交付**的基础

#### AI Coding 工程化详解（业务动机）

**业务价值**：

| 维度 | 传统开发 | AI工程化 |
|------|---------|----------|

**追问：40%怎么算的？**

→ 三层保障：Rules约束规范 + Spec提供上下文减少幻觉 + Code Review最终把关

**追问：Rules和Skills有什么区别？**
→ Rules是“约束”（什么能做什么不能做），Skills是“模板”（某类任务的标准流程）

**面试话术（30秒）**：

#### EU 站 DLT 业务开发详解（业务动机）

**背景**：OSL是全球化数字资产交易平台，EU站面向欧盟用户，DLT=Distributed Ledger Technology（分布式账本/区块链业务）

**核心挑战**：欧盟对金融业务有严格合规要求（MiFID II、GDPR等），EU站数据必须走独立服务器和域名，不能和全球站混用

| 挑战 | 说明 |
|------|------|
| 双端一致 | 原生+Flutter都要替换域名，行为必须一致 |
| 动态切换 | 不能写死，需根据用户区域/环境动态决定 |
| 多环境部署 | dev/staging/prod每环境域名不同 |
| 合规隔离 | EU数据必须走EU域名，否则**违规** |

**方案**：在HTTP拦截层做域名动态路由，业务代码完全不感知域名差异
- 域名配置化：各区域域名从配置中心获取，不硬编码
- 双端统一：原生和Flutter共用同一套域名路由策略
- 请求拦截替换：根据区域标识自动替换请求域名
- 异常兑底：配置异常时默认走最严格的EU域名，宁可多隔离也不泄露

**业务价值**：

| 维度 | 不做动态替换 | 动态替换 |
|------|------------|----------|
| 合规性 | 域名写死，有违规风险 | 自动路由，**满足合规** |
| 部署灵活性 | 新增区域要改代码+发版 | 配置域名即可，**零代码** |
| 双端一致性 | 各自实现，容易不一致 | **统一策略** |

**追问：为什么原生和Flutter都要做？**
→ 混合架构下部分页面在原生，部分在Flutter。只改一端另一端走旧域名，数据不通。必须双端统一

**追问：难在哪？**
→ 技术不复杂，难在双端一致性和合规可靠性。合规场景下，“偶尔出错”和“完全不出错”的区别就是“罚款”和“不罚款”的区别

**面试话术（20秒）**：
> EU站有独立合规要求，数据必须走欧盟区域服务器。我在原生和Flutter双端实现了域名动态替换，网络层根据区域自动路由，业务代码零感知。满足合规的同时支持多环境灵活部署

### 2. KuCoin — 支付重构

| 项 | 内容 |
|----|------|
| 痛点 | 支付代码耦合，新渠道接入要2周 |
| 方案 | 4层组件化分层 + 策略模式 |
| 数据 | 接入周期2周→3-5天 |
| 原则 | 架构服务业务节奏：探索期不过度设计，稳定期提前储备 |

#### P2P Express 详解（业务动机）

**背景**：KuCoin用户想用法币购买加密货币，原来要4步操作、涉及3个账户的资金划转

**原流程**：
```
法币充值→Funding账户 → 划转→Exchange账户 → 下单购买 → 提币（4步，3个账户）
```

**问题**：流程太长，用户容易中途放弃，转化率低

**方案：P2P Express**
```
选择币种+金额 → 确认支付（2步，中间划转全部自动化）
```
- 用户只需选币+付款，中间Funding→Exchange→交易的资金调拨系统自动完成
- 本质：**在复杂账户体系之上做了一层简化体验的封装**

**保价/不保价双模式**：

| 模式 | 说明 | 适合谁 |
|------|------|--------|
| 保价 | 锁定当前价格，成交按锁定价执行 | 对价格敏感、不想承担波动的用户 |
| 不保价 | 按实际成交时的市场价执行 | 愿意承担波动、可能拿到更好价格的用户 |

→ 让用户**自己选择风险偏好**，保价收稍高手续费覆盖对冲成本，不保价手续费更低

**业务价值**：

| 维度 | 原来 | P2P Express |
|------|------|-------------|
| 操作步骤 | 4步 | **2步** |
| 账户感知 | 3个账户手动划转 | 系统自动，**用户无感** |
| 转化率 | 基准 | **+15%** |
| 风险策略 | 单一 | 双模式可选 |

**追问：15%转化率怎么算的？**
→ 对比上线前后，相同流量入口下“进入买币页面→完成交易”的转化率，由产品侧埋点统计

**追问：为什么原来要3个账户？**
→ 历史原因。Funding管充值提现，Exchange管交易，专业交易场景下有优势（资金隔离、风控），但对普通买币用户是多余的复杂度

**面试话术（20秒）**：
> 原来用户买币要4步操作、3个账户划转，流程复杂转化率低。我设计了P2P Express，压缩到2步，中间划转全自动。同时设计保价/不保价双模式让用户自选风险策略。转化率提升约15%

#### MVVM → MVI 架构重构详解（业务动机）

**背景**：KuCoin支付业务（P2P、充提、划转）状态复杂，涉及余额/汇率/手续费/订单状态等多个并发状态

**原方案（GetX + MVVM）的问题**：

| 问题 | 说明 |
|------|------|
| 状态分散 | 多个StateFlow各自变化，可能出现矛盾状态（余额新但手续费旧） |
| 操作和状态混合 | 用户操作和网络回调都可能改状态，混在一起难追溯 |
| GetX隐式注入 | Get.find()运行时才发现错误，多页面共享Controller时状态串扰 |

**方案：Riverpod + MVI**

核心改变：**从“多个独立数据流”变成“单一状态源 + 单向数据流”**

```
用户操作(Intent) → Reducer(纯函数) → 新State(不可变) → View渲染
      ↑                                                  │
      └──────────── 单向数据流 ────────────────────────┘
```

- **单一State**：一个页面只有一个State对象，包含所有状态，不可能矛盾
- **单向数据流**：Intent→Reducer→State，每个状态变化都可追溯
- **Riverpod**：编译时安全，自动生命周期管理，显式依赖注入

**重构前后对比**：

| 维度 | GetX+MVVM | Riverpod+MVI |
|------|-----------|---------------|
| 状态管理 | 多个独立流，可能矛盾 | **单一State，不可能矛盾** |
| 数据流向 | 双向，操作和回调混合 | **单向，Intent→State→View** |
| 问题追溯 | 追踪多个流时序 | **一个Intent对应一个State变化** |
| 依赖注入 | 隐式，运行时发现 | **显式，编译时检查** |
| 可测试性 | 需Mock多个流 | **给Intent断言State，纯函数测试** |

**业务价值**：
1. 减少线上bug：单一状态源消除状态不一致
2. 排查问题更快：单向数据流让每个变化可追溯
3. 迭代更安全：改一个功能不影响其他状态
4. 新人上手快：MVI模式固定，按模板写就行

**追问：重构过程中业务不能停怎么办？**
→ 新页面直接用MVI，老页面按模块逐步迁移。优先迁移状态最复杂的页面（收益最大），简单展示页保持MVVM不动

**追问：为什么选Riverpod不是Bloc？**
→ Bloc更重（Event+State+Bloc三个文件），Riverpod更轻量，编译时安全，依赖注入内置。项目规模刚好匹配

**追问：GetX有什么不好？**
→ GetX不是不好，是不适合复杂业务。隐式注入在简单场景下方便，但在支付这种多模块场景下容易运行时出错。Riverpod显式声明虽然写多一点，但编译时就能发现问题

**面试话术（20秒）**：
> 支付业务状态复杂，MVVM下多个StateFlow各自变化容易状态不一致，出问题难追溯。重构为Riverpod+MVI，单一状态源+单向数据流，每个状态变化都可追溯。重构后状态不一致的bug显著减少，排查效率大幅提升

## 架构演进：MVC → MVP → MVVM → MVI

**核心观点**：不是追新技术，而是每个阶段都有真实的业务痛点驱动

### 演进路线

| 架构 | 解决的问题 | 核心改变 | 适用场景 |
|------|----------|---------|----------|
| MVC | 项目早期，功能少 | View+Controller混在一起 | 简单页面 |
| MVP | Controller太胖，View和逻辑强耦合 | View变被动，Presenter通过接口通信 | 中等复杂度 |
| MVVM | Presenter手动更新UI太繁琐 | 响应式数据绑定，数据变UI自动刷新 | 中高复杂度 |
| MVI | MVVM多状态分散，容易不一致 | **单一状态源+单向数据流** | 高复杂度/多状态 |

### 每个架构的核心区别

- **MVC**：View和Controller双向通信，Controller越来越胖
- **MVP**：View纯展示，Presenter通过接口推UI，可单测
- **MVVM**：View观察ViewModel数据，数据变UI自动刷新（LiveData/StateFlow）
- **MVI**：Intent→Model计算→State→View渲染，单向循环，状态不可变

### 我的实践路径

| 公司 | 架构 | 具体工作 |
|------|------|----------|
| 上海钢联 | MVC→MVP | 重构后核心模块代码行数-20% |
| 饿了么 | 组件化分层 | 4层架构+ARouter组件间通信 |
| 滴滴 | MVVM+Clean | Flutter侧基于Bloc的洋葱模型 |
| 小红书 | MVVM | 基于GetX搭建，解决多文档嵌套状态串扰 |
| KuCoin | MVVM→MVI | 从GetX的MVVM重构为Riverpod的MVI |

### 面试话术（30秒）

> 架构演进不是追新技术，是每个阶段都有业务痛点驱动。MVC代码太胖拆到MVP，MVP手动更新UI太繁琐升级到MVVM，MVVM多状态不一致再演进到MVI的单一状态源+单向数据流。我在不同公司经历了不同阶段，核心原则始终是：**架构服务于业务复杂度，不过度设计，也不欠设计**

### 追问准备

**追问：为什么不一开始就用MVI？**
→ MVI适合高复杂度场景。简单业务用重架构是浪费，架构选型要看业务复杂度

**追问：MVVM到MVI最大的改变？**
→ 从“多个独立数据流”变成“单一状态源+单向数据流”。5个LiveData各自变化可能矛盾，一个State对象包含所有状态，每次整体更新，不会不一致

**追问：为什么选Riverpod而不是Bloc？**
→ Riverpod更轻量，编译时安全，依赖注入内置。对于项目规模刚好匹配

**追问：重构最大挑战？**
→ 不是技术，是**业务不能停**。策略：新页面直接用MVI，老页面按模块逐步迁移，优先迁移状态最复杂的页面（收益最大）

| 问题 | 说明 |
|------|------|

**方案**：

1. **WebView通用容器**：开箱即用，包含初始化/生命周期/Loading/错误页/白屏检测
2. **JSBridge通信协议**：统一调用格式（方法名+参数+回调），统一错误码，支持异步回调+事件推送

**业务价值**：

| 维度 | 原来 | 现在 |
|------|------|------|
| 接入周期 | 1周 | **2天** |
| 重复开发 | 每个业务自己搭 | 开箱即用 |
| 交互规范 | 五花八门 | **统一协议** |
| 业务覆盖 | - | **10+业务场景** |

**追问：为什么选H5不全部原生？**
→ H5迭代快不需发版，适合运营活动/帮助文档等变化频繁的页面。核心功能用原生保证性能。混合方案是效率和体验的平衡

**追问：白屏问题怎么解决？**

**面试话术（20秒）**：
> 小红书大量H5页面需要嵌入Native，每个业务各自接入，交互不统一，接入周期长。我封装了WebView通用容器，制定JSBridge通信协议，统一交互规范。新业务接入从1周缩短到2天，覆盖10+业务场景

## 小红书 — Flutter多引擎架构

**背景**：小红书文档空间需要支持多文档同屏协作（20+文档），单引擎下所有文档共享一个Isolate，一个文档卡住影响全部

**单引擎的问题**：

| 问题 | 说明 |
|------|------|
| 页面耦合 | 共享Isolate，一个文档卡住影响所有文档 |
| 崩溃影响 | 一个崩全部崩 |
| 内存集中 | 20+文档数据+渲染在一个引擎，内存压力大 |
| 无法独立管理 | 不能单独销毁某个文档的引擎 |

**方案：每个文档一个独立Engine，基础服务下沉Native**

```
Native层：基础服务（网络/登录态/文件存储/推送）— 共享一份
    ↑ Platform Channel ↑ Platform Channel ↑
 Engine1(文档A)    Engine2(文档B)    EngineN(文档N)
  独立UI+独立Isolate    独立UI+独立Isolate    独立UI+独立Isolate
```

- **每个文档一个Engine**：独立Isolate，互不影响
- **基础服务下沉Native**：网络/登录态/文件只维护一份，所有引擎通过Platform Channel调用
- **数据共享通过Native中转**：引擎间不直接通信，需要共享时通过Native层中转
- **引擎生命周期独立管理**：可单独创建/销毁某个文档的引擎

**业务价值**：

| 维度 | 单引擎 | 多引擎 |
|------|--------|--------|
| 文档独立性 | 共享Isolate，互相影响 | **独立Isolate** |
| 崩溃影响 | 一个崩全部崩 | **只影响一个文档** |
| 同屏文档数 | 受限 | **20+文档** |
| 引擎启动 | - | **控制在300ms以内** |
| 基础服务 | 每个引擎各自维护 | **下沉Native，共享一份** |

**追问：300ms包含哪些？**
→ FlutterEngine初始化 + Dart VM创建 + 首帧渲染。优化手段：引擎预热（预创建引擎池）、懒加载非关键资源、首屏数据延迟加载

**追问：多引擎内存怎么控制？**
→ 三个策略：引擎池复用（销毁的引擎等新文档复用）、后台文档降低帧率/暂停渲染、超过阈值回收最早不活跃的文档引擎

**追问：Platform Channel频繁通信不会有性能问题吗？**
→ Channel通信开销很小（微秒级）。大数据量采用二进制格式传输，避免JSON序列化开销。实际使用中不是性能瓶颈

**面试话术（20秒）**：
> 文档协作需要20+文档同屏，单引擎下所有文档共享Isolate，一个卡住影响全部。我搭建了多引擎架构，每个文档独立引擎独立Isolate，基础服务下沉Native共享，引擎间数据通过Native中转。启动耗时300ms以内，支撑20+文档同屏

## 组件化分层架构（饿了么 & KuCoin）

**背景**：项目做大后所有代码混在一个module里，编译慢、耦合严重、多人协作冲突不断

**原问题**：

| 问题 | 说明 |
|------|------|
| 编译慢 | 改一行全量编译5-10分钟 |
| 耦合严重 | A模块直接调用B模块内部类，牵一发动全身 |
| 无法独立开发 | 多人协作同module，冲突不断 |
| 无法独立测试 | 测试一个模块要拉起整个App |
| 代码腐化 | 无层级约束，任何类可调用任何其他类 |

**方案：纵向分层 + 横向组件化**

纵向分层：
```
应用层（App Shell）         ← 组装各模块，不含业务逻辑
业务层（Payment/Order/IM）  ← 具体业务模块
基础业务层（用户/账户）     ← 跨业务通用能力
基础设施层（网络/DB/日志） ← 最底层能力
```
规则：上层依赖下层，下层不依赖上层，同层不直接依赖

横向组件化：每个业务域拆成独立Gradle Module，可独立编译/测试/发版

组件间通信（ARouter）：通过路由URL跳转，组件间完全不需要互相依赖

**业务价值**：

| 维度 | 组件化前 | 组件化后 |
|------|---------|----------|
| 编译速度 | 5-10分钟 | **秒级增量编译** |
| 代码耦合 | 互相调用 | **路由/接口通信** |
| 多人协作 | 冲突不断 | **各改各的组件** |
| 新渠道接入(KuCoin) | 2周 | **3-5天** |

**追问：分层和组件化有什么区别？**
→ 分层是纵向职责划分（解决“谁依赖谁”），组件化是横向模块拆分（解决“代码耦合”）。两者结合才是完整的组件化分层架构

**追问：组件间通信为什么用ARouter？**
→ ARouter用于页面跳转，接口用于服务调用。好处是解耦彻底，两个模块完全不需要互相依赖

**追问：编译速度提升怎么量化？**
→ 组件化前全量编译5-10分钟，组件化后只编译改动模块，秒级。开发者一天编译几十次，每次省5分钟就是省几小时

**面试话术（20秒）**：
> 项目做大后所有代码混在一个module，编译慢、耦合严重。我做了分层+组件化：纵向分4层，上层依赖下层；横向拆成独立module，组件间通过路由通信。编译从10分钟降到秒级，新支付渠道接入从2周缩短到3-5天

## 饿了么 — LeakCanary & BlockCanary 稳定性保障

**背景**：OnPOS收银系统长时间运行（12-16小时），内存泄漏和UI卡顿是高频问题，但开发阶段难发现，往往到线上才暴露

**原问题**：

| 问题 | 内存泄漏 | UI卡顿 |
|------|---------|--------|
| 发现时机 | 运行几小时后OOM崩溃 | 用户投诉才知道 |
| 定位难度 | OOM堆栈是结果不是原因 | 不知道哪段代码阻塞主线程 |
| 复现难度 | 需长时间运行 | 特定操作/数据量才卡 |
| 业务影响 | OOM=崩溃=无法收银 | 卡顿=效率下降=商户投诉 |

**方案：把问题前置到开发阶段**

**LeakCanary（内存泄漏检测）**：
- 原理：页面销毁时用WeakReference监控 → 触发GC → 检查是否回收 → 未回收则分析引用链
- 效果：开发者退出页面时自动检测，直接展示泄漏对象的引用链

**BlockCanary（UI卡顿检测）**：
- 原理：主线程Looper设置Printer监听 → 记录Message执行时间 → 超过阈值截取堆栈
- 效果：卡顿超过阈值自动捕获，直接展示阻塞主线程的代码堆栈

**业务价值**：

| 维度 | 没有框架 | 引入后 |
|------|---------|--------|
| 泄漏发现 | 线上OOM | **开发阶段即时发现** |
| 泄漏定位 | 看堆栈猜 | **直接展示引用链** |
| 卡顿发现 | 用户投诉 | **开发/测试自动捕获** |
| 卡顿定位 | 逐行排查 | **直接展示阻塞堆栈** |
| 排查效率 | 几小时到几天 | **分钟级定位** |

**追问：LeakCanary影响性能吗？**
→ 只在Debug包集成，Release包不集成。检测在后台线程执行，对开发体验几乎无影响

**追问：BlockCanary阈值怎么定？**
→ 默认500ms。收银系统对流畅度要求高，可降到300ms

**追问：发现泄漏后怎么修？**
→ 根据引用链定位：匿名内部类持有Activity→改静态内部类+弱引用；单例持有Activity→置空或用ApplicationContext；未取消回调→onDestroy中取消

**面试话术（20秒）**：
> 收银系统长时间运行，内存泄漏和卡顿开发阶段难发现。我引入LeakCanary和BlockCanary，把问题前置到开发阶段——泄漏在页面退出时自动检测展示引用链，卡顿超阈值自动捕获展示阻塞堆栈。OOM崩溃率和卡顿投诉显著下降

## 上海钢联 — OkHttp网络框架二次封装

**背景**：资讯+价格行情App，网络请求量大，但每个开发者自己写请求，风格不统一，没有日志，线上问题排查困难

**原问题**：

| 问题 | 说明 |
|------|------|
| 重复代码 | 每个请求手动配置请求头/Token，重复代码多 |
| 风格不统一 | 有人用Callback，有人用RxJava，有人同步请求 |
| 日志缺失 | 没有统一日志，出了问题不知道请求发了什么、服务端返回了什么 |
| 错误处理不统一 | 有的Toast，有的Dialog，有的静默失败 |
| 排查困难 | 线上问题开发说“我本地是好的”，没日志无法追溯 |

**方案：统一网络层，业务只关心“请求什么”和“拿到什么”**

1. **统一请求头&公共参数**（拦截器自动注入Token、设备信息、App版本）
2. **统一日志拦截器**（记录请求URL/Headers/Body + 响应码/Body/耗时）
3. **统一错误处理**（Token过期自动刷新重试、网络异常统一提示、业务错误统一回调）

**业务价值**：

| 维度 | 没有封装 | 二次封装后 |
|------|---------|----------|
| 重复代码 | 每个请求手动配置 | **自动注入，零重复** |
| 日志排查 | 没有日志靠猜 | **完整请求/响应日志，-40%** |
| 错误处理 | 各页面自己处理 | **统一处理，Token自动刷新** |
| 新人上手 | 不知道怎么写 | **参考基类复制粘贴** |

**追问：为什么二次封装不是自己写网络框架？**
→ OkHttp已处理连接池/缓存/HTTPS等底层细节。二次封装是在其上加业务适配层，解决统一请求头、日志、错误处理等业务层问题

**追问：Token自动刷新怎么实现？**
→ 收到401时拦截器自动调刷新接口，拿新Token后重新发起原始请求。关键：加锁，多个并发请求同时401只触发一次刷新

**追问：日志在Release包怎么处理？**
→ 可配置日志级别：完全关闭/只记录异常/记录所有但不记Body。根据实际需要选择

**面试话术（20秒）**：
> 网络请求量大但各自为战，风格不统一，没日志，线上问题排查困难。我对OkHttp二次封装：拦截器统一注入请求头和公共参数，自动记录完整请求/响应日志，统一错误处理含Token自动刷新。日志排查问题时间缩短40%

## 上海钢联 — 应用性能优化

**背景**：资讯+价格行情App，图片多列表长，用户碎片化快速浏览，对启动速度和流畅度敏感，不少用户用中低端机型

**原问题**：启动3.2s、内存峰值280MB、低端机卡顿严重

| 问题 | 说明 |
|------|------|
| 启动慢 | 3.2s冷启动，第一印象差 |
| 内存高 | 280MB峰值，低端机容易被系统杀进程 |
| 卡顿严重 | 低端机滑动列表帧率低 |
| 图片加载慢 | 大量图片，白屏时间长 |

**方案：启动优化 + 内存优化 + 渲染优化**

**启动优化（3.2s→2.1s，-35%）**：
- 延迟初始化：非首屏SDK推迟到首页渲染后初始化
- 异步初始化：可并行的SDK放子线程，不阻塞主线程
- 首页数据预加载：Application阶段异步请求，首页展示时数据已就绪
- 布局优化：减少首页布局层级，ConstraintLayout替代多层嵌套

**内存优化（280MB→200MB，-28%）**：
- 图片三级缓存：内存LruCache→磁盘→网络，复用已加载图片
- 图片降采样：根据ImageView实际大小加载合适分辨率，不加载原图
- 及时释放：页面不可见时释放图片资源
- 内存泄漏修复：配合LeakCanary修复已发现的泄漏

**渲染优化（低端机卡顿率-45%）**：
- 布局层级优化：减少嵌套，ConstraintLayout扁平化
- 避免过度绘制：去除不必要背景色
- 列表优化：ViewHolder复用+图片异步加载+滑动时暂停加载
- ViewStub懒加载：不常用View延迟加载

**业务价值**：

| 维度 | 优化前 | 优化后 |
|------|--------|--------|
| 启动速度 | 3.2s | **2.1s（-35%）** |
| 内存峰值 | 280MB | **200MB（-28%）** |
| 低端机卡顿率 | 基准 | **降低45%** |

**追问：启动速度怎么量化？**
→ Application.onCreate()开始和首页onWindowFocusChanged()各打时间戳，差值就是冷启动耗时。同时用Systrace分析各阶段耗时找瓶颈

**追问：图片降采样具体怎么做？**
→ BitmapFactory.Options的inSampleSize。先读原图尺寸，根据ImageView实际宽高计算inSampleSize。如ImageView 200x200，原图2000x2000，inSampleSize=4，只加载500x500，内存减少94%

**追问：怎么确认优化有效？**
→ 建立性能基准，每次优化后相同设备相同场景对比。接入性能监控线上持续跟踪，确保不回退

**面试话术（20秒）**：
> App启动3.2s、内存280MB，低端机卡顿严重。我从三个维度优化：启动优化（延迟/异步初始化非首屏SDK），内存优化（图片三级缓存+降采样），渲染优化（布局扁平化+列表懒加载）。启动降至2.1s，内存降至200MB，低端机卡顿率降低45%

## 上海钢联 — 线程池 + Handler + RxJava 异步任务处理

**背景**：资讯App有大量异步操作（网络请求、数据库读写、图片解码、文件IO），全部放主线程会卡顿，随意开线程会导致线程爆炸和资源竞争

**原问题**：

| 问题 | 说明 |
|------|------|
| 线程滥用 | 到处new Thread()，线程数不可控，资源竞争严重 |
| 回调地狱 | 多层异步嵌套，代码难以维护 |
| 线程安全 | 多线程同时操作数据，偶现数据不一致 |
| 生命周期脱节 | Activity销毁了异步任务还在跑，导致崩溃或内存泄漏 |

**方案：线程池统一管理 + RxJava链式调度 + Handler切回主线程**

```
异步任务流程：

业务层 → RxJava Observable/Flowable（定义任务链）
           ↓
       线程池（Schedulers.io / custom）（执行耗时操作）
           ↓
       主线程（AndroidSchedulers.mainThread()）（更新UI）
           ↓
       Disposable（绑定生命周期，页面销毁自动取消）
```

1. **线程池统一管理**：
   - 核心线程池（CPU密集型）：线程数 = CPU核心数，用于数据计算、JSON解析
   - IO线程池（IO密集型）：线程数 = CPU核心数×2+1，用于网络/文件/数据库
   - 单线程池：串行执行需要保证顺序的任务

2. **RxJava链式调度**：
   - subscribeOn指定执行线程，observeOn指定回调线程
   - flatMap/map操作符串联多步异步操作，避免回调嵌套
   - debounce/switchMap处理高频事件（如搜索框实时查询）

3. **Handler主线程回调**：
   - RxJava最终通过AndroidSchedulers.mainThread()切回主线程更新UI
   - 底层仍是Handler消息机制，RxJava只是封装了线程切换

4. **生命周期绑定**：
   - 使用CompositeDisposable收集所有任务
   - Activity.onDestroy时统一dispose，防止泄漏

**业务价值**：

| 维度 | 原来（随意开线程） | 现在（线程池+RxJava） |
|------|-------------------|----------------------|
| 线程数 | 不可控，可能几十上百个 | **固定池化，可控** |
| 代码可读性 | 回调嵌套3-4层 | **链式调用，一行一行读** |
| 线程安全 | 偶现数据不一致 | **单线程池串行保证** |
| 内存泄漏 | Activity销毁任务还在跑 | **Disposable自动取消** |
| 性能 | 频繁创建销毁线程 | **线程复用，开销低** |

**追问：为什么用线程池而不是直接new Thread？**
→ new Thread每次创建/销毁有开销，且线程数不可控。线程池复用线程、管理队列、限制并发数，是生产级做法

**追问：CPU密集型和IO密集型为什么线程数不同？**
→ CPU密集型：线程数=CPU核心数，多了反而增加上下文切换开销。IO密集型：线程大部分时间在等待IO，多开线程可以提高CPU利用率

**追问：RxJava和协程有什么区别？为什么当时选RxJava？**
→ RxJava功能更丰富（操作符多），适合复杂异步流。协程更轻量、代码更简洁。当时项目基于Java，RxJava是成熟方案。后来新项目中已逐步迁移到协程

**追问：CompositeDisposable怎么防止泄漏？**
→ 每个异步任务subscribe后返回Disposable，加入CompositeDisposable。Activity.onDestroy时调用composite.clear()，所有未完成的任务自动取消回调，不再持有Activity引用

**面试话术（20秒）**：
> 异步操作到处new Thread，线程数不可控，回调嵌套难维护，Activity销毁了任务还在跑。我用线程池统一管理线程资源，RxJava链式调度替代回调嵌套，Disposable绑定生命周期自动取消。代码可读性大幅提升，内存泄漏问题基本解决

## 管理三板块

### 任务分工

- **能力梯度**：核心给老手，新模块给成长中的人
- **业务域Owner**：每人端到端负责一个域
- **留Buffer**：每迭代留15-20%给紧急事项

### 向上汇报

- **周报三段式**：完成 / 计划 / 风险
- **里程碑主动报**：关键节点不等领导问
- **风险前置带方案**：延期第一时间说+附方案

### 向下管理

- **明确预期**：交付标准+时间说清楚
- **关键节点Check**：中途Code Review，不微观管理
- **及时反馈**：好的公开夸，差的私下聊
- **表现不佳**：先判原因（能力→带教 / 态度→沟通 / 信息不对称→反思自己）
