## 一、RecyclerView

> **一句话总结**：核心是四级缓存（Scrap → CachedViews → Extension → Pool）就近复用 ViewHolder，滑出屏幕的不立即销毁而是按策略降级存储，滑入时优先从缓存取，配合 GapWorker 预取和 DiffUtil 局部刷新，实现高效列表渲染。

### 1. 核心架构

RecyclerView 采用 **MVP + 策略模式** 的设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **RecyclerView** | 视图容器，负责初始化、事件分发、绘制 |
| **Adapter** | 数据与 ViewHolder 的桥梁，创建和绑定 ViewHolder |
| **LayoutManager** | 决定 Item 如何布局（线性、网格、瀑布流） |
| **ViewHolder** | 持有 Item View 的引用，避免重复 `findViewById` |
| **Recycler** | 内部缓存管理器，负责 ViewHolder 的回收与复用 |
| **ItemAnimator** | 控制 Item 增删改的动画效果 |
| **ItemDecoration** | 绘制 Item 之间的装饰（如分割线） |

### 2. 四级缓存机制（核心重点）

RecyclerView 的缓存由内部类 `Recycler` 管理，共四级：

#### 第一级：mAttachedScrap / mChangedScrap（屏幕内缓存）
- **mAttachedScrap**：屏幕内可见的 ViewHolder，布局期间临时分离再重新附加
- **mChangedScrap**：数据发生变化但仍可见的 ViewHolder
- 布局时先 detach 所有可见 ViewHolder，布局完成后再重新 attach 或 scrap
- **不需要重新 bind**，直接使用

#### 第二级：mCachedViews（离屏缓存）
- 默认容量 **2**（可通过 `setItemViewCacheSize()` 修改）
- 滑出屏幕的 ViewHolder 先进入这里
- **不需要重新 bind**，直接复用（保留数据）
- 按 position 查找，优先匹配相同 position
- 满了之后，最早的 ViewHolder 被**降级**到第三级

#### 第三级：ViewCacheExtension（自定义扩展缓存）
- 开发者可自行实现 `ViewCacheExtension` 提供额外缓存
- 官方默认不使用，属于预留扩展点

#### 第四级：RecycledViewPool（回收池，真正的缓存）
- 按 **viewType** 分类存储
- 进入此级的 ViewHolder 会被 **reset**（清除数据，标记为 invalid）
- 复用时**必须重新 bind**（调用 `onBindViewHolder`）
- 默认无上限，可通过 `setMaxRecycledViews(viewType, max)` 设置

#### 缓存查找流程

```
滑动需要 ViewHolder 时的查找顺序：

1. mChangedScrap / mAttachedScrap → 有就直接用（不 bind）
2. mCachedViews → 按 position 匹配，有就直接用（不 bind）
3. ViewCacheExtension → 有就直接用（不 bind）
4. RecycledViewPool → 按 viewType 匹配，需要重新 bind
5. 都没有 → 调用 Adapter.createViewHolder() 创建新的
```

#### 缓存流转图

```
屏幕内 ViewHolder 滑出屏幕
        ↓
  mCachedViews（容量 2，不 bind）
        ↓ 满了
  RecycledViewPool（按 viewType，需 bind）
        ↓ 复用
  重新进入屏幕（从 Pool 取出 → bind → 显示）
```

### 3. 布局流程（onLayout）

`onLayout()` → `dispatchLayout()` → `dispatchLayoutStep1/2/3`

#### Step1：预布局（dispatchLayoutStep1）
- 处理预动画（predictive animations）
- 确定哪些 Item 需要动画
- 更新 mOldPosition、mPosition 等状态

#### Step2：实际布局（dispatchLayoutStep2）
- 核心步骤，调用 `LayoutManager.onLayoutChildren()`
- 内部流程：
  1. 先 scrap 所有可见 ViewHolder（detach 到 mAttachedScrap）
  2. 从第一个可见位置开始，依次调用 `fill()` 填充
  3. `fill()` → `layoutChunk()` → 逐个放置 Item
  4. 每个 Item 先查找缓存（四级缓存），找到就 bind，找不到就 create
  5. 直到填满可见区域

#### Step3：布局后处理（dispatchLayoutStep3）
- 处理动画
- 通知 Adapter 数据变化
- 清理 Scrap 缓存

### 4. 滑动回收流程

#### 滑动时的核心调用链

```
scrollByInternal()
    ↓
  dispatchNestedPreScroll()（嵌套滑动预处理）
    ↓
  dispatchNestedScroll()
    ↓
  LayoutManager.scrollVerticallyBy() / scrollHorizontallyBy()
    ↓
  offsetChildrenVertical() / offsetChildrenHorizontal()（偏移子 View）
    ↓
  fill()（填充新出现的空白区域）
    ↓
  recycleViewsOutOfBounds()（回收超出屏幕的 ViewHolder）
```

#### 回收逻辑
1. 计算屏幕可见区域
2. 遍历所有子 View，判断是否在可见区域内
3. 不在可见区域 → detach → 判断是否放入 mCachedViews
4. mCachedViews 满了 → 移入 RecycledViewPool

### 5. notifyDataSetChanged vs notifyItemXxx

| 方式 | 行为 | 动画 | 性能 |
|------|------|------|------|
| `notifyDataSetChanged()` | 全量刷新，所有 ViewHolder 进入 mAttachedScrap | 无动画 | 差 |
| `notifyItemInserted()` | 局部刷新，仅影响插入位置及之后 | 有动画 | 好 |
| `notifyItemRemoved()` | 局部刷新，被删除的进入 mChangedScrap | 有动画 | 好 |
| `notifyItemChanged()` | 局部刷新，仅重新 bind 目标 Item | 有动画 | 好 |
| `DiffUtil` | 自动计算差异，批量 dispatch | 有动画 | 最优 |

### 6. DiffUtil 原理

基于 **Eugene W. Myers 差分算法**：

1. 将旧列表和新列表视为两个序列
2. 通过 Myers 算法计算从旧列表变为新列表的最少操作（insert / remove / change）
3. 生成 `DiffResult`，包含所有 dispatch 操作
4. 调用 `dispatchUpdatesTo(adapter)` 逐个通知 Adapter

```kotlin
// 使用示例
val diffResult = DiffUtil.calculateDiff(object : DiffUtil.Callback() {
    override fun getOldListSize() = oldList.size
    override fun getNewListSize() = newList.size
    override fun areItemsTheSame(oldPos: Int, newPos: Int): Boolean {
        return oldList[oldPos].id == newList[newPos].id
    }
    override fun areContentsTheSame(oldPos: Int, newPos: Int): Boolean {
        return oldList[oldPos] == newList[newPos]
    }
})
diffResult.dispatchUpdatesTo(adapter)
```

### 7. 预取机制（GapWorker / prefetch）

RecyclerView 内部有 `GapWorker`，利用 `Choreographer` 的帧回调，在每一帧绘制前**提前预取**即将滑入屏幕的 Item：

1. 监听 `ViewTreeObserver.OnPreDrawListener`
2. 在下一帧绘制前，计算即将进入屏幕的 position
3. 提前从缓存中取出或创建 ViewHolder 并 bind
4. 这样滑动时 ViewHolder 已经准备好，避免卡顿

### 8. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 避免重复创建 ViewHolder | 充分利用缓存，`onCreateViewHolder` 尽量少调用 |
| 减少 bind 耗时 | `onBindViewHolder` 中避免耗时操作，图片异步加载 |
| 使用 DiffUtil | 替代 `notifyDataSetChanged()`，精确刷新 |
| 设置固定大小 | `setHasFixedSize(true)` 避免每次数据变化都重新测量 |
| 共享 RecycledViewPool | 多个 RecyclerView 共享同一个 Pool：`setRecycledViewPool()` |
| 预加载 | `setItemViewCacheSize()` 增大离屏缓存 |
| 避免嵌套滑动冲突 | 合理使用 `setNestedScrollingEnabled(false)` |
| 复用优化 | `setIsRecyclable(false)` 慎用，仅在特殊场景（如动画中）使用 |

### 9. 大列表加载性能优化
> 大列表优化的核心思路就是三个词：**少刷新、快复用、轻绑定**。用 DiffUtil 做局部刷新减少不必要的 bind，用缓存机制和预热加速复用，把 `onBindViewHolder` 里的操作压到最轻。再配合分页加载控制数据量，基本就能保证大列表的流畅性了。

#### 9.1 局部刷新 — DiffUtil / AsyncListDiffer

千万不要一有数据变化就 `notifyDataSetChanged()`，这会导致全量刷新，所有可见的 ViewHolder 都会重新 bind。

正确做法是用 `DiffUtil` 或者更方便的 `AsyncListDiffer`，它会在**后台线程**计算新旧列表的差异，然后只刷新变化的部分。比如只插入了 3 条数据，那就只 bind 那 3 个 item，其他完全不动。

#### 9.2 开启 setHasStableIds

给 Adapter 设置 `setHasStableIds(true)`，然后重写 `getItemId()`，给每个 item 返回一个唯一稳定的 ID。

这样做的好处是 RecyclerView 在数据变化时，能通过 ID 识别出哪些 ViewHolder 可以复用，减少不必要的 create 和 bind。

#### 9.3 分页加载 / 无限滚动

不要一次性把所有数据都塞进去。用分页加载，比如每次加载 20 条，滑到底部再加载下一页。

配合 **Paging 3** 库来做，它帮你处理了分页逻辑、预加载、占位符这些，省心很多。

#### 9.4 预取 — prefetch

RecyclerView 有个 `LinearLayoutManager.setPrefetchCount()`，默认是 4。意思是当 item 快滑出屏幕时，提前在后台准备好后面几个 ViewHolder。

对于滑动速度很快的场景，可以适当调大这个值，让滑动更流畅。

#### 9.5 onBindViewHolder 里千万别做耗时操作

`onBindViewHolder` 是在**主线程**执行的，这里面只能做简单的数据绑定：
- 不要在这里做图片解码
- 不要在这里做数据库查询
- 不要在这里做复杂的字符串拼接

图片加载用 Glide/Coil 这种异步库，复杂数据提前在后台处理好，bind 的时候直接 set 就行。

#### 9.6 RecycledViewPool 预热

如果是打开页面就需要大量数据展示的场景，可以提前预热缓存。在数据准备好之后，先手动创建一批 ViewHolder 放进 `RecycledViewPool`，这样列表渲染的时候直接从缓存取，不用临时 create。

#### 9.7 setItemViewCacheSize

调大 `RecyclerView.setItemViewCacheSize()` 的值，让 `mCachedViews` 能缓存更多刚滑出屏幕的 ViewHolder。这些 ViewHolder 回来时**不需要重新 bind**，对频繁来回滑动的场景效果很明显。

#### 9.8 图片采用 WebP / AVIF 等二进制格式

相比 PNG/JPEG，WebP/AVIF 体积更小、解码更快，能显著降低内存占用和网络传输开销：
- **WebP**：同画质下比 PNG 小 26%、比 JPEG 小 25-34%，Android 4.0+ 原生支持
- **AVIF**：比 WebP 再小 20% 左右，Android 12+ 原生支持
- 服务端下发 WebP/AVIF，客户端直接用 Glide/Coil 加载，无需额外处理
- 列表场景图片量大，格式优化带来的内存和性能收益非常明显

#### 9.9 减少过渡绘制（Overdraw）

过渡绘制指同一像素被多次绘制，GPU 做了无用的重复工作。在列表场景中尤其严重，因为每个 item 都在快速滑过。

**排查方式**：开发者选项中开启「GPU 呈现模式分析」或「调试 GPU 过渡绘制」，蓝色/绿色区域过多说明 Overdraw 严重。

**优化手段**：
- **去掉多余背景**：最常见的问题，Window 默认有白色背景 + Activity 又设了背景 = 双重绘制。解决方案是 `Activity.theme` 中设置 `<item name="android:windowBackground">@null</item>`
- **`clipChildren = true`**：父容器裁剪子 View 超出边界的部分，避免子 View 绘制到不可见区域
- **避免层叠布局**：减少不必要的嵌套和叠加，让每个像素尽量只绘制一次

#### 9.10 布局层级尽量扁平化

每一层嵌套都会增加 measure/layout 的开销，列表中有成百上千个 item，层级过深会严重拖慢帧率。

- 使用 **ConstraintLayout** 替代多层嵌套的 LinearLayout/RelativeLayout，用约束关系代替嵌套
- 目标：**item 布局层级控制在 3 层以内**
- 扁平化不仅减少 measure 开销，还能减少 View 对象的创建数量，降低内存压力

#### 9.11 setItemEventNames 统一事件处理

`RecyclerView` 提供了 `setItemEventName(int position, String eventName)` 和 `setItemEventName(String viewTag, String eventName)` 两个 API，用于给 item 绑定事件名称。

**核心好处**：
- **避免每个 ViewHolder 单独创建 Listener 对象**：传统写法每个 item 都 `setOnClickListener`，会创建大量匿名内部类实例
- **统一分发**：所有事件通过 `onItemEvent(eventName, view)` 统一回调，集中处理
- **减少 GC 压力**：Listener 对象数量大幅减少，滑动更流畅

```kotlin
// 传统写法：每个 item 创建一个 Listener
holder.itemView.setOnClickListener { doSomething(position) }

// setItemEventNames 写法：统一事件分发
recyclerView.setItemEventName(position, "item_click")
// 在 onItemEvent 中统一处理
recyclerView.addOnItemEventListener(object : RecyclerView.OnItemEventListener {
    override fun onItemEvent(eventName: String, view: View) {
        when (eventName) {
            "item_click" -> handleClick(view)
            "item_long_click" -> handleLongClick(view)
        }
    }
})
```

#### 9.12 Flow 替代 LiveData

在列表数据源层面，用 **Flow** 替代 LiveData 有明显优势：

- **自带线程切换**：`flowOn(Dispatchers.IO)` 一行搞定后台计算 + 主线程更新，LiveData 需要手动切线程
- **操作符丰富**：`debounce`、`distinctUntilChanged`、`combine` 等操作符可以直接在数据流上做变换，避免中间状态
- **感知生命周期**：通过 `lifecycleScope.launch` / `repeatOnLifecycle` 自动随生命周期暂停和恢复收集，不会像 LiveData 那样在后台白白执行
- **与 Paging 3 天然配合**：Paging 3 的 `Pager` 直接返回 `Flow<PagingData<T>>`，无缝衔接

```kotlin
// Flow 数据流示例
val listFlow = repository.getItems()
    .flowOn(Dispatchers.IO)        // 后台线程查数据
    .map { it.sortedBy { item -> item.priority } }  // 后台排序
    .distinctUntilChanged()        // 数据没变就不刷新
    .flowOn(Dispatchers.Main)      // 切回主线程更新 UI
```

## 二、Glide

> **一句话总结**：核心是四级缓存（ActiveResources → MemoryCache → DiskCache → Network）就近获取，配合 Fragment 生命周期绑定自动管理请求（页面销毁自动取消），DiskCacheStrategy 支持 5 种磁盘缓存策略，BitmapPool 通过 inBitmap 复用内存避免频繁 GC。

### 1. 核心架构

Glide 采用 **Builder 模式 + 责任链 + 工厂模式** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **Glide** | 全局入口，管理 RequestManager 生命周期 |
| **RequestManager** | 管理每个 Activity/Fragment 的请求，绑定生命周期 |
| **RequestBuilder** | 构建加载请求（指定 URL、占位图、变换等） |
| **Request** | 实际执行加载的任务（`SingleRequest` 是核心实现） |
| **Engine** | 引擎层，包含 `DecodeJob` 的调度与执行 |
| **ModelLoader** | 将各种数据源（URL/File/ResourceId）转换为 InputStream |
| **DataFetcher** | 从数据源获取原始数据（网络下载、文件读取等） |
| **Decoder** | 将原始数据解码为 Bitmap/Drawable |
| **Transcoder** | 将解码后的资源转换为目标格式（如 Bitmap → GlideBitmapDrawable） |
| **ResourceTranscoder** | 资源转码器 |
| **ActiveResources / MemoryCache / DiskCache** | 三级缓存 |

### 2. 三级缓存机制（核心重点）

#### 第一级：Active Resources（正在使用的资源）
- 存储当前**正在显示**的图片资源
- 使用弱引用（`WeakReference`）持有，防止内存泄漏
- 当图片不再显示时，移入 MemoryCache
- 通过 `ActiveResources` 类管理，内部用 `HashMap<Key, WeakReference<Resource>>` 存储

#### 第二级：Memory Cache（内存缓存）
- 使用 `LruResourceCache` 实现（基于 `LruCache`）
- 默认大小为设备可用内存的 **1/8**
- 存储**已解码**的 Bitmap 资源
- 强引用持有，超出 LRU 限制时淘汰最久未使用的
- 当 Activity 被销毁时，MemoryCache 中的资源会被释放或转入磁盘缓存

#### 第三级：Disk Cache（磁盘缓存）
- 使用 `DiskLruCacheWrapper` 实现
- 默认存储路径：`/data/data/<包名>/image_manager_disk_cache/`
- 默认大小 **250MB**
- 存储**未解码**的原始数据（经过签名后的文件）
- 使用 **SafeKeyGenerator** 生成缓存 Key（URL + 变换参数 + 尺寸等 hash）
- 缓存策略（`DiskCacheStrategy`）：

| 策略 | 原始数据 | 变换后数据 | 说明 |
|------|:--------:|:----------:|------|
| **ALL** | ✅ | ✅ | 原始数据和变换后的都缓存 |
| **DATA** | ✅ | | 只缓存原始数据 |
| **RESOURCE** | | ✅ | 只缓存变换后的数据 |
| **NONE** | | | 不缓存磁盘 |
| **AUTOMATIC** | 根据来源自动选择 | — | 本地文件只缓存变换后数据，远程数据两个都缓存（**默认**） |

#### 缓存查找流程

```
加载图片时的查找顺序：

1. Active Resources → 正在显示？直接取（弱引用）
2. Memory Cache → 内存中有？直接取（强引用，不 decode）
3. Disk Cache → 磁盘中有？读取 → decode → 放入 Memory Cache
4. 都没有 → 网络/数据源下载 → decode → 存入 Disk Cache → 存入 Memory Cache → 显示
```

### 3. 生命周期绑定原理

Glide 最核心的设计之一：**将请求与 Activity/Fragment 生命周期绑定**。

#### 实现方式

```
Glide.with(activity/fragment)
        ↓
  创建一个不可见的 Fragment（SupportRequestManagerFragment）
        ↓
  将该 Fragment 添加到 Activity/Fragment 中
        ↓
  Fragment 的生命周期回调 → 驱动 RequestManager 的行为
```

#### 生命周期回调对应行为

| 生命周期回调 | Glide 行为 |
|---|---|
| `onStart` | 恢复暂停的请求 |
| `onStop` | 暂停正在进行的请求 |
| `onDestroy` | 取消所有请求，释放资源，清理缓存 |

#### 为什么用 Fragment 而不是直接监听 Activity？
- Fragment 的生命周期回调更精确
- 子 Fragment 可以自动跟随父 Activity/Fragment 的生命周期
- 如果用 Application Context，则无法感知生命周期，请求不会被自动管理

### 4. 加载流程（核心链路）

```
Glide.with(context).load(url).into(imageView)
        ↓
  ① Glide.with() → 获取/创建 RequestManager（绑定生命周期）
        ↓
  ② .load(url) → 创建 RequestBuilder，设置 model（数据源）
        ↓
  ③ .into(imageView) → 核心入口
        ↓
  ④ 构建 Target（ImageViewTarget）
        ↓
  ⑤ 构建 Request（SingleRequest）
        ↓
  ⑥ Request.begin() → 开始加载
        ↓
  ⑦ 检查缓存（Active → Memory → Disk）
        ↓
  ⑧ 缓存未命中 → 创建 EngineJob + DecodeJob
        ↓
  ⑨ DecodeJob 执行（在 GlideExecutor 线程池中）
        ↓
  ⑩ ModelLoader → DataFetcher → 获取原始数据（网络下载）
        ↓
  ⑪ ResourceDecoder → 解码为 Bitmap
        ↓
  ⑫ ResourceTranscoder → 转码为目标格式
        ↓
  ⑬ 回调到主线程 → Target.onResourceReady() → ImageView.setImageBitmap()
```

### 5. DecodeJob 执行流程（引擎层核心）

`DecodeJob` 是 Glide 加载流程的核心，实现了 `Runnable`，在线程池中执行：

#### 执行阶段（Stage）

```
DecodeJob.run()
    ↓
  runWrapped() → 按阶段执行
    ↓
  Stage.RESOURCE_CACHE → 查磁盘资源缓存
    ↓ 未命中
  Stage.DATA_CACHE → 查磁盘数据缓存
    ↓ 未命中
  Stage.SOURCE → 从数据源加载（网络/文件等）
    ↓
  每个阶段都会执行：
    1. 检查对应缓存
    2. 缓存未命中 → DataFetcher 获取数据
    3. ResourceDecoder 解码
    4. Transcoder 转码
    5. 结果回调到主线程
```

#### 数据转换流水线（Data → Resource）

```
原始数据（InputStream）
    ↓
  ResourceDecoder.decode() → 解码为 Bitmap
    ↓
  Transformation（可选）→ 圆角、模糊等变换
    ↓
  ResourceTranscoder.transcode() → 转码为 Drawable
    ↓
  回调到主线程 → 设置到 ImageView
```

### 6. 与 Activity 生命周期联动的内存管理

```
Activity.onDestroy()
    ↓
  RequestManager.onDestroy()
    ↓
  取消所有正在执行的 Request
    ↓
  清理 ActiveResources（弱引用置空）
    ↓
  清空 MemoryCache
    ↓
  MemoryCache 中的资源 → 判断是否仍被引用
    ↓ 无引用
  转入 DiskCache（可选）或直接释放
```

#### 内存管理的关键设计

Glide 的内存管理有几个比较巧妙的设计：

1. **生命周期绑定**：Glide 会在当前 Activity/Fragment 上绑定一个不可见的 Fragment 来监听生命周期。页面销毁了，请求自动取消，内存缓存自动清理。这就是为什么 Glide 不容易 OOM。
2. **内存警告监听**：Glide 注册了 `ComponentCallbacks2`，当系统发出低内存警告时，会自动清理内存缓存。
3. **Bitmap 复用**：Glide 4.x 之后支持 Bitmap 对象池，通过 `inBitmap` 复用已有的 Bitmap 内存，避免频繁 GC。

### 7. 关键设计亮点

#### 7.1 对象池复用（BitmapPool）
- Glide 内部维护 `LruBitmapPool`，复用已不再使用的 Bitmap 对象
- 解码时通过 `BitmapFactory.Options.inBitmap` 复用已有 Bitmap 内存
- 避免频繁创建和回收 Bitmap，减少 GC
- 默认大小：设备可用内存的 **1/40**（4.x）或 **1/20**（5.0+，因为 5.0 后 Bitmap 内存分配在 native 堆）

#### 7.2 智能降采样（Downsampling）
- 根据 ImageView 的实际宽高计算 `inSampleSize`
- 避免加载远超显示尺寸的图片，节省内存
- 如果 ImageView 尺寸未知，会先使用 `inJustDecodeBounds` 获取原始尺寸

#### 7.3 请求优先级（Priority）
- 支持设置 `Priority.LOW / NORMAL / HIGH / IMMEDIATE`
- 同一优先级的请求按 FIFO 执行
- 高优先级的请求可以插队
- ListView/RecyclerView 滑动时，可见 Item 的请求优先级高于不可见的

#### 7.4 请求合并与去重
- 相同 Key 的请求同时存在时，新请求会**加入**已有请求的回调列表
- 不会重复发起网络请求，结果共享给所有等待者
- 通过 `EngineJob` 的 `addCallback()` 实现

### 8. 主流图片加载框架对比

#### 8.1 综合对比表

| 维度 | Glide | Picasso | Fresco | Coil |
|------|-------|---------|--------|------|
| **缓存层级** | 三级（Active + Memory + Disk） | 两级（Memory + Disk） | 三级（内存 + 磁盘 + 未解码） | 两级（Memory + Disk） |
| **Bitmap 存储** | Java 堆（4.x）/ Native 堆（5.0+） | Java 堆 | Native 堆（匿名共享内存） | Native 堆（5.0+） |
| **生命周期绑定** | 绑定 Fragment | 无 | 无（需手动管理） | 绑定 Lifecycle（Jetpack） |
| **GIF 支持** | 原生支持 | 不支持 | 原生支持 | 通过扩展支持（gif 解码器） |
| **WebP/AVIF** | 支持（WebP 原生，AVIF 需扩展） | 不支持 | 支持（WebP） | 支持（WebP 原生，AVIF 需扩展） |

#### 8.2 各框架核心特点

**Glide**：
- 功能最全面的 Java 图片库，社区成熟、文档完善
- 三级缓存 + BitmapPool 复用，内存管理精细
- 支持视频缩略图、GIF、自定义 Transformation
- 与 RecyclerView 深度集成，滑动时自动暂停/恢复加载
- 缺点：API 相对繁琐，Java 风格较重

**Picasso**：
- Square 出品，API 最简洁，学习成本最低
- 内部实现简单，包体积最小（~100KB）
- 不支持 GIF、视频缩略图，功能相对单一
- 无生命周期管理，需手动处理取消请求
- 适合简单场景，复杂项目不推荐

**Fresco**：
- Facebook 出品，专为大量图片展示优化（如 Facebook App）
- 将 Bitmap 存储在 Native 堆（匿名共享内存），彻底避免 Java 堆 OOM
- 支持渐进式 JPEG、WebP、GIF
- 缺点：包体积大（~3MB）、初始化慢、与 RecyclerView 集成不如 Glide 灵活
- 适合低端设备 + 大量图片的场景（如社交/电商 App）

**Coil**：
- Kotlin First，API 最现代，与 Kotlin 协程天然契合
- 基于 Jetpack Lifecycle 管理请求生命周期
- 包体积小（~300KB），轻量级
- 支持 SVG、GIF（扩展）、视频帧提取（扩展）
- 底层默认使用 OkHttp 作为网络层，缓存策略与 OkHttp 一致
- 缺点：社区相对年轻，生态不如 Glide 成熟
- 适合 Kotlin 项目首选，特别是已使用协程的项目

```
    └─ 否 → 按上面规则选
```

## 三、ARouter

> **一句话总结**：编译时通过 APT 扫描 @Route 注解生成 Root（分组索引）和 Group（分组路由表）两类映射文件，运行时 init 只加载分组索引，具体路由表在首次跳转时按需懒加载；页面跳转走路由表 + 拦截器链，接口通信走 IProvider 反射实例化 + 单例缓存（轻量依赖注入）。

### 1. 核心架构

ARouter 是 Android 平台的路由框架，采用 **APT + 策略模式 + 责任链模式** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **ARouter** | 全局入口，初始化、路由跳转、服务发现 |
| **Postcard** | 路由信息封装（路径、参数、标记等），继承自 `RouteMeta` |
| **RouteMeta** | 路由元信息（路径、目标类型、Group、路由地址等） |
| **LogisticsCenter** | 路由调度中心，负责路由表查找、拦截器调度 |
| **InterceptorService** | 拦截器服务，管理全局拦截器链 |
| **IProvider** | 服务接口，用于跨模块接口通信（依赖注入） |
| **RouteProcessor / ProviderProcessor** | APT 编译器，编译期生成路由映射代码 |
| **_ARouter** | 内部核心实现类，封装所有路由逻辑 |

### 2. 两大核心功能

ARouter 主要解决两个问题：
1. **页面跳转**：通过 URL 路径跳转到 Activity/Fragment/其他组件，支持拦截器
2. **接口通信（依赖注入）**：通过 `IProvider` 实现跨模块接口调用，解耦模块间依赖

### 3. 编译期路由表生成（APT）

#### 3.1 注解处理

ARouter 在编译期通过 APT（Annotation Processing Tool）处理两类注解：

| 注解 | 作用 | 生成类 |
|------|------|--------|
| `@Route(path = "/xx/xx")` | 标记路由目标（Activity/Fragment） | `ARouter$$Group$$xxx` |
| `@Route(path = "/xx/xx")` + `implements IProvider` | 标记服务提供者 | `ARouter$$Providers$$xxx` |

#### 3.2 生成的路由表结构

APT 生成的文件有两类：

**① ARouter$$Root$$模块名 — 分组索引表**

记录"我这个模块有哪些分组"，实现 `IRouteRoot` 接口：
```java
public void loadInto(Map<String, Class<? extends IRouteGroup>> routes) {
    routes.put("order", ARouter$$Group$$order.class);
    routes.put("user", ARouter$$Group$$user.class);
}
```

**② ARouter$$Group$$分组名 — 分组路由表**

记录"这个分组下有哪些路由"，实现 `IRouteGroup` 接口：
```java
public void loadInto(Map<String, RouteMeta> atlas) {
    atlas.put("/order/detail", RouteMeta.build(
        RouteType.ACTIVITY, OrderDetailActivity.class, "/order/detail", "order", ...));
}
```

简单说：**Root 文件管"有哪些分组"，Group 文件管"每个分组下有哪些路由"**。编译完就全生成好了，运行时不需要反射扫描注解，性能很好。

**服务表（Provider Table）**：
```
ARouter$$Providers$$xxx（服务提供者表）
    └── loadInto(Warehouse.providers)  // 注册 IProvider 映射
        providers.put("com.xxx.IUserService", UserServiceImpl.class)
```

#### 3.3 三级映射（Group 分组优化）

```
第一级：Root 表 → Group 名 映射到 Group 类
第二级：Group 表 → 具体路径 映射到 RouteMeta（目标类 + 路径信息）
第三级：Providers 表 → 接口名 映射到 Provider 实现类
```

**为什么要分组？**
- 避免启动时加载所有路由表，按需加载
- 首次访问某个 Group 时，才加载该 Group 的路由表
- 减少初始化耗时，加快启动速度

### 4. 页面跳转流程（核心）

#### 4.1 跳转执行流程

```
ARouter.getInstance().build("/app/MainActivity").withString("key", "value").navigation()
        ↓
  ① build() → 创建 Postcard（封装路径、参数）
        ↓
  ② LogisticsCenter.completion(postcard) → 查路由表
        ↓
  ③ 查 Warehouse.groupsAtRoute → 找到对应 Group 类
        ↓
  ④ 反射加载 Group 类 → loadInto(Warehouse.routes) → 注册该组路由
        ↓
  ⑤ 查 Warehouse.routes → 找到 RouteMeta（目标类、路径等）
        ↓
  ⑥ 将 RouteMeta 信息填充到 Postcard
        ↓
  ⑦ _ARouter.navigation(context, postcard) → 执行跳转
        ↓
  ⑧ 拦截器链处理（InterceptorService）
        ↓
  ⑨ 根据 RouteMeta.type 分发：
        ├─ ACTIVITY → 构建 Intent → startActivity()
        ├─ FRAGMENT → 反射创建 Fragment 实例
        ├─ PROVIDER → 反射创建 Provider 实例
        └─ CONTENT_PROVIDER → 通过 ContentProvider 跳转
```

#### 4.2 页面跳转的底层原理

**① 发起跳转 — Postcard 创建**

调用 `build(path)` 后创建 `Postcard` 对象，封装了这次跳转的所有信息：路径、参数（Bundle）、标志位等。

**② 拦截器链处理**

在进入真正的跳转逻辑之前，先经过全局拦截器链 `Warehouse.interceptors`（按优先级排序）：

```
navigation() → _navigation()
  → LogisticsCenter.completion(postcard)  // 补全路由信息
  → 有拦截器？→ 进入拦截器链
    → 拦截器1.handle() → onContinue() → 拦截器2 → ... → 最终跳转
    → 某个拦截器 onInterrupt() → 中断，不跳转
```

**③ 路由信息补全**

`LogisticsCenter.completion()` 从 `Warehouse.routes` 里查 `RouteMeta`，没有就懒加载 Group 路由表。补全之后 Postcard 就有了目标页面的 Class 信息和类型（Activity/Fragment/Service 等）。

**④ 根据类型执行跳转**

```java
switch (type) {
    case ACTIVITY:
        Intent intent = new Intent(context, postcard.getDestination());
        intent.putExtras(postcard.getExtras()); // withString/withInt 等参数
        context.startActivity(intent);
        break;
    case FRAGMENT:
        BaseFragment fragment = (BaseFragment) postcard.getDestination().newInstance();
        fragment.setArguments(postcard.getExtras());
        // 通过 FragmentManager 添加
        break;
}
```

**⑤ 回调**

跳转完成后通过 `NavigationCallback` 通知调用方：
- `onFound(Postcard)` — 找到路由
- `onLost(Postcard)` — 没找到路由
- `onArrival(Postcard)` — 到达目标
- `onInterrupt(Postcard)` — 被拦截器拦截

#### 关键细节
- **Group 按需加载**：首次访问某个 Group 时才加载，加载后缓存在 `Warehouse.groupsAtRoute`
- **路由表懒加载**：`Warehouse.routes` 只在对应 Group 被访问时才填充
- **参数传递**：通过 `Postcard.getExtras()` 携带 Bundle，跳转时放入 Intent

### 5. 拦截器链机制

拦截器用于在跳转前执行全局逻辑（如登录检查、权限校验等）。

#### 5.1 拦截器定义

```kotlin
@Interceptor(priority = 1, name = "登录拦截器")
class LoginInterceptor : IInterceptor {
    override fun process(postcard: Postcard, callback: InterceptorCallback) {
        if (isLogin) {
            callback.onContinue(postcard)  // 放行
        } else {
            callback.onInterrupt(null)     // 拦截，不跳转
        }
    }
    override fun init(context: Context) { }
}
```

#### 5.2 拦截器链执行流程

```
_ARouter.navigation()
        ↓
  获取所有拦截器（按 priority 排序）
        ↓
  构建责任链：Interceptor1 → Interceptor2 → ... → InterceptorN
        ↓
  执行第一个拦截器
        ↓
  ├─ onContinue() → 执行下一个拦截器
  └─ onInterrupt() → 终止跳转，回调 NavigationCallback.onLost()
        ↓
  所有拦截器都 onContinue() → 执行实际跳转
```

#### 5.3 拦截器初始化时机
- 拦截器在 ARouter 初始化时（`ARouter.init()`）被扫描和实例化
- 通过 APT 生成的 `ARouter$$Interceptors$$xxx` 收集所有拦截器类
- 按 `priority` 升序排列（数字越小优先级越高）
- `init(context)` 在初始化时被调用

### 6. 接口通信（IProvider 依赖注入）流程

#### 6.1 执行流程

```
ARouter.getInstance().navigation(IUserService::class.java)
        ↓
  ① 查 Warehouse.providers → 找到 ProviderBean（接口名 → 实现类）
        ↓
  ② ProviderBean 中有实现类 Class，但实例为 null
        ↓
  ③ 反射创建实现类实例：UserServiceImpl()
        ↓
  ④ 调用 provider.init(context) → 初始化
        ↓
  ⑤ 将实例缓存到 ProviderBean.instance
        ↓
  ⑥ 返回 IUserService 实例
        ↓
  后续调用直接返回缓存的实例（单例模式）
```

#### 6.2 接口通信的底层原理

ARouter 除了跳页面，还能做接口级别的通信，本质上是一个**轻量级的依赖注入框架**。

**① 定义接口和实现**

```java
// 定义接口，继承 IProvider
public interface IUserService extends IProvider {
    String getUserName();
}

// 实现类，用 @Route 标注
@Route(path = "/service/user")
public class UserServiceImpl implements IUserService {
    @Override
    public void init(Context context) { /* 初始化逻辑 */ }

    @Override
    public String getUserName() { return "张三"; }
}
```

**② 编译时 — APT 生成 Provider 映射**

编译时 APT 生成 `ARouter$$Providers$$模块名`，记录接口和实现类的映射：
```java
public void loadInto(Map<String, Class<? extends IProvider>> providers) {
    providers.put(IUserService.class.getName(), UserServiceImpl.class);
}
```

**③ 运行时 — 获取实例（伪代码）**

```java
public <T> T navigation(Class<T> service) {
    // 1. 先从缓存里找
    IProvider provider = Warehouse.providers.get(service.getName());
    if (provider != null) return (T) provider;  // 有就直接返回，单例

    // 2. 从 providers 映射表里找实现类
    Class<? extends IProvider> implClass = Warehouse.providersIndex.get(service.getName());

    // 3. 反射创建实例 + init 初始化
    IProvider instance = implClass.newInstance();
    instance.init(context);

    // 4. 缓存起来，下次直接返回
    Warehouse.providers.put(service.getName(), instance);
    return (T) instance;
}
```

**关键点**：IProvider 是**单例**的，第一次获取时创建实例并缓存，后面直接返回缓存实例。

**④ 存储结构**

```java
// Warehouse 中的关键 Map
// 接口全限定名 → 实现类的 Class 对象
static Map<String, Class<? extends IProvider>> providersIndex = new HashMap<>();
// 接口全限定名 → 实现类的单例实例
static Map<String, IProvider> providers = new HashMap<>();
```

#### 关键细节
- **单例**：每个 Provider 实现只创建一次，后续复用缓存实例
- **init() 只调用一次**：首次创建时调用，后续复用不再调用
- **线程安全**：通过 `LogisticsCenter` 的同步机制保证

### 7. 页面跳转 vs 接口通信对比

#### 7.1 对比表

| 维度 | 页面跳转 | 接口通信（IProvider） |
|------|----------|------------------|
| **入口** | `navigation(path)` | `navigation(Class)` |
| **查找方式** | 通过路径查 `Warehouse.routes` | 通过接口名查 `Warehouse.providersIndex` |
| **执行逻辑** | 构建 Intent → 拦截器链 → startActivity | 反射创建实例 → init → 缓存 |
| **结果** | 打开一个新页面 | 返回一个接口实现类的单例 |
| **拦截器** | 支持 | 不支持 |
| **生命周期** | 由 Android 系统管理 | 单例，全局复用 |
| **本质** | 路由导航 | 依赖注入（DI） |

#### 7.2 核心区别

页面跳转的本质是 **路径 → RouteMeta → Intent → startActivity**，中间经过拦截器链做各种拦截逻辑；接口通信的本质是 **接口 Class → 实现类 Class → 反射实例化 → 单例缓存**，是一个轻量级的依赖注入。两者共用同一套 APT 生成机制和 Warehouse 存储，但运行时的处理逻辑完全不同。

### 8. 初始化流程与路由表加载

#### 8.1 初始化流程

```
ARouter.init(application)
        ↓
  _ARouter.init(application)
        ↓
  LogisticsCenter.init(context, config)
        ↓
  加载路由表：
    1. 扫描 APK 中的 dex 文件，查找 "com/alibaba/android/arouter/routes/" 开头的类
    2. 反射加载 ARouter$$Root$$xxx → 注册 Group 映射到 groupsAtRoute
    3. 反射加载 ARouter$$Providers$$xxx → 注册 Provider 映射到 providers
    4. 反射加载 ARouter$$Interceptors$$xxx → 注册拦截器类
        ↓
  初始化拦截器服务（InterceptorService）
        ↓
  实例化所有拦截器并调用 init()
```

#### 8.2 路由表是如何加载到内存的

ARouter 的路由表加载核心思路：**编译时生成 + 运行时懒加载**。

**运行时核心存储 — Warehouse**

`Warehouse` 是路由表的存储中心，里面有几个关键的 Map：

```java
// 存储分组索引：groupName → Group 类的 Class 对象
static Map<String, Class<? extends IRouteGroup>> groupsIndex = new HashMap<>();
// 存储具体路由：path → RouteMeta
static Map<String, RouteMeta> routes = new HashMap<>();
```

**第一步：init 时加载 Root 分组索引**

调用 `ARouter.init(application)` 时，走到 `LogisticsCenter.init()`：
1. 找到所有模块生成的 `ARouter$$Root$$xxx` 类
2. 通过反射调用它们的 `loadInto` 方法
3. 把分组信息注册到 `Warehouse.groupsIndex` 中

```java
// 伪代码
Class rootClass = Class.forName("...ARouter$$Root$$app");
IRouteRoot rootInstance = (IRouteRoot) rootClass.newInstance();
rootInstance.loadInto(Warehouse.groupsIndex);
```

> 注意：这一步**只加载了分组索引**，还没加载具体的路由信息。

**第二步：按需懒加载 Group 路由表**

当真正要跳转某个路径（比如 `/order/detail`）时，`LogisticsCenter.completion()` 去 `Warehouse.routes` 里找：
- **找到了** → 直接用，返回 RouteMeta
- **没找到** → 说明这个分组还没加载过，去 `Warehouse.groupsIndex` 找到对应的 Group 类，反射实例化后调用 `loadInto`，把该分组下的所有路由加载到 `Warehouse.routes` 中

```java
// 伪代码
if (routes.get(path) == null) {
    Class groupClass = groupsIndex.get(groupName);
    IRouteGroup groupInstance = groupClass.newInstance();
    groupInstance.loadInto(Warehouse.routes);  // 加载该分组的所有路由
}
RouteMeta meta = routes.get(path);  // 再次获取
```

这就是**懒加载**——用到的时候才加载，不用的分组不加载，节省内存和启动时间。

#### 8.3 完整流程总结

```
编译时：
  @Route 注解 → APT 扫描 → 生成 ARouter$$Root$$xxx + ARouter$$Group$$xxx

运行时 init：
  ARouter.init() → LogisticsCenter.init()
    → 反射调用所有 Root 类的 loadInto()
    → 分组索引写入 Warehouse.groupsIndex

运行时跳转：
  navigation("/order/detail") → LogisticsCenter.completion()
    → 查 Warehouse.routes，有就直接用
    → 没有就反射加载对应的 Group 类 → loadInto → 写入 Warehouse.routes
    → 再查 Warehouse.routes，拿到 RouteMeta
    → 根据 RouteMeta 里的 Class 信息启动目标页面
```

### 9. 关键设计亮点

#### 9.1 按 Group 懒加载路由表
- 启动时只加载 Root 表和 Providers 表
- 具体 Group 的路由表在首次访问时才加载
- 大幅减少初始化耗时

#### 9.2 编译期生成代码，运行时零反射
- 路由表、Provider 映射、拦截器列表全部由 APT 在编译期生成
- 运行时只需加载生成的类，不需要扫描注解
- 性能远优于运行时反射方案

#### 9.3 支持多模块
- 每个模块独立生成路由表
- 通过统一的 Root 表合并所有模块的路由
- 模块间完全解耦，只需依赖 ARouter 注解

#### 9.4 URL Scheme 支持
- 支持通过 URL Scheme 跳转（如 `arouter://m.aliuche.com/main`）
- 内部将 URL 解析为 Postcard 路径
- 可与 H5、DeepLink 打通

### 10. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 减少初始化耗时 | 利用 Group 懒加载，避免全量加载 |
| 拦截器性能 | 拦截器数量不宜过多，每个拦截器逻辑尽量轻量 |
| 避免重复跳转 | 设置 `withTransition()` 或防重复点击拦截器 |
| 混淆配置 | 保留 ARouter 生成的类和 IProvider 接口 |
| 多模块路由表 | 每个模块独立配置 APT，自动合并 |
| 服务发现 | 用 IProvider 替代接口暴露，实现模块解耦 |

## 四、Retrofit

> **一句话总结**：通过动态代理拦截接口方法调用，解析方法上的注解（@GET/@POST/参数注解等）构建 HTTP 请求，再委托 OkHttp 执行网络请求，最后通过 Converter 反序列化为对象、CallAdapter 适配返回类型（Call/RxJava/协程），实现"声明式接口 = HTTP 请求"。

### 1. 核心架构

Retrofit 是一个类型安全的 HTTP 框架，采用 **Builder 模式 + 动态代理 + 适配器模式 + 策略模式** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **Retrofit** | 全局配置入口，管理 baseUrl、ConverterFactory、CallAdapter 等 |
| **ServiceMethod** | 解析接口方法的注解（@GET/@POST、参数注解等），构建请求 |
| **RequestFactory** | 根据注解构建 HTTP 请求（URL、Header、参数等） |
| **OkHttpCall** | 封装 OkHttp 的 Call，实现同步/异步请求 |
| **Service** | 用户定义的接口，通过动态代理生成实现 |
| **Converter** | 数据转换器（JSON → 对象），如 GsonConverterFactory |
| **CallAdapter** | 将 Call<T> 适配为目标返回类型（如 RxJava、Coroutine） |
| **Platform** | 平台相关逻辑（Android 默认回调到主线程） |

### 2. 核心设计思想

Retrofit 的核心设计可以用一句话概括：**通过动态代理 + 注解，将 HTTP 接口声明转换为 HTTP 请求执行**。

```
开发者声明式接口（注解描述 HTTP 请求）
        ↓
  动态代理拦截方法调用
        ↓
  解析注解 → 构建 HTTP 请求
        ↓
  通过 OkHttp 执行请求
        ↓
  解析响应 → 转换数据 → 回调结果
```

### 3. 初始化流程

```kotlin
val retrofit = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .addConverterFactory(GsonConverterFactory.create())
    .addCallAdapterFactory(CoroutinesCallAdapterFactory.create())
    .client(okHttpClient)
    .build()
```

#### Builder 内部做了什么

```
Retrofit.Builder()
    ↓
  初始化默认配置：
    - callFactory = OkHttpClient（默认）
    - converterFactories = 内置的 BuiltInConverters（支持 ResponseBody/RequestBody 等）
    - callAdapterFactories = 平台默认（Android 默认回调主线程的 DefaultCallAdapterFactory）
    - callbackExecutor = Android 主线程 Executor
    ↓
  build()
    ↓
  构建 Retrofit 实例，锁定所有配置（不可变）
```

### 4. 动态代理机制（核心重点）

```kotlin
val apiService = retrofit.create(ApiService::class.java)
```

#### create() 内部流程

```
retrofit.create(ApiService::class.java)
        ↓
  ① 验证接口合法性（不能是接口以外的类型、不能有泛型等）
        ↓
  ② 检查平台是否需要默认方法（Android 需要注入默认方法）
        ↓
  ③ 创建动态代理 Proxy.newProxyInstance()
        ↓
  ④ 每次调用接口方法时，触发 InvocationHandler.invoke()
        ↓
  ⑤ invoke() 内部：
        ├─ 特殊方法（equals/hashCode/toString）→ 直接处理
        ├─ default 方法 → 直接调用
        └─ 普通方法 → loadServiceMethod(method) → 执行
```

#### ServiceMethod 解析（loadServiceMethod）

```
loadServiceMethod(method)
        ↓
  ① 先从缓存查：serviceMethodCache.get(method)
        ↓
  ② 缓存未命中 → 创建 ServiceMethod
        ↓
  ③ ServiceMethod.parseAnnotations()
        ├─ 解析 HTTP 方法注解（@GET/@POST/...）→ 得到 relativeUrl
        ├─ 解析 Header 注解（@Headers/@Header/@HeaderMap）
        ├─ 解析参数注解（@Body/@Field/@Query/@Path/...）
        ├─ 解析返回类型 → 确定 CallAdapter
        └─ 解析 Converter → 确定数据转换方式
        ↓
  ④ 缓存到 serviceMethodCache（ConcurrentHashMap，避免重复解析）
```

### 5. 请求执行流程

#### 5.1 同步请求

```
apiService.getUser("id").execute()
        ↓
  ① 动态代理 → ServiceMethod → 创建 OkHttpCall
        ↓
  ② OkHttpCall.createRequest() → 构建 OkHttp 的 Request
        ├─ 拼接 URL（baseUrl + relativeUrl + Path 参数）
        ├─ 设置 Header
        ├─ 设置 Query 参数
        ├─ 设置 RequestBody（@Body 转换后的 JSON）
        └─ 设置 HTTP Method
        ↓
  ③ OkHttpCall.execute() → rawCall.execute()
        ↓
  ④ OkHttp 执行网络请求（拦截器链 → 连接服务器 → 获取响应）
        ↓
  ⑤ parseResponse(rawResponse) → 解析响应
        ├─ 检查 HTTP 状态码（2xx 成功，其他抛 HttpException）
        ├─ 读取 ResponseBody
        └─ Converter.convert() → JSON 反序列化为对象
        ↓
  ⑥ 返回 Response<T>
```

#### 5.2 异步请求

```
apiService.getUser("id").enqueue(callback)
        ↓
  ① 动态代理 → ServiceMethod → 创建 OkHttpCall
        ↓
  ② OkHttpCall.enqueue()
        ↓
  ③ 调用 OkHttp 的 call.enqueue()（异步执行）
        ↓
  ④ 请求完成回调：
        ├─ 成功 → parseResponse() → Converter 转换
        ├─ 通过 callbackExecutor（Android 主线程）回调到主线程
        └─ callback.onResponse() 或 callback.onFailure()
```

### 6. 核心组件详解

#### 6.1 Converter（数据转换器）

将 HTTP 响应体转换为目标类型，或将请求体从目标类型序列化。

```
请求：对象 → Converter → RequestBody（JSON 字符串）
响应：ResponseBody（JSON 字符串） → Converter → 对象
```

| 转换器 | 依赖 | 适用场景 |
|---------|------|----------|
| GsonConverterFactory | gson | JSON 序列化/反序列化 |
| MoshiConverterFactory | moshi | JSON（Kotlin 友好） |
| ScalarsConverterFactory | 内置 | String/基本类型 |
| ProtobufConverterFactory | protobuf | Protocol Buffers |
| JAXBConverterFactory | jaxb | XML |

**Converter 查找顺序**：按添加顺序依次尝试，第一个能处理的 Converter 生效。

#### 6.2 CallAdapter（调用适配器）

将 `Call<T>` 适配为目标返回类型。

```
接口声明：suspend fun getUser(): User
CallAdapter 将 Call<User> → suspend fun 返回 User
```

| 适配器 | 返回类型 |
|---------|----------|
| DefaultCallAdapterFactory | `Call<T>` |
| CoroutinesCallAdapterFactory | `suspend fun` 返回 `T` |
| RxJavaCallAdapterFactory | `Observable<T>` / `Flowable<T>` / `Single<T>` |

**CallAdapter 查找顺序**：按添加顺序依次尝试，第一个能处理的 CallAdapter 生效。

### 7. 注解体系

#### 7.1 HTTP 方法注解

| 注解 | HTTP 方法 | 是否有请求体 |
|------|-----------|------------|
| `@GET` | GET | 否 |
| `@POST` | POST | 是 |
| `@PUT` | PUT | 是 |
| `@DELETE` | DELETE | 可选 |
| `@PATCH` | PATCH | 是 |
| `@HEAD` | HEAD | 否 |
| `@OPTIONS` | OPTIONS | 否 |
| `@HTTP` | 自定义 | 可配置 |

#### 7.2 参数注解

| 注解 | 作用 | 位置 |
|------|------|------|
| `@Path` | URL 路径参数替换 | URL 中 `{id}` → 实际值 |
| `@Query` | URL 查询参数 | `?key=value` |
| `@QueryMap` | 多个查询参数（Map） | `?k1=v1&k2=v2` |
| `@Field` | 表单字段（POST body） | `application/x-www-form-urlencoded` |
| `@FieldMap` | 多个表单字段 | 同上 |

| `@HeaderMap` | 多个请求头（Map） | Header 中 |
| `@Part` | Multipart 字段 | `multipart/form-data` |

### 8. OkHttp 拦截器链（Retrofit 底层网络层）

Retrofit 底层使用 OkHttp 执行请求，OkHttp 的拦截器链是责任链模式：

```
用户请求
    ↓
  用户自定义 Interceptors（addInterceptor）
    ↓
  RetryAndFollowUpInterceptor（重试和重定向）
    ↓
  BridgeInterceptor（添加 Header、Cookie、Gzip 等）
    ↓
  CacheInterceptor（缓存策略）
    ↓
  ConnectInterceptor（建立连接）
    ↓
  CallServerInterceptor（实际发送请求、读取响应）
    ↓
  响应返回
```

### 9. 关键设计亮点

#### 9.1 动态代理 + 注解 = 声明式 API
- 开发者只需定义接口 + 注解，无需写实现
- Retrofit 通过动态代理在运行时生成实现
- 注解解析结果被缓存，避免重复解析

#### 9.2 高度可扩展
- Converter 和 CallAdapter 都是接口，可自由扩展
- OkHttp 拦截器链可自由插入自定义逻辑
- 支持多种序列化格式、多种异步模型

#### 9.3 ServiceMethod 缓存
- 每个方法的注解解析结果缓存在 `ConcurrentHashMap<Method, ServiceMethod>`
- 同一个方法多次调用只解析一次
- 线程安全

#### 9.4 与 Kotlin 协程的完美融合
- 通过 `suspend fun` 声明接口方法
- CallAdapter 将 `Call<T>` 适配为挂起函数
- 底层通过 `suspendCancellableCoroutine` 实现挂起等待
- 支持协程取消时自动取消 HTTP 请求

### 10. Retrofit vs OkHttp vs Volley 对比

| 维度 | Retrofit | OkHttp | Volley |
|------|----------|--------|--------|
| **定位** | HTTP 接口框架 | HTTP 客户端 | HTTP 请求库 |
| **关系** | 底层封装了 OkHttp | 独立 HTTP 客户端 | 独立 HTTP 客户端 |
| **API 风格** | 声明式（接口 + 注解） | 编程式（构建 Request） | 编程式 |
| **数据转换** | 内置 Converter 体系 | 无（需手动解析） | 内置 JSON 解析 |
| **协程支持** | 原生支持 | 不支持 | 不支持 |
| **缓存** | 依赖 OkHttp | 完善（多级缓存） | 内存缓存 |
| **适用场景** | RESTful API | 底层 HTTP 操作 | 简单 GET/POST |

### 11. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 连接池复用 | 使用单例 OkHttpClient，避免重复创建连接 |
| 超时配置 | 根据场景设置 connect/read/write 超时时间 |
| 拦截器顺序 | 公共 Header、日志等拦截器按正确顺序添加 |
| Converter 选择 | 根据数据格式选择最合适的 Converter |
| 取消请求 | 利用协程取消或 `Call.cancel()` 避免无效请求 |
| 缓存策略 | 通过 OkHttp Cache + 拦截器实现响应缓存 |
| 错误处理 | 统一封装 ErrorBody 解析，避免每个接口重复处理 |
| 基址 URL 管理 | 使用 `@Url` 动态指定完整 URL，或 baseUrl 拼接 |

## 五、OkHttp

> **一句话总结**：请求依次经过五个内置拦截器（Retry → Bridge → Cache → Connect → CallServer）各司其职，连接池通过 Keep-Alive 复用 TCP 连接避免重复握手，Dispatcher 控制全局并发数（maxRequests=64、perHost=5），底层基于责任链模式实现高度可扩展的 HTTP 客户端。

### 1. 核心架构

OkHttp 是一个高效的 HTTP 客户端，采用 **责任链模式 + Builder 模式 + 工厂模式** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **OkHttpClient** | 全局配置入口，管理拦截器、连接池、缓存等 |
| **Call** | 单次 HTTP 请求的抽象，支持同步/异步 |
| **RealCall** | Call 的核心实现，负责请求的创建和执行 |
| **Request** | 封装 HTTP 请求（URL、Header、Method、Body） |
| **Response** | 封装 HTTP 响应（状态码、Header、Body） |
| **Interceptor** | 拦截器接口，责任链的核心单元 |
| **ConnectionPool** | 连接池，复用 TCP 连接（HTTP Keep-Alive） |
| **Dispatcher** | 调度器，管理并发请求（同步/异步队列） |
| **Cache** | 磁盘缓存，基于 DiskLruCache |
| **RealConnection** | 底层 TCP 连接封装 |

### 2. 整体架构分层

```
应用层
  ↓
  OkHttpClient（配置入口）
  ↓
  Call / RealCall（请求抽象）
  ↓
  Dispatcher（调度器：并发控制）
  ↓
  拦截器链（责任链模式）
  ├─ 用户自定义拦截器
  ├─ RetryAndFollowUpInterceptor
  ├─ BridgeInterceptor
  ├─ CacheInterceptor
  ├─ ConnectInterceptor
  └─ CallServerInterceptor
  ↓
  ConnectionPool（连接池：TCP 复用）
  ↓
  网络层（Socket / TLS）
```

### 3. 请求执行流程

#### 3.1 同步请求

```
client.newCall(request).execute()
        ↓
  ① RealCall 创建（封装 Request + OkHttpClient）
        ↓
  ② Dispatcher.executedCalls.add(this) → 记录正在执行的请求
        ↓
  ③ getResponseWithInterceptorChain() → 构建拦截器链
        ↓
  ④ 拦截器链依次执行（详见第 5 节）
        ↓
  ⑤ 返回 Response
        ↓
  ⑥ Dispatcher.executedCalls.remove(this) → 移除记录
```

#### 3.2 异步请求

```
client.newCall(request).enqueue(callback)
        ↓
  ① RealCall 创建
        ↓
  ② Dispatcher.enqueue(call) → 加入异步队列
        ↓
  ③ Dispatcher 调度逻辑：
        ├─ 检查 runningAsyncCalls 是否 < maxRequests（默认 64）
        ├─ 检查同一 host 的并发是否 < maxRequestsPerHost（默认 5）
        ├─ 满足条件 → 加入 runningAsyncCalls → 线程池执行
        └─ 不满足 → 加入 readyAsyncCalls 等待队列
        ↓
  ④ 线程池执行 getResponseWithInterceptorChain()
        ↓
  ⑤ 回调到主线程：callback.onResponse() / callback.onFailure()
```

### 4. Dispatcher 调度器（并发控制）

Dispatcher 是 OkHttp 的并发控制中心，管理同步和异步请求。

#### 4.1 核心参数

| 参数 | 默认值 | 作用 |
|------|---------|------|
| `maxRequests` | 64 | 全局最大并发请求数 |
| `maxRequestsPerHost` | 5 | 同一 Host 最大并发数 |

#### 4.2 三个队列

```
readyAsyncCalls        → 等待执行的异步请求
runningAsyncCalls      → 正在执行的异步请求
runningSyncCalls       → 正在执行的同步请求（不受 maxRequests 限制）
```

#### 4.3 调度流程

```
新异步请求 enqueue()
        ↓
  检查 runningAsyncCalls.size < maxRequests
  且 同一 host 的并发 < maxRequestsPerHost
        ↓
  ├─ 满足 → 加入 runningAsyncCalls → executorService().execute()
  └─ 不满足 → 加入 readyAsyncCalls 等待
        ↓
  某个请求完成 finished()
        ↓
  从 runningAsyncCalls 移除
        ↓
  从 readyAsyncCalls 取出等待的请求 → 提升执行
```

#### 4.4 线程池配置

```kotlin
executorService = ThreadPoolExecutor(
    corePoolSize = 0,
    maximumPoolSize = Int.MAX_VALUE,  // 无上限，由 Dispatcher 控制
    keepAliveTime = 60L,
    unit = TimeUnit.SECONDS,
    workQueue = SynchronousQueue()    // 不缓存，直接交付
)
```

### 5. 拦截器链（核心重点）

OkHttp 的拦截器链是**责任链模式**的经典实现，每个拦截器负责一个职责。

#### 5.1 拦截器执行顺序

```
用户请求
    ↓
  ① 用户自定义 Interceptors（addInterceptor）
        添加公共 Header、日志记录、Token 注入等
    ↓
  ② RetryAndFollowUpInterceptor（重试与重定向）
        处理失败重试、3xx 重定向、认证挑战
    ↓
  ③ BridgeInterceptor（应用层与网络层桥接）
        添加 Host、Content-Type、Content-Length
        添加 Cookie、Accept-Encoding（Gzip）
        添加 User-Agent
    ↓
  ④ CacheInterceptor（缓存策略）
        检查缓存是否可用，可用则直接返回缓存响应
        否则继续执行，拿到响应后根据 Cache-Control 决定是否缓存
    ↓
  ⑤ ConnectInterceptor（建立连接）
        从 ConnectionPool 获取可用连接
        或创建新连接（TCP 握手 + TLS 握手）
    ↓
  ⑥ CallServerInterceptor（实际网络通信）
        向服务器发送请求头 + 请求体
        读取服务器响应头 + 响应体
    ↓
  响应返回（逐层向上）
```

#### 5.2 各拦截器详解

**RetryAndFollowUpInterceptor**：
- 处理请求失败时的重试（连接超时、路由失败等）
- 处理 3xx 重定向（自动跟随 Location）
- 处理 401 认证挑战（Authentication）
- 最大重试次数默认 20 次

**BridgeInterceptor**：
- 将用户构建的 Request 补充为完整的网络请求
- 添加必要的 Header（Host、Content-Type、Content-Length、Cookie 等）
- 处理 Gzip 压缩（添加 `Accept-Encoding: gzip`，自动解压）

**CacheInterceptor**：
- 根据请求的 Cache-Control 和缓存策略判断
- 缓存命中 → 直接返回缓存响应，不执行后续拦截器
- 缓存未命中 → 继续执行，拿到响应后根据策略存入缓存
- 支持 `Cache-Control: max-age`、`max-stale`、`no-cache` 等

**ConnectInterceptor**：
- 从 ConnectionPool 获取可复用的连接
- 或创建新连接（TCP 握手 + TLS 握手）
- 将连接封装为 HttpCodec（HTTP/1.1 或 HTTP/2）

**CallServerInterceptor**：
- 向服务器写入请求头 + 请求体
- 读取服务器响应头
- 读取服务器响应体
- 处理 100 Continue 等中间状态

### 6. 连接池（ConnectionPool）

连接池是 OkHttp 性能优化的核心，通过复用 TCP 连接避免重复握手。

#### 6.1 核心参数

| 参数 | 默认值 | 作用 |
|------|---------|------|
| `maxIdleConnections` | 5 | 最大空闲连接数 |
| `keepAliveDuration` | 5 分钟 | 空闲连接存活时间 |

#### 6.2 连接复用条件

两个请求能复用同一个连接，必须满足：
1. 相同的 Host + Port
2. 相同的 URL Scheme（http/https）
3. 相同的代理配置
4. 连接处于活跃状态且未超时

#### 6.3 连接清理机制

```
后台清理线程（cleanupRunnable）
        ↓
  定期遍历连接池
        ↓
  检查每个连接的 lastUseTime
        ↓
  空闲时间 > keepAliveDuration → 关闭连接
  空闲连接数 > maxIdleConnections → 关闭最早的空闲连接
```

#### 6.4 HTTP/2 多路复用

HTTP/2 支持在同一个 TCP 连接上并发多个请求/响应：
- 一个连接可以同时传输多个 Stream
- 避免了 HTTP/1.1 的队头阻塞问题
- OkHttp 自动协商 HTTP/2（通过 ALPN）

### 7. 缓存机制

OkHttp 的缓存基于 `DiskLruCache`，完全遵循 HTTP 缓存协议。

#### 7.1 缓存配置

```kotlin
val cache = Cache(
    directory = File(cacheDir, "http_cache"),
    maxSize = 50L * 1024 * 1024  // 50MB
)
val client = OkHttpClient.Builder()
    .cache(cache)
    .build()
```

#### 7.2 缓存判断流程

```
CacheInterceptor.intercept()
        ↓
  ① 从 Cache 中查找候选缓存响应
        ↓
  ② 无缓存 → 继续执行拦截器链，拿到响应后存入缓存
        ↓
  ③ 有缓存 → 检查缓存策略：
        ├─ Cache-Control: no-cache → 不使用缓存
        ├─ max-age 未过期 → 直接使用缓存
        ├─ max-stale 允许过期 → 使用过期缓存
        └─ 需要验证 → 发送条件请求（If-Modified-Since / If-None-Match）
                ├─ 304 Not Modified → 使用缓存
                └─ 200 OK → 使用新响应，更新缓存
```

#### 7.3 缓存 Key

缓存 Key 由请求的 URL + 请求方法组成，通过 DiskLruCache 的 Key 机制存储。

### 8. 连接建立流程

#### 8.1 TCP 连接

```
ConnectInterceptor
        ↓
  查找 ConnectionPool 中可复用连接
        ↓
  无可复用 → 创建新连接
        ↓
  RouteSelector.select() → 选择路由（IP + Port + 代理）
        ↓
  Socket 连接（TCP 三次握手）
        ↓
  如果是 HTTPS → TLS 握手
        ↓
  封装为 HttpCodec
```

#### 8.2 TLS 握手（HTTPS）

```
TLS 握手流程：
    1. Client Hello（支持的加密套件、TLS 版本）
    2. Server Hello（选定加密套件、TLS 版本、证书）
    3. 客户端验证证书（证书链 → CA 根证书）
    4. 密钥交换（RSA / ECDHE）
    5. 建立加密通道
```

### 9. 关键设计亮点

#### 9.1 责任链模式
- 每个拦截器职责单一，可独立测试和替换
- 用户可插入自定义拦截器，扩展性极强
- 拦截器顺序固定，行为可预测

#### 9.2 连接池复用
- 避免频繁 TCP 握手，大幅降低延迟
- 空闲连接自动清理，避免资源浪费
- 支持 HTTP/2 多路复用

#### 9.3 透明 Gzip 压缩
- BridgeInterceptor 自动添加 `Accept-Encoding: gzip`
- 自动解压 Gzip 响应，对上层透明
- 减少网络传输量

#### 9.4 自动重试与重定向
- 连接失败自动重试（最多 20 次）
- 3xx 自动跟随重定向
- 401 自动处理认证挑战

#### 9.5 响应缓存
- 完全遵循 HTTP 缓存协议
- 支持条件请求（If-Modified-Since / ETag）
- 磁盘缓存基于 DiskLruCache，线程安全

### 10. OkHttp 与 Retrofit 的关系

```
Retrofit（声明式 HTTP 框架）
    ├─ 动态代理 + 注解 → 将接口方法转换为 HTTP 请求
    ├─ Converter → 数据转换（JSON ↔ 对象）
    └─ CallAdapter → 返回类型适配（Call/RxJava/Coroutine）
        ↓
  OkHttp（HTTP 客户端）
    ├─ 拦截器链 → 请求处理
    ├─ 连接池 → TCP 复用
    ├─ 缓存 → 响应缓存
    └─ Dispatcher → 并发控制
        ↓
  网络层（Socket / TLS）
```

- Retrofit 负责 **API 声明与数据转换**
- OkHttp 负责 **网络通信与性能优化**
- 两者通过 `Call.Factory` 接口解耦

### 11. 主流网络请求框架对比

#### 11.1 综合对比表

| 维度 | OkHttp | Retrofit | Volley |
|------|--------|----------|--------|
| **定位** | 底层 HTTP 客户端 | 声明式 HTTP 接口框架（底层用 OkHttp） | 上层 HTTP 请求库 |
| **开发者** | Square | Square | Google |
| **API 风格** | 编程式（构建 Request/Response） | 声明式（接口 + 注解） | 编程式（RequestQueue + Request） |
| **数据转换** | 无（手动解析 ResponseBody） | 内置 Converter 体系（Gson/Moshi/Proto 等） | 内置 JSON 解析（JsonObjectRequest） |
| **缓存机制** | 完善（磁盘缓存 + HTTP 协议缓存） | 依赖 OkHttp 的缓存 | 内存缓存（无磁盘缓存） |
| **连接复用** | 内置连接池（HTTP Keep-Alive / HTTP/2 多路复用） | 通过 OkHttp 复用 | 无连接池，每次请求新建连接 |
| **协程支持** | 原生支持（suspend 函数通过 Call 封装） | 原生支持（CallAdapter 适配） | 不支持 |
| **文件上传/下载** | 原生支持（Multipart / Streaming） | 原生支持（@Multipart / @Streaming） | 支持但不够灵活 |
| **请求取消** | `Call.cancel()` 支持 | `Call.cancel()` + 协程取消自动传播 | `Request.cancel()` 支持 |
| **拦截器** | 完善的责任链拦截器体系 | 通过 OkHttp 拦截器 | 无拦截器机制 |
| **包体积** | ~400KB | ~200KB（+ OkHttp 依赖） | ~100KB |
| **维护状态** | 活跃维护 | 活跃维护 | **已停止维护**（官方推荐迁移到 OkHttp/Retrofit） |

#### 11.2 各框架核心特点

**OkHttp**：
- Android 事实标准的底层 HTTP 客户端，Retrofit 底层就是它
- 内置连接池、磁盘缓存、透明 Gzip、自动重试、HTTP/2 支持
- API 偏底层，需要手动构建 Request、解析 Response
- 适合需要精细控制网络行为的场景（如自定义协议、WebSocket）
- 几乎所有 Android 项目都直接或间接（通过 Retrofit）使用 OkHttp

**Retrofit**：
- 基于 OkHttp 的上层封装，通过动态代理 + 注解实现声明式 API
- 开发者只需定义接口 + 注解，无需写任何实现代码
- Converter 体系支持多种数据格式，CallAdapter 支持多种异步模型
- 与 Kotlin 协程天然契合，是目前最主流的网络请求方案
- 适合绝大多数项目的 RESTful API 调用场景

**Volley**：
- Google 出品，早期 Android 推荐的网络库，适合高频小请求
- 内置内存缓存，对图片加载有内置支持（ImageRequest）
- 缺点明显：无磁盘缓存、无连接池、不支持复杂请求（如大文件上传）
- **已停止维护**，Google 官方已迁移到 OkHttp/Retrofit
- 仅适合维护老项目，新项目不推荐

#### 11.3 选型建议

```
新项目？
    ├─ 是 → Retrofit + OkHttp（标准方案）
    └─ 否 → 老项目用的什么就继续用什么

需要 WebSocket / 自定义协议？
    ├─ 是 → 直接用 OkHttp
    └─ 否 → Retrofit + OkHttp

只是简单的图片加载 + 小数据请求？
    ├─ 是 → Volley 也能用（但不推荐，已停止维护）
    └─ 否 → Retrofit + OkHttp
```

> **结论**：现代 Android 开发中，**Retrofit + OkHttp** 是标准组合方案。Volley 已停止维护，不建议新项目使用。

## 六、Jetpack

> Android Jetpack 架构组件，提供生命周期感知的数据管理、UI 状态持有和生命周期分发能力。

### 1. LiveData

> **一句话总结**：内部通过 mVersion 版本号机制实现数据分发，Observer 的 mLastVersion < mVersion 时才回调；绑定 LifecycleOwner，只在 STARTED/RESUMED 活跃状态下分发，DESTROYED 时自动移除；新 Observer 订阅时因 mLastVersion 为初始值会立即收到最新值（粘性事件本质）。

#### 1. 核心架构

LiveData 是 Android Jetpack 提供的**可观察数据容器**，采用 **观察者模式 + 生命周期感知** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **LiveData** | 抽象基类，持有数据并管理观察者，感知生命周期 |
| **MutableLiveData** | LiveData 的可变子类，提供 `setValue()` / `postValue()` |
| **MediatorLiveData** | 聚合多个 LiveData 的数据源 |
| **Observer** | 观察者接口，接收数据变化回调 |
| **LifecycleOwner** | 生命周期持有者（Activity/Fragment） |
| **Lifecycle** | 生命周期状态管理 |

#### 2. 核心特性

| 特性 | 说明 |
|------|------|
| **生命周期感知** | 只在 Observer 处于 STARTED/RESUMED 状态时回调 |
| **自动取消订阅** | Observer 所在的 LifecycleOwner 被 DESTROYED 时自动移除 |
| **粘性事件** | 新 Observer 订阅时，会立即收到最新值（如果有的话） |
| **防倒灌** | Lifecycle 从 DESTROYED 回到 STARTED 时不会重复收到数据 |
| **线程安全** | `setValue()` 只能在主线程调用，`postValue()` 可在任意线程 |

#### 3. 核心数据结构

LiveData 内部维护了三个关键数据结构：

```kotlin
// LiveData 内部核心字段
private val mData: Any?              // 当前数据值
private val mObservers: SafeIterableMap<Observer<T>, ObserverWrapper>  // 观察者映射
private var mVersion: Int            // 数据版本号

// ObserverWrapper 内部关键字段
class ObserverWrapper(val observer: Observer<T>) {
    var mLastVersion: Int = INIT_VERSION  // 该观察者上次处理的版本号
    var mActive: Boolean = false          // 是否处于活跃状态
}
```

#### 4. setValue() 流程（主线程）

```
liveData.setValue(newValue)
        ↓
  ① 检查是否在主线程（非主线程抛异常）
        ↓
  ② mVersion++（版本号递增）
        ↓
  ③ mData = newValue（更新数据）
        ↓
  ④ 遍历 mObservers：
        ↓
  ⑤ 对每个 ObserverWrapper：
        ├─ 检查 mActive == true（是否处于活跃状态）
        ├─ 检查 shouldDispatch()：mVersion > mLastVersion
        │   （数据版本 > 观察者上次处理的版本 → 有新数据）
        └─ 满足条件 → 调用 observer.onChanged(mData)
                ↓
        更新 mLastVersion = mVersion
```

#### 5. postValue() 流程（任意线程）

```
liveData.postValue(newValue)
        ↓
  ① synchronized 加锁
        ↓
  ② 检查是否有待发送的数据（mData != null）
        ├─ 有 → 只更新 mData，不重复投递 Runnable
        └─ 无 → 更新 mData + 投递 Runnable 到主线程
        ↓
  ③ ArchTaskExecutor.getInstance().postToMainThread(postValueRunnable)
        ↓
  ④ 主线程执行 postValueRunnable：
        ↓
  ⑤ 取出 mData（加锁）
        ↓
  ⑥ 调用 setValue(data) → 走 setValue 流程
```

#### postValue 的丢值问题

```
连续调用 postValue("A") → postValue("B") → postValue("C")
        ↓
  第一次：mData = "A"，投递 Runnable
  第二次：mData = "B"，已有 Runnable，不重复投递
  第三次：mData = "C"，已有 Runnable，不重复投递
        ↓
  Runnable 执行时：取出的 mData = "C"
        ↓
  Observer 只会收到 "C"，"A" 和 "B" 被丢弃
```

**结论**：`postValue()` 连续调用时，中间值会丢失，只有最后一次值会被回调。

#### 6. 生命周期感知原理（核心重点）

##### 6.1 订阅流程

```
liveData.observe(lifecycleOwner, observer)
        ↓
  ① 检查当前 Lifecycle 状态是否为 DESTROYED → 是则直接返回
        ↓
  ② 创建 ObserverWrapper（包装 Observer）
        ↓
  ③ 将 ObserverWrapper 加入 mObservers
        ↓
  ④ 注册 LifecycleObserver 到 LifecycleOwner：
        lifecycleOwner.lifecycle.addObserver(observer)
        ↓
  ⑤ LifecycleObserver 监听状态变化：
        ├─ ON_CREATE / ON_START → 检查是否需要更新状态
        ├─ ON_RESUME → mActive = true → 分发最新值
        ├─ ON_PAUSE → mActive = false（停止分发）
        ├─ ON_STOP → mActive = false
        └─ ON_DESTROY → 移除 Observer → 自动取消订阅
```

##### 6.2 状态与分发规则

```
Lifecycle 状态：
  INITIALIZED → CREATED → STARTED → RESUMED
                                  ↓
                              [活跃状态，接收回调]
                                  ↓
                              PAUSED → STOPPED → DESTROYED
                              [非活跃状态，停止回调]
```

- **STARTED / RESUMED** → Observer 处于活跃状态，会收到数据变化回调
- **CREATED / DESTROYED** → Observer 处于非活跃状态，不会收到回调
- **DESTROYED** → Observer 被自动移除

##### 6.3 粘性事件原理

新 Observer 订阅时，会立即收到当前最新值（如果有的话）：

```
liveData.value = "Hello"  // mVersion = 1
        ↓
  此时新 Observer 订阅：
        ↓
  ObserverWrapper 的 mLastVersion = INIT_VERSION (-1)
        ↓
  检查：mVersion(1) > mLastVersion(-1) → true
        ↓
  立即回调 observer.onChanged("Hello")
        ↓
  更新 mLastVersion = 1
```

**这就是粘性事件的本质**：新 Observer 的 `mLastVersion` 是初始值，总是小于当前 `mVersion`，所以会立即收到最新值。

##### 6.4 配置变更（屏幕旋转）后的行为

```
屏幕旋转前：
  Activity 状态 RESUMED，LiveData 有值 "A"，mVersion = 1
  Observer.mLastVersion = 1
        ↓
  屏幕旋转 → Activity 重建
        ↓
  新 Activity 的 Lifecycle 状态：INITIALIZED → CREATED → STARTED → RESUMED
        ↓
  observe() 重新订阅，创建新的 ObserverWrapper
  新 ObserverWrapper.mLastVersion = INIT_VERSION (-1)
        ↓
  mVersion(1) > mLastVersion(-1) → true
        ↓
  立即收到 "A"（粘性事件）
```

#### 7. MediatorLiveData（多源聚合）

MediatorLiveData 可以观察多个 LiveData，并在任意源变化时回调：

```kotlin
val mediator = MediatorLiveData<String>()
mediator.addSource(liveData1) { value ->
    // liveData1 变化时回调
    mediator.value = "source1: $value"
}
mediator.addSource(liveData2) { value ->
    // liveData2 变化时回调
    mediator.value = "source2: $value"
}
```

#### 内部实现

```
addSource(liveData, observer)
        ↓
  创建 Source（包装 liveData + observer）
        ↓
  将 Source 加入 mSources
        ↓
  调用 liveData.observeForever(source.plug)
        ↓
  任意源变化 → plug 被回调 → 转发给 observer
```

#### 8. LiveData 与 Flow 对比

| 维度 | LiveData | Flow |
|------|----------|------|
| **生命周期感知** | 原生支持 | 需配合 `flowWithLifecycle()` |
| **线程切换** | 不支持（只能在主线程观察） | 原生支持（`flowOn()`） |
| **操作符** | 很少（map/switchMap/mediator） | 丰富（map/filter/flatMap/combine 等） |
| **粘性事件** | 有（新观察者立即收到最新值） | 无（默认冷流，从头开始） |
| **背压** | 不支持 | 支持（buffer/conflate/collectLatest） |
| **协程集成** | 不支持 | 原生支持（suspend 函数） |
| **多数据源聚合** | MediatorLiveData | combine/zip/merge |
| **适用场景** | UI 层简单数据观察 | 复杂数据流、异步操作 |

#### 9. 关键设计亮点

##### 9.1 生命周期感知
- 自动在合适的生命周期状态下分发/停止分发
- 自动在 DESTROYED 时移除观察者，避免内存泄漏

##### 9.2 版本号机制
- 每次 `setValue()` 都会递增 `mVersion`
- Observer 通过 `mLastVersion` 记录上次处理的版本
- 避免重复分发同一数据

##### 9.3 线程安全
- `setValue()` 强制主线程，避免并发问题
- `postValue()` 通过 synchronized + Handler 保证线程安全

##### 9.4 与 ViewModel 的完美配合
- ViewModel 在配置变更（屏幕旋转）时存活
- LiveData 持有数据，ViewModel 重建后自动恢复
- Observer 重新订阅后自动收到最新值（粘性事件）

#### 10. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 避免粘性事件 | 使用 `SingleLiveEvent` 封装一次性事件（如 Toast、导航） |
| postValue 丢值 | 避免连续快速调用 `postValue()`，改用 `setValue()` 或 Flow |
| 内存泄漏 | 始终使用 `observe(owner, observer)` 而非 `observeForever()` |
| 复杂数据流 | 考虑迁移到 Flow，获得更丰富的操作符和协程支持 |
| 多线程场景 | 使用 `postValue()` 或 Flow 的 `flowOn()` 切换线程 |
| 数据转换 | 使用 `Transformations.map()` / `switchMap()` 避免手动转换 |
| 多数据源 | 使用 `MediatorLiveData` 聚合多个数据源 |
| 单元测试 | LiveData 可直接 `getValue()` 测试，无需 Mock 观察者 |

### 2. ViewModel

> **一句话总结**：屏幕旋转时通过 Activity.onRetainNonConfigurationInstance() 将 ViewModelStore 保存到 NonConfigurationInstances，新 Activity 创建时从 ActivityThread 恢复同一个 ViewModelStore，数据全部保留；真正 finish() 时才调 onCleared() 释放，同一 Owner 中同类型 ViewModel 单例。

#### 1. 核心架构

ViewModel 是 Android Jetpack 提供的**生命周期感知数据持有组件**，核心设计目标是在配置变更（屏幕旋转）时存活，核心类职责如下：

| 类 | 职责 |
|---|---|
| **ViewModel** | 抽象基类，持有 UI 数据，配置变更时存活 |
| **ViewModelStore** | 存储 ViewModel 实例的容器（内部 HashMap） |
| **ViewModelProvider** | 创建/获取 ViewModel 的入口 |
| **ViewModelProvider.Factory** | ViewModel 工厂，负责创建 ViewModel 实例 |
| **ViewModelStoreOwner** | 持有 ViewModelStore 的接口（Activity/Fragment 实现） |
| **NonConfigurationInstances** | Activity 内部类，用于跨配置变更保留数据 |
| **FragmentHostCallback** | Fragment 管理中 ViewModelStore 的传递媒介 |

#### 2. 核心特性

| 特性 | 说明 |
|------|------|
| **配置变更存活** | 屏幕旋转时 ViewModel 不会被销毁，数据保留 |
| **生命周期绑定** | Activity/Fragment 真正销毁时（finish）自动调用 `onCleared()` |
| **单例作用域** | 同一 ViewModelStoreOwner 中同一类型 ViewModel 只创建一个 |
| **与 UI 解耦** | ViewModel 不持有 Activity/View 引用，避免内存泄漏 |
| **支持工厂模式** | 通过 Factory 传入依赖，支持依赖注入 |

#### 3. ViewModel 存活原理（核心重点）

##### 3.1 Activity 配置变更时的保留机制

```
Activity 配置变更（如屏幕旋转）：
        ↓
  Activity.onRetainNonConfigurationInstance()
        ↓
  ① 取出 ViewModelStore：mViewModelStore
        ↓
  ② 创建 NonConfigurationInstances 对象：
        NonConfigurationInstances {
            custom = onRetainCustomNonConfigurationInstance(),
            viewModelStore = mViewModelStore  // ← 关键：保留 ViewModelStore
        }
        ↓
  ③ 返回 NonConfigurationInstances，由 ActivityThread 保存
        ↓
  新 Activity 创建：
        ↓
  Activity.attach()
        ↓
  ④ 从 ActivityThread 获取上次保存的 NonConfigurationInstances
        ↓
  ⑤ 恢复 mViewModelStore = nc.viewModelStore
        ↓
  结果：新 Activity 拿到的是同一个 ViewModelStore
  → 其中的 ViewModel 数据全部保留
```

##### 3.2 真正销毁时的清理

```
Activity.finish() 或用户手动销毁：
        ↓
  onDestroy()
        ↓
  检查 isChangingConfigurations()
        ├─ true（配置变更）→ 不清理 ViewModelStore
        └─ false（真正销毁）→ 清理 ViewModelStore
                ↓
        ViewModelStore.clear()
                ↓
        遍历所有 ViewModel，调用 onCleared()
                ↓
        清空 HashMap，释放引用
```

##### 3.3 流程图

```
屏幕旋转：
  旧 Activity → onRetainNonConfigurationInstance()
                    ↓
              保存 ViewModelStore 到 NonConfigurationInstances
                    ↓
              旧 Activity 销毁（但 ViewModelStore 被保留）
                    ↓
  新 Activity → attach() → 恢复 ViewModelStore
                    ↓
              ViewModel 数据全部保留

真正 finish()：
  Activity → onDestroy() → isChangingConfigurations() = false
                    ↓
              ViewModelStore.clear() → onCleared() → 释放
```

#### 4. ViewModelProvider 创建流程

```kotlin

// 或使用 by viewModels() 委托
val viewModel: MyViewModel by viewModels()
```

#### 内部流程

```
ViewModelProvider(owner).get(MyViewModel::class.java)
        ↓
  ① 从 owner 获取 ViewModelStore：
        owner.getViewModelStore()  // Activity/Fragment 实现 ViewModelStoreOwner
        ↓
  ② 从 ViewModelStore 中查找：
        store.get(key)  // key = "androidx.lifecycle.ViewModelProvider.DefaultKey:MyViewModel"
        ↓
  ③ 已存在 → 直接返回（单例）
        ↓
  ④ 不存在 → 通过 Factory 创建：
        Factory.create(MyViewModel::class.java)
        ↓
  ⑤ 存入 ViewModelStore：

        ↓

```

#### Factory 体系

#### 6. ViewModel 与 onSaveInstanceState 对比

| 维度 | ViewModel | onSaveInstanceState |
|------|-----------|-------------------|
| **存储位置** | 内存 | 磁盘（Bundle） |
| **数据类型** | 任意对象 | 只能存 Parcelable/Serializable |
| **数据量** | 无限制 | 有限制（Bundle 大小限制，约 1MB） |
| **生命周期** | 配置变更存活，进程死亡丢失 | 配置变更 + 进程死亡都存活 |
| **适用场景** | UI 状态、数据缓存、业务逻辑 | 少量关键状态（滚动位置、选中标签） |
| **性能** | 快（内存引用） | 慢（序列化/反序列化） |

**最佳实践**：ViewModel 存大量数据 + onSaveInstanceState 存少量关键状态，两者配合使用。

#### 7. ViewModel 的生命周期

```
Activity.onCreate()
        ↓
  ViewModel 创建（首次）
        ↓
  Activity.onStart() → onResume() → 使用中
        ↓
  屏幕旋转 → Activity 销毁 → 新 Activity 创建
        ↓
  ViewModel 存活（不重新创建，数据保留）
        ↓
  Activity.finish()
        ↓
  ViewModel.onCleared() → 释放资源
        ↓
  ViewModel 销毁
```

#### onCleared() 的作用

```kotlin
class MyViewModel : ViewModel() {
    private val disposable = CompositeDisposable()

    override fun onCleared() {
        super.onCleared()
        disposable.clear()  // 清理 RxJava 订阅
        // 释放其他资源
    }
}
```

#### 8. ViewModel 为什么不能持有 View 引用

```
错误示例：
class MyViewModel(val textView: TextView) : ViewModel()  // ❌

原因：
  1. Activity 配置变更时，旧 Activity 销毁，但 ViewModel 存活
  2. ViewModel 持有旧 Activity 的 TextView 引用
  3. 旧 Activity 无法被 GC 回收 → 内存泄漏
  4. 新 Activity 有新的 TextView，旧引用已失效

正确做法：
  - ViewModel 只持有数据（LiveData/Flow）
  - Activity/Fragment 观察数据，更新自己的 View
```

#### 9. 关键设计亮点

##### 9.1 NonConfigurationInstances 保留机制
- 利用 Activity 框架提供的 `onRetainNonConfigurationInstance()` 钩子
- 系统级保留，不依赖任何生命周期回调
- 比 `onSaveInstanceState` 更高效（内存引用 vs 序列化）

##### 9.2 ViewModelStore 单例管理
- 同一 Owner 中同一类型 ViewModel 只创建一个
- 通过 HashMap + Key 保证单例语义
- 真正销毁时统一调用 `onCleared()` 清理

##### 9.3 Factory 模式
- 支持自定义创建逻辑，方便依赖注入
- 内置 `AndroidViewModelFactory` 支持 Application 参数
- 可与 Hilt/Dagger 集成

##### 9.4 与 LiveData/Flow 的天然配合
- ViewModel 持有 LiveData/Flow 数据源
- Activity/Fragment 观察数据，自动更新 UI
- 配置变更后 Observer 重新订阅，自动收到最新数据

#### 10. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 避免内存泄漏 | ViewModel 不持有 Activity/View 引用 |
| 依赖注入 | 自定义 `ViewModelProvider.Factory` 传入 Repository |
| 协程作用域 | 使用 `viewModelScope` 自动跟随 ViewModel 生命周期取消 |
| 进程死亡恢复 | 配合 `SavedStateHandle` 保存关键状态 |
| Fragment 共享 | 使用 `activityViewModels()` 实现 Fragment 间数据共享 |
| 避免重复创建 | 使用 `by viewModels()` 委托确保单例 |
| 清理资源 | 重写 `onCleared()` 释放订阅、关闭连接 |
| 单元测试 | ViewModel 不依赖 Android 框架，可直接单元测试 |

### 3. Lifecycle

> **一句话总结**：核心是 LifecycleRegistry 状态机，通过 handleLifecycleEvent() 驱动状态变化并分发事件给所有观察者；Activity 通过注入 ReportFragment（或直接回调）将生命周期映射到 Lifecycle 状态；新观察者加入时自动同步状态（从 INITIALIZED 逐步推进到当前状态）。

#### 1. 核心架构

Lifecycle 是 Android Jetpack 提供的**生命周期感知组件**，是 LiveData、ViewModel 等组件的基础，采用 **观察者模式 + 状态机** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **Lifecycle** | 抽象基类，定义生命周期状态和事件 |
| **LifecycleOwner** | 接口，持有 Lifecycle 对象（Activity/Fragment 实现） |
| **LifecycleObserver** | 观察者接口，监听生命周期变化 |
| **LifecycleEventObserver** | 事件观察者接口，接收具体事件 |
| **DefaultLifecycleObserver** | 默认生命周期观察者，提供 ON_CREATE/ON_START 等回调方法 |
| **LifecycleRegistry** | Lifecycle 的实现类，负责状态管理和事件分发 |
| **ReportFragment** | 注入到 Activity 中的无 UI Fragment，驱动 Lifecycle 状态变化 |

#### 2. 状态与事件模型

##### 2.1 状态（State）

```
INITIALIZED → CREATED → STARTED → RESUMED
                                    ↓
                                [活跃状态]
                                    ↓
                              PAUSED → STOPPED → DESTROYED
```

| 状态 | 含义 |
|------|------|
| `INITIALIZED` | LifecycleOwner 已创建，但尚未收到 ON_CREATE |
| `CREATED` | 已创建（onCreate 后） |
| `STARTED` | 已启动（onStart 后） |
| `RESUMED` | 已恢复（onResume 后，可交互） |
| `DESTROYED` | 已销毁（onDestroy 后） |

##### 2.2 事件（Event）

| 事件 | 对应回调 | 状态变化 |
|------|----------|----------|
| `ON_CREATE` | onCreate | INITIALIZED → CREATED |
| `ON_START` | onStart | CREATED → STARTED |
| `ON_RESUME` | onResume | STARTED → RESUMED |
| `ON_PAUSE` | onPause | RESUMED → STARTED |
| `ON_STOP` | onStop | STARTED → CREATED |
| `ON_DESTROY` | onDestroy | CREATED → DESTROYED |
| `ON_ANY` | 任意事件 | 任意状态变化 |

#### 3. Lifecycle 与 Activity 的绑定原理

##### 3.1 ComponentActivity 的实现

```kotlin
class ComponentActivity : Activity(), LifecycleOwner {
    private val mLifecycleRegistry = LifecycleRegistry(this)

    override val lifecycle: Lifecycle
        get() = mLifecycleRegistry

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // 注入 ReportFragment 驱动 Lifecycle
        ReportFragment.injectIfNeededIn(this)
        mLifecycleRegistry.handleLifecycleEvent(Event.ON_CREATE)
    }

    override fun onStart() {
        super.onStart()
        mLifecycleRegistry.handleLifecycleEvent(Event.ON_START)
    }

    override fun onResume() {
        super.onResume()
        mLifecycleRegistry.handleLifecycleEvent(Event.ON_RESUME)
    }

    // onPause/onStop/onDestroy 同理
}
```

##### 3.2 ReportFragment 的作用

```
ReportFragment.injectIfNeededIn(activity)
        ↓
  向 Activity 注入一个无 UI 的 Fragment
        ↓
  Fragment 的生命周期回调 → 驱动 LifecycleRegistry 状态变化
        ↓
  Fragment.onResume() → handleLifecycleEvent(ON_RESUME)
  Fragment.onPause() → handleLifecycleEvent(ON_PAUSE)
  ...
```

**为什么需要 ReportFragment？**
- 在早期版本中，Activity 的生命周期回调顺序不确定
- ReportFragment 的回调在 Activity 回调**之后**执行，保证状态一致性
- 新版本中已直接在 Activity 回调中处理，ReportFragment 作为兼容方案

#### 4. LifecycleRegistry 状态机（核心重点）

LifecycleRegistry 是 Lifecycle 的核心实现，负责状态管理和事件分发。

##### 4.1 handleLifecycleEvent()

```
lifecycleRegistry.handleLifecycleEvent(event)
        ↓
  ① 根据 Event 计算新的 State：
        ON_CREATE → CREATED
        ON_START → STARTED
        ON_RESUME → RESUMED
        ON_PAUSE → CREATED
        ON_STOP → CREATED
        ON_DESTROY → DESTROYED
        ↓
  ② 更新当前状态：mState = newState
        ↓
  ③ 同步分发事件给所有观察者：sync()
```

##### 4.2 sync() 分发逻辑

```
sync()
        ↓
  遍历所有观察者（mObserverMap）
        ↓
  对每个观察者：
        ├─ 计算观察者当前状态 vs Lifecycle 当前状态
        ├─ 如果观察者状态 < Lifecycle 状态 → 向前推进（ON_CREATE → ON_START → ...）
        ├─ 如果观察者状态 > Lifecycle 状态 → 向后回退（ON_DESTROY → ON_STOP → ...）
        └─ 如果状态相同 → 不处理
```

##### 4.3 观察者状态同步

```
观察者状态同步示例：

Lifecycle 当前状态：RESUMED
新观察者加入，初始状态：INITIALIZED
        ↓
  sync() 发现观察者状态 < Lifecycle 状态
        ↓
  依次分发：
    ON_CREATE → 观察者状态变为 CREATED
    ON_START → 观察者状态变为 STARTED
    ON_RESUME → 观察者状态变为 RESUMED
        ↓
  观察者状态追上 Lifecycle 状态，同步完成
```

#### 5. 观察者注册流程

```kotlin
lifecycle.addObserver(object : DefaultLifecycleObserver {
    override fun onResume(owner: LifecycleOwner) { }
    override fun onPause(owner: LifecycleOwner) { }
})
```

#### 内部流程

```
lifecycle.addObserver(observer)
        ↓
  ① 创建 ObserverWithState（包装观察者 + 初始状态）
        ↓
  ② 将 observer → ObserverWithState 存入 mObserverMap
        ↓
  ③ 获取当前 Lifecycle 状态
        ↓
  ④ 同步分发事件给新观察者（使其状态追上当前状态）
        ↓
  ⑤ 如果 Lifecycle 已经是 DESTROYED → 直接移除观察者
```

#### 6. 自动销毁机制

```
Lifecycle 状态变为 DESTROYED 时：
        ↓
  ① 分发 ON_DESTROY 给所有观察者
        ↓
  ② 清空 mObserverMap（移除所有观察者）
        ↓
  ③ 后续 addObserver() 调用会被忽略（因为已 DESTROYED）
```

#### 7. Lifecycle 与 LiveData 的协作

Lifecycle 是 LiveData 生命周期感知的底层基础：

```
liveData.observe(lifecycleOwner, observer)
        ↓
  ① 创建 LifecycleBoundObserver（包装 Observer）
        ↓
  ② 注册到 Lifecycle：
        lifecycleOwner.lifecycle.addObserver(boundObserver)
        ↓
  ③ LifecycleBoundObserver 监听状态变化：
        ├─ ON_RESUME → mActive = true → 开始分发数据
        ├─ ON_PAUSE → mActive = false → 停止分发
        ├─ ON_DESTROY → 移除 Observer → 自动取消订阅
        └─ 其他状态 → 更新 mActive 状态
```

#### 8. ProcessLifecycleOwner（应用级生命周期）

ProcessLifecycleOwner 提供**应用进程级别**的生命周期感知：

```kotlin
ProcessLifecycleOwner.get().lifecycle.addObserver(
    object : DefaultLifecycleObserver {
        override fun onResume(owner: LifecycleOwner) {
            // 应用进入前台
        }
        override fun onPause(owner: LifecycleOwner) {
            // 应用进入后台
        }
    }
)
```

#### 原理

```
ProcessLifecycleOwner 内部：
        ↓
  监听所有 Activity 的生命周期
        ↓
  应用进入前台（任意 Activity onResume）→ ON_RESUME
  应用进入后台（所有 Activity onStop）→ ON_PAUSE
        ↓
  延迟判断：
    进入后台时延迟 ~700ms 再分发 ON_PAUSE
    避免 Activity 切换时的误判
```

#### 9. 关键设计亮点

##### 9.1 状态机模型
- LifecycleRegistry 内部维护状态机，保证状态转换的正确性
- 新观察者加入时自动同步到当前状态，不会漏掉事件

##### 9.2 观察者状态独立追踪
- 每个观察者有自己的状态记录（ObserverWithState）
- 不同观察者可以处于不同状态，独立分发

##### 9.3 自动清理
- DESTROYED 时自动移除所有观察者，避免内存泄漏
- 与 ViewModel 配合，实现完整的生命周期管理

##### 9.4 应用级生命周期
- ProcessLifecycleOwner 提供进程级生命周期感知
- 可用于全局前后台切换监听

#### 10. Lifecycle 组件协作全景图

```
Lifecycle（生命周期感知基础）
    ├─→ LiveData（观察数据时感知生命周期）
    ├─→ ViewModel（生命周期存活）
    ├─→ LifecycleObserver（自定义生命周期感知组件）
    ├─→ ProcessLifecycleOwner（应用级前后台感知）
    └─→ WorkManager / DataBinding 等（底层均依赖 Lifecycle）
```

#### 11. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 避免内存泄漏 | 使用 `DefaultLifecycleObserver` 而非手动注册 |
| 前后台监听 | 使用 `ProcessLifecycleOwner` 而非 Activity 计数 |
| 自定义组件 | 实现 `LifecycleObserver` 让组件自动感知生命周期 |
| 协程集成 | 使用 `lifecycleScope` 自动跟随 Activity 生命周期取消 |
| 避免重复注册 | Lifecycle 已 DESTROYED 后 addObserver 会被忽略 |
| 状态同步 | 新观察者加入时会自动同步到当前状态，无需手动处理 |
| 与 Flow 集成 | 使用 `flowWithLifecycle()` 替代 `observeForever()` |

## 七、Handler 消息机制

> **一句话总结**：典型的生产者-消费者模式——Handler 发送 Message 到 MessageQueue（按时间排序的单链表），Looper 通过 loop() 死循环从队列取消息并分发回 Handler 处理，ThreadLocal 保证每个线程只有一个 Looper，空闲时通过 epoll 机制休眠不占 CPU。

### 1. 核心架构

Handler 消息机制是 Android 线程间通信的基础，采用 **生产者-消费者模式** 设计，核心类职责如下：

| 类 | 职责 |
|---|---|
| **Handler** | 消息的生产者与消费者，发送和处理 Message |
| **Message** | 消息载体，封装数据和目标 Handler 引用 |
| **MessageQueue** | 消息队列，按时间顺序存储待处理的消息（单链表） |
| **Looper** | 消息循环，不断从 MessageQueue 中取出消息并分发 |
| **ThreadLocal** | 线程本地存储，保证每个线程只有一个 Looper |

### 2. 四大组件关系

```
Thread
    ↓
  ThreadLocal<Looper> → 保证每个线程只有一个 Looper
    ↓
  Looper
    ├─ MessageQueue（消息队列）
    │     └─ Message → Message → Message → ...（单链表）
    └─ loop() 死循环
          ↓
        取出 Message
          ↓
        Message.target.dispatchMessage(msg)
          ↓
        Handler 处理消息
```

### 3. 完整工作流程

#### 3.1 初始化流程

```
// 主线程（ActivityThread）
Looper.prepareMainLooper()  // 创建主线程 Looper
        ↓
  ① new Looper(quitAllowed = false)  // 主线程 Looper 不可退出
        ├─ MessageQueue = new MessageQueue()
        └─ Thread = Thread.currentThread()
        ↓
  ② ThreadLocal.set(looper)  // 存入 ThreadLocal
        ↓
  ③ sMainThreadLooper = looper  // 保存主线程 Looper 引用

// 子线程
Looper.prepare()  // 创建子线程 Looper
        ↓
  ① 检查 ThreadLocal 是否已有 Looper（有则抛异常）
  ② new Looper(quitAllowed = true)  // 子线程 Looper 可退出
  ③ ThreadLocal.set(looper)

// 创建 Handler
val handler = object : Handler(Looper.myLooper() ?: Looper.getMainLooper()) {
    override fun handleMessage(msg: Message) {
        // 处理消息
    }
}
```

#### 3.2 消息发送流程

```
handler.sendMessage(msg)
        ↓
  ① msg.target = this  // 将 Handler 设置为 Message 的 target
        ↓
  ② MessageQueue.enqueueMessage(msg, when)
        ├─ 按 when 时间插入到单链表的合适位置
        └─ 如果需要唤醒 → 调用 nativeWake() 唤醒 Looper
        ↓
  ③ Looper.loop() 被唤醒
```

#### 3.3 消息循环与分发流程

```
Looper.loop()  // 死循环
        ↓
  ① MessageQueue.next() → 取出下一条消息
        ├─ 有消息 → 返回 Message
        └─ 无消息 → nativePollOnce() 阻塞等待
        ↓
  ② msg.target.dispatchMessage(msg)
        ↓
  ③ Handler.dispatchMessage(msg)
        ├─ msg.callback != null → callback.run()（Runnable 消息）
        ├─ mHandler.mCallback != null → mCallback.handleMessage(msg)
        └─ 否则 → this.handleMessage(msg)（重写的方法）
        ↓
  ④ msg.recycleUnchecked() → 回收 Message 到对象池
        ↓
  ⑤ 回到 ①，继续循环
```

### 4. MessageQueue 详解

#### 4.1 数据结构

MessageQueue 内部是一个**按时间排序的单链表**：

```
MessageQueue
    └─ mMessages → Message(when=100) → Message(when=200) → Message(when=300) → null
```

#### 4.2 enqueueMessage() 插入逻辑

```
enqueueMessage(msg, when)
        ↓
  ① synchronized(this) 加锁
        ↓
  ② 如果队列空 或 when < mMessages.when：
        → 插入到头部
        ↓
  ③ 否则，遍历链表找到合适位置：
        → 找到第一个 when > msg.when 的节点
        → 插入到该节点之前
        ↓
  ④ 如果插入到头部 或 needWake：
        → nativeWake() 唤醒 Looper
```

#### 4.3 next() 取出逻辑

```
next()
        ↓
  ① nativePollOnce(timeout) → 阻塞等待（epoll 机制）
        ↓
  ② 有消息且 when <= 当前时间：
        → 从链表中移除并返回
        ↓
  ③ 有消息但 when > 当前时间：
        → 计算等待时间，继续 nativePollOnce
        ↓
  ④ 无消息：
        → nativePollOnce(-1) 无限阻塞
```

### 5. Looper.loop() 详解

```kotlin
// 简化版源码
public static void loop() {
    final Looper me = myLooper();
    final MessageQueue queue = me.mQueue;

    for (;;) {  // 死循环
        Message msg = queue.next(); // 可能阻塞
        if (msg == null) return;    // Looper 退出

        msg.target.dispatchMessage(msg);  // 分发

        msg.recycleUnchecked();  // 回收
    }
}
```

**关键点**：
- `loop()` 是死循环，为什么不会 ANR？
  - 没有消息时通过 `nativePollOnce()` 进入休眠（epoll 机制）
  - 不占用 CPU，有消息时被唤醒
  - ANR 是因为消息处理耗时，不是因为 loop 死循环

### 6. 主线程为什么不需要 Looper.prepare()

```
ActivityThread.main()  // 应用入口
        ↓
  Looper.prepareMainLooper()  // 创建主线程 Looper
        ↓
  ActivityThread 创建 → Application.onCreate() → Activity 生命周期
        ↓
  Looper.loop()  // 开始主线程消息循环
        ↓
  所有 UI 事件、生命周期回调、Handler 消息都在这里处理
```

### 7. 子线程使用 Handler 的步骤

```kotlin
val thread = Thread {
    Looper.prepare()  // ① 准备 Looper
    val handler = object : Handler(Looper.myLooper()!!) {
        override fun handleMessage(msg: Message) {
            // 在子线程处理消息
        }
    }
    Looper.loop()  // ② 开始循环（会阻塞）
}
thread.start()
```

### 8. Handler 内存泄漏问题

#### 8.1 泄漏原因

```
非静态内部类 Handler
    ↓
  持有外部类（Activity）的引用
        ↓
  Message.target = Handler
        ↓
  Message 在 MessageQueue 中等待处理
        ↓
  MessageQueue 持有 Message → Message 持有 Handler → Handler 持有 Activity
        ↓
  Activity 无法被 GC 回收 → 内存泄漏
```

#### 8.2 解决方案

```kotlin
// 方案 1：静态内部类 + 弱引用
class MyActivity : AppCompatActivity() {
    private class SafeHandler(activity: MyActivity) : Handler(Looper.getMainLooper()) {
        private val activityRef = WeakReference(activity)

        override fun handleMessage(msg: Message) {
            val activity = activityRef.get() ?: return
            // 处理消息
        }
    }

    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacksAndMessages(null)  // 清空消息队列
    }
}
```

### 9. HandlerThread

HandlerThread 是封装了 Looper 的线程类：

```kotlin
val handlerThread = HandlerThread("worker")
handlerThread.start()  // 内部自动调用 Looper.prepare() + Looper.loop()

val handler = Handler(handlerThread.looper)
handler.post { /* 在 HandlerThread 中执行 */ }

// 用完记得退出
handlerThread.quitSafely()
```

#### 内部实现

```kotlin
public class HandlerThread : Thread {
    override fun run() {
        Looper.prepare()
        synchronized(this) {
            mLooper = Looper.myLooper()
            notifyAll()  // 通知等待者 Looper 已就绪
        }
        Looper.loop()
    }

    public fun getLooper(): Looper {
        if (!isAlive) return null
        synchronized(this) {
            while (isAlive && mLooper == null) {
                wait()  // 等待 Looper 就绪
            }
        }
        return mLooper
    }
}
```

### 10. 同步屏障（Sync Barrier）

同步屏障用于保证某些消息（如 UI 绘制）优先执行：

```
// 发送屏障消息
MessageQueue.postSyncBarrier()
        ↓
  插入一个 target == null 的特殊 Message
        ↓
  后续 next() 时：
    遇到屏障消息 → 只处理异步消息（跳过普通消息）
    屏障移除后 → 恢复正常顺序
```

**应用场景**：
- View.invalidate() 触发重绘时，通过屏障保证绘制消息优先执行
- 避免普通消息延迟绘制

### 11. Message 对象池

Message 使用对象池避免频繁创建：

```
Message.obtain() / Handler.obtainMessage()
        ↓
  从对象池（sPool）中取出复用
        ↓
  使用完毕后 → msg.recycleUnchecked()
        ↓
  归还到对象池（链表头部插入）
```

- 对象池最大长度：**50**
- 通过链表实现，`next` 指针串联
- 避免频繁 GC

### 12. 关键设计亮点

#### 12.1 生产者-消费者模式
- Handler 是生产者（发送消息）和消费者（处理消息）
- MessageQueue 是缓冲区
- Looper 是调度器

#### 12.2 epoll 机制
- 底层使用 Linux epoll 实现消息等待/唤醒
- 无消息时线程休眠，不占用 CPU
- 有消息时通过 nativeWake() 唤醒

#### 12.3 单链表消息队列
- 按时间排序的单链表
- 插入 O(n)，但实际中 n 通常很小
- 内存连续，缓存友好

#### 12.4 ThreadLocal 保证线程安全
- 每个线程的 Looper 存储在 ThreadLocal 中
- 保证每个线程只有一个 Looper
- 线程间隔离，互不干扰

### 13. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 避免内存泄漏 | 使用静态内部类 + 弱引用，onDestroy 清空消息 |
| 复用 Message | 使用 `Message.obtain()` 而非 `new Message()` |
| 子线程通信 | 使用 `HandlerThread` 避免手动管理 Looper |
| 延迟消息 | 使用 `sendMessageDelayed()` 而非 Thread.sleep |
| 批量操作 | 使用 `post(Runnable)` 而非多次 sendMessage |
| 及时清理 | 不需要时调用 `removeCallbacksAndMessages(null)` |
| 避免主线程阻塞 | 耗时操作放到子线程，结果通过 Handler 回传 |
| 同步屏障 | 谨慎使用，确保屏障被正确移除 |

## 八、ThreadLocal

> **一句话总结**：每个 Thread 内部持有独立的 ThreadLocalMap（Entry 的 key 是 ThreadLocal 弱引用，value 是值副本），set/get 操作都是操作当前线程自己的 Map，实现线程间数据隔离，空间换时间避免加锁。

### 1. 核心概念

ThreadLocal 是 Java 提供的**线程本地存储**机制，每个线程都有自己独立的变量副本，线程间互不影响。

| 特性 | 说明 |
|------|------|
| **线程隔离** | 每个线程拥有独立的变量副本 |
| **无锁并发** | 不需要加锁，每个线程操作自己的数据 |
| **空间换时间** | 用内存空间换取线程安全 |

### 2. 核心数据结构

```
Thread
    └─ ThreadLocalMap threadLocals = null
              ↓
        ThreadLocalMap（内部类）
            └─ Entry[] table
                    ↓
              Entry（继承 WeakReference<ThreadLocal<?>>）
                  ├─ key: ThreadLocal 对象（弱引用）
                  └─ value: 存储的值
```

**关键点**：
- ThreadLocalMap 存储在 **Thread** 对象中，而不是 ThreadLocal 中
- 每个 Thread 有自己的 ThreadLocalMap
- Entry 的 key 是 ThreadLocal 对象的**弱引用**

### 3. 核心 API

```kotlin
val threadLocal = ThreadLocal<String>()

// 设置值（当前线程）
threadLocal.set("hello")

// 获取值（当前线程）
val value = threadLocal.get()  // "hello"

// 移除值（防止内存泄漏）
threadLocal.remove()
```

### 4. set() 流程

```
threadLocal.set(value)
        ↓
  ① 获取当前线程：Thread t = Thread.currentThread()
        ↓
  ② 获取线程的 ThreadLocalMap：t.threadLocals
        ↓
  ③ 如果 map 不为 null：
        → map.set(this, value)
          ├─ 遍历 table，找到 key == this 的 Entry → 更新 value
          └─ 没找到 → createEntry(this, value)  // 新建 Entry
        ↓
  ④ 如果 map 为 null：
        → createMap(t, value)
          └─ t.threadLocals = new ThreadLocalMap(this, value)
```

### 5. get() 流程

```
threadLocal.get()
        ↓
  ① 获取当前线程：Thread t = Thread.currentThread()
        ↓
  ② 获取线程的 ThreadLocalMap：t.threadLocals
        ↓
  ③ 如果 map 不为 null：
        → map.getEntry(this)
          ├─ 遍历 table，找到 key == this 的 Entry → 返回 value
          └─ 没找到 → setInitialValue()  // 返回初始值（默认 null）
        ↓
  ④ 如果 map 为 null：
        → setInitialValue()  // 返回初始值
```

### 6. remove() 流程

```
threadLocal.remove()
        ↓
  ① 获取当前线程的 ThreadLocalMap
        ↓
  ② 如果 map 不为 null：
        → map.remove(this)
          └─ 遍历 table，找到 key == this 的 Entry → 清除
```

**重要**：线程池场景下必须调用 `remove()`，否则线程复用时会导致数据混乱。

### 7. 内存泄漏问题

#### 7.1 泄漏原因

```
ThreadLocalMap.Entry 的 key 是 ThreadLocal 的弱引用
        ↓
  如果 ThreadLocal 对象没有外部强引用
        ↓
  GC 时 ThreadLocal 对象被回收
        ↓
  Entry 的 key 变为 null
        ↓
  但 value 仍然被 Entry 强引用，无法回收
        ↓
  内存泄漏
```

#### 7.2 ThreadLocalMap 的清理机制

ThreadLocalMap 内部有**启发式清理**机制：

```
每次 set/get 操作时：
        ↓
  ① 检查当前 Entry 的 key 是否为 null
        ↓
  ② 如果为 null（ThreadLocal 已被回收）：
        → 清除该 Entry 的 value
        → 将该 Entry 从 table 中移除
        ↓
  ③ 同时向后扫描，清理其他 key 为 null 的 Entry
```

#### 7.3 最佳实践

```kotlin
// 始终使用 try-finally 确保清理
try {
    threadLocal.set(value)
    // 使用 threadLocal.get()
} finally {
    threadLocal.remove()  // 必须调用
}
```

### 8. ThreadLocal 在 Android 中的应用

#### 8.1 Handler 机制中的应用

```
Looper.prepare()
        ↓
  ① 创建 Looper 对象
        ↓
  ② sThreadLocal.set(looper)  // 存入当前线程的 ThreadLocal
        ↓
  Looper.myLooper()
        ↓
  return sThreadLocal.get()  // 从当前线程的 ThreadLocal 取出
```

**为什么用 ThreadLocal？**
- 每个线程只能有一个 Looper
- ThreadLocal 保证线程隔离，互不干扰
- 主线程和子线程各自持有自己的 Looper

#### 8.2 其他应用场景

| 场景 | 用途 |
|------|------|
| Handler/Looper | 存储每个线程的 Looper 实例 |
| SimpleDateFormat | 线程安全地复用日期格式化器 |
| 数据库连接 | 每个线程持有独立的数据库连接 |
| 事务管理 | 每个线程持有独立的事务上下文 |
| 用户会话 | Web 应用中每个请求持有独立的用户信息 |

### 9. InheritableThreadLocal

InheritableThreadLocal 允许子线程继承父线程的值：

```kotlin
val inheritableThreadLocal = InheritableThreadLocal<String>()
inheritableThreadLocal.set("parent")

val thread = Thread {
    println(inheritableThreadLocal.get())  // "parent"
}
thread.start()
```

#### 原理

```
Thread 创建时：
        ↓
  ① 检查父线程的 inheritableThreadLocals
        ↓
  ② 如果不为 null：
        → 复制父线程的 InheritableThreadLocalMap 到子线程
        ↓
  ③ 子线程拥有独立的副本，修改互不影响
```

### 10. TransmittableThreadLocal（阿里开源）

TransmittableThreadLocal（TTL）解决了线程池场景下的值传递问题：

```
普通 ThreadLocal 在线程池中的问题：
  线程池复用线程，ThreadLocal 值不会自动传递
        ↓
  TransmittableThreadLocal 的解决方案：
  ① 任务提交时捕获当前 ThreadLocal 值
  ② 任务执行前恢复 ThreadLocal 值
  ③ 任务执行后清理 ThreadLocal 值
```

### 11. ThreadLocal vs synchronized 对比

| 维度 | ThreadLocal | synchronized |
|------|-------------|---------------|
| **思路** | 空间换时间 | 时间换空间 |
| **原理** | 每个线程独立副本 | 同一份数据，加锁串行化 |
| **性能** | 无锁，性能好 | 有锁竞争，性能差 |
| **内存** | 每个线程一份，内存占用大 | 共享一份，内存占用小 |
| **适用场景** | 线程间不需要共享数据 | 线程间需要共享数据 |

### 12. 关键设计亮点

#### 12.1 线程隔离
- 数据存储在 Thread 对象中，而非 ThreadLocal 中
- 每个线程拥有独立的 ThreadLocalMap
- 完全隔离，无竞争

#### 12.2 弱引用设计
- Entry 的 key 是 ThreadLocal 的弱引用
- ThreadLocal 被回收后，Entry 的 key 变为 null
- ThreadLocalMap 会启发式清理这些 Entry

#### 12.3 无锁并发
- 不需要加锁，每个线程操作自己的数据
- 性能远优于 synchronized

### 13. 关键优化要点

| 优化项 | 做法 |
|--------|------|
| 避免内存泄漏 | 始终在 finally 中调用 `remove()` |
| 线程池场景 | 必须使用 `remove()` 或 TransmittableThreadLocal |
| 继承场景 | 使用 `InheritableThreadLocal` 传递父线程值 |
| 初始化值 | 重写 `initialValue()` 提供默认值 |
| 避免滥用 | 只在必要时使用，优先使用局部变量 |
| 性能考虑 | ThreadLocal 比 synchronized 性能更好 |
| 调试困难 | ThreadLocal 值难以调试，建议添加日志 |

## 九、ThreadPoolExecutor

> **一句话总结**：任务提交时先创建核心线程执行，核心线程满则入队列，队列满再创建临时线程，都满则执行拒绝策略；Worker 通过 runWorker() 循环从队列取任务执行，核心线程阻塞等待、临时线程超时等待，ctl 变量同时维护运行状态和线程数。

### 1. 核心架构

ThreadPoolExecutor 是 Java 并发包提供的**线程池实现**，采用 **生产者-消费者模式 + 拒绝策略** 设计，核心参数与职责如下：

| 参数 | 含义 |
|------|------|
| **corePoolSize** | 核心线程数，即使空闲也不会被回收（除非设置 `allowCoreThreadTimeOut`） |
| **maximumPoolSize** | 最大线程数，包含核心线程和临时线程 |
| **keepAliveTime** | 临时线程的空闲存活时间 |
| **unit** | keepAliveTime 的时间单位 |
| **workQueue** | 任务队列，存储待执行的任务 |
| **threadFactory** | 线程工厂，用于创建新线程 |
| **handler** | 拒绝策略，当线程池和队列都满时的处理方式 |

### 2. 线程池状态

ThreadPoolExecutor 通过 `ctl` 变量（AtomicInteger）同时存储**线程数**和**运行状态**：

```
ctl = runState << 29 | workerCount

运行状态：
  RUNNING  → 接收新任务，处理队列中的任务
  SHUTDOWN → 不接收新任务，但处理队列中的任务
  STOP     → 不接收新任务，不处理队列中的任务，中断正在运行的任务
  TIDYING  → 所有任务已终止，workerCount = 0
  TERMINATED → terminated() 回调执行完毕
```

### 3. 任务提交流程（核心重点）

```
executor.execute(command)
        ↓
  ① 检查线程池状态（是否 RUNNING）
        ↓
  ② 检查 workerCount < corePoolSize：
        ├─ 是 → addWorker(command, core = true)  // 创建核心线程执行任务
        └─ 否 → 进入下一步
        ↓
  ③ 尝试将任务加入 workQueue：
        ├─ 成功 → 再次检查线程池状态
        │         ├─ 如果 RUNNING 且 workerCount == 0 → addWorker(空任务)
        │         └─ 否则直接返回（等待工作线程取任务）
        └─ 失败（队列满）→ 进入下一步
        ↓
  ④ 检查 workerCount < maximumPoolSize：
        ├─ 是 → addWorker(command, core = false)  // 创建临时线程执行任务
        └─ 否 → 进入下一步
        ↓
  ⑤ 执行拒绝策略：handler.rejectedExecution(command, this)
```

### 4. Worker 工作线程

Worker 是 ThreadPoolExecutor 的内部类，封装了工作线程和任务：

```kotlin
class Worker extends AbstractQueuedSynchronizer implements Runnable {
    final Thread thread;      // 工作线程
    Runnable firstTask;       // 初始任务

    Worker(Runnable firstTask) {
        this.thread = getThreadFactory().newThread(this);
        this.firstTask = firstTask;
    }

    public void run() {
        runWorker(this);  // 执行任务循环
    }
}
```

#### runWorker() 任务循环

```
runWorker(Worker w)
        ↓
  ① 获取工作线程和初始任务
        ↓
  ② 循环执行任务：
        ├─ 获取任务：task = getTask()
        │     ├─ 核心线程 → 阻塞等待（workQueue.take()）
        │     └─ 临时线程 → 超时等待（workQueue.poll(keepAliveTime)）
        │
        ├─ 执行任务：task.run()
        │
        └─ 任务完成后继续循环
        ↓
  ③ getTask() 返回 null → 退出循环
        ↓
  ④ processWorkerExit() → 移除 Worker，检查是否需要补充线程
```

### 5. 四种拒绝策略

| 策略 | 行为 |
|------|------|
| **AbortPolicy**（默认） | 抛出 `RejectedExecutionException` |
| **CallerRunsPolicy** | 由提交任务的线程直接执行该任务 |
| **DiscardPolicy** | 直接丢弃任务，不抛异常 |
| **DiscardOldestPolicy** | 丢弃队列中最旧的任务，重新提交 |

### 6. 常用工厂方法

```kotlin
// 固定大小线程池
Executors.newFixedThreadPool(4)
// corePoolSize = maximumPoolSize = 4
// workQueue = LinkedBlockingQueue（无界）

// 缓存线程池
Executors.newCachedThreadPool()
// corePoolSize = 0, maximumPoolSize = Integer.MAX_VALUE
// workQueue = SynchronousQueue
// keepAliveTime = 60s

// 单线程池
Executors.newSingleThreadExecutor()
// corePoolSize = maximumPoolSize = 1
// workQueue = LinkedBlockingQueue（无界）

// 定时线程池
Executors.newScheduledThreadPool(4)
// 支持定时和周期性任务
```

**为什么阿里巴巴规范不建议使用 Executors？**

| 工厂方法 | 问题 |
|----------|------|
| `newFixedThreadPool` / `newSingleThreadExecutor` | 队列无界（LinkedBlockingQueue），任务堆积可能导致 OOM |
| `newCachedThreadPool` | 最大线程数为 Integer.MAX_VALUE，可能创建大量线程导致 OOM |
| `newScheduledThreadPool` | 最大线程数为 Integer.MAX_VALUE，可能创建大量线程 |

### 7. 自定义线程池（推荐）

```kotlin
val executor = ThreadPoolExecutor(
    corePoolSize = 4,
    maximumPoolSize = 8,
    keepAliveTime = 60L,
    unit = TimeUnit.SECONDS,
    workQueue = LinkedBlockingQueue(100),  // 有界队列
    threadFactory = object : ThreadFactory {
        private val count = AtomicInteger(0)
        override fun newThread(r: Runnable): Thread {
            return Thread(r).apply {
                name = "my-pool-thread-${count.incrementAndGet()}"
                isDaemon = false
            }
        }
    },
    handler = ThreadPoolExecutor.CallerRunsPolicy()
)
```

### 8. 线程池参数配置建议

| 任务类型 | corePoolSize | maximumPoolSize | workQueue |
|----------|-------------|----------------|------------|
| **CPU 密集型** | CPU 核心数 + 1 | CPU 核心数 + 1 | 无界队列 |
| **IO 密集型** | CPU 核心数 * 2 | CPU 核心数 * 4 | 有界队列 |
| **混合型** | 根据任务比例调整 | 根据任务比例调整 | 有界队列 |

**计算公式**：
- CPU 密集型：N_threads = N_CPU + 1
- IO 密集型：N_threads = N_CPU / (1 - 阻塞系数)，阻塞系数 ≈ 0.8~0.9

### 9. 线程池的生命周期

```
创建线程池 → RUNNING
        ↓
  shutdown()
        ↓
  SHUTDOWN（不接收新任务，处理队列中的任务）
        ↓
  队列任务执行完毕
        ↓
  TIDYING（所有任务终止，workerCount = 0）
        ↓
  terminated() 回调
        ↓
  TERMINATED

shutdownNow()
        ↓
  STOP（不接收新任务，不处理队列，中断运行中的任务）
        ↓
  TIDYING → TERMINATED
```

#### 11.1 三级缓冲

- 逐级缓冲，避免频繁创建/销毁线程

#### 11.2 线程复用

#### 11.3 动态扩缩容

#### 11.4 拒绝策略

## 十、LeakCanary

> **一句话总结**：在 Activity/Fragment 销毁时创建 KeyedWeakReference 关联引用队列，延迟 5 秒后手动 GC 检查引用是否被回收，未回收则判定泄漏，导出 hprof 堆转储文件，用 Shark 库 BFS 分析从 GC Roots 到泄漏对象的最短引用链。

### 1. 核心架构

LeakCanary 是 Square 开源的**内存泄漏检测工具**，采用 **弱引用 + 堆转储 + 图分析** 设计，核心模块职责如下：

| 模块 | 职责 |
|------|------|
| **LeakCanary** | 全局入口，初始化配置 |
| **InternalAppWatcher** | 监控 Activity/Fragment 的销毁 |
| **ObjectWatcher** | 监控对象是否被回收（弱引用 + 引用队列） |
| **HeapDumper** | 导出 hprof 堆转储文件 |
| **Shark** | 分析 hprof 文件，查找 GC Roots 到泄漏对象的引用链 |
| **NotificationListener** | 展示泄漏通知和分析结果 |

### 2. 核心检测原理

LeakCanary 的检测基于 JVM 的 **WeakReference + ReferenceQueue** 机制：

- **WeakReference**：弱引用持有的对象，当没有强引用指向它时，下次 GC 就会被回收
- **ReferenceQueue**：当弱引用的对象被回收后，这个弱引用本身会被自动加入到引用队列中

```java
ReferenceQueue queue = new ReferenceQueue();
WeakReference ref = new WeakReference(activity, queue);

// 如果 activity 被 GC 回收了，ref 会被加入 queue
// 如果 queue 里没有 ref，说明 activity 还没被回收 → 可能泄漏了
```

这就是 LeakCanary 判断"有没有泄漏"的核心手段。

### 3. 完整检测流程

#### 3.1 流程概览

```
Activity.onDestroy() / Fragment.onDestroy()
        ↓
  ① ObjectWatcher.expectWeaklyReachable(watchedObject, name)
        ↓
  ② 创建 WeakReference + ReferenceQueue：
        key = UUID
        reference = WeakReference(watchedObject, queue)
        存入 watchedObjects Map
        ↓
  ③ 延迟 5 秒后检查：
        Handler.postDelayed({
            checkRetainedObjects()
        }, 5000)
        ↓
  ④ 检查前，手动触发 GC：
        Runtime.getRuntime().gc()
        ↓
  ⑤ 遍历 watchedObjects：
        ├─ reference.get() == null → 对象已被回收 → 正常
        └─ reference.get() != null → 对象未被回收 → 疑似泄漏
        ↓
  ⑥ 发现泄漏对象：
        → 导出 hprof 堆转储文件
        ↓
  ⑦ Shark 库分析 hprof：
        → 查找从 GC Roots 到泄漏对象的最短引用链
        ↓
  ⑧ 展示泄漏通知：
        → 显示泄漏对象 + 引用链
```

#### 3.2 各步骤详解

**① 监听生命周期**

LeakCanary 在初始化时注册 Activity 和 Fragment 的生命周期监听，**只在销毁时才开始检测**——因为销毁了还被引用着，那就是泄漏：

```java
application.registerActivityLifecycleCallbacks(new ActivityLifecycleCallbacks() {
    @Override
    public void onActivityDestroyed(Activity activity) {
        watchActivity(activity);  // Activity 销毁了，开始检测
    }
});
```

**② 创建弱引用 + 加入引用队列**

Activity 被 onDestroy 之后，创建 `KeyedWeakReference` 并关联引用队列：

```java
void watchActivity(Activity activity) {
    // 1. 创建弱引用，关联引用队列
    KeyedWeakReference ref = new KeyedWeakReference(activity, activity.getClass().getName(), queue);
    // 2. 存到 watchedReferences 中，方便后续查找
    watchedReferences.put(ref.key, ref);
    // 3. 延迟几秒后检查
    checkForLeakLater(ref);
}
```

> 为什么要延迟几秒？因为 Activity 销毁后可能还有一些异步操作没完（动画、Handler 消息等），给它们一点时间释放引用。

**③ 检查是否被回收**

几秒之后，检查引用队列，**主动触发一次 GC** 确保该回收的都回收了：

```java
void checkForLeak(KeyedWeakReference ref) {
    Runtime.getRuntime().gc();  // 手动触发 GC

    // 检查引用队列 —— 被回收的弱引用会出现在这里
    Reference removedRef = queue.poll();
    while (removedRef != null) {
        watchedReferences.remove(removedRef.key);  // 已回收，移除
        removedRef = queue.poll();
    }

    // 如果 ref 还在 watchedReferences 里，说明没被回收 → 泄漏了！
    if (watchedReferences.containsKey(ref.key)) {
        heapDumpAndAnalyze(ref);  // 确认泄漏，进行堆转储分析
    }
}
```

**④ 堆转储 + 分析引用链**

确认泄漏后做两件事：

1. **HeapDump**：把当前 JVM 堆内存快照导出为 `.hprof` 文件，包含所有存活对象和引用关系
2. **Shark 分析**：解析 hprof 文件，从 GC Roots 出发找到泄漏对象的最短引用路径

分析结果示例：
```
com.xxx.MyActivity
  ↑ 被引用自
com.xxx.MyPresenter.mActivity
  ↑ 被引用自
com.xxx.MyFragment.mPresenter
  ↑ 被引用自
android.app.Fragment.mFragment
```

一看就知道：Fragment 的 Presenter 持有了 Activity 引用，Fragment 销毁了但 Presenter 没释放，导致 Activity 泄漏。

**⑤ 展示结果**

LeakCanary 把分析结果以通知形式展示，点击可看到完整的泄漏引用链，开发者一看就知道哪里出了问题。

## 十一、BlockCanary

> **一句话总结**：通过 Looper.setMessageLogging() 安装自定义 Printer，在每条 Message 处理前后的两次 println 时间差计算耗时，超过阈值判定卡顿，同时启动采样线程定期采集主线程堆栈，卡顿结束后输出完整引用链定位问题代码。

### 1. 核心架构

BlockCanary 是 Android 平台的**主线程卡顿检测工具**，基于 Looper 的 Printer 机制实现，核心类职责如下：

| 类 | 职责 |
|---|---|
| **BlockCanary** | 全局入口，初始化配置 |
| **BlockCanaryContext** | 配置上下文，定义阈值、存储路径等 |
| **LooperMonitor** | 监控 Looper 消息处理耗时 |
| **LooperPrinter** | 自定义 Printer，拦截消息处理前后回调 |
| **Sampler** | 采集主线程堆栈信息 |
| **BlockInfo** | 封装卡顿信息（堆栈、耗时、时间戳等） |
| **LogWriter** | 写入卡顿日志到文件 |

### 2. 核心检测原理

BlockCanary 基于 **Looper 的 Printer 机制**：

```
Looper.loop() 内部：
    for (;;) {
        Message msg = queue.next();
        ...
        // 开始处理消息前
        Printer.println(">>>>>> Dispatching to " + msg.target + " " + msg.callback);
        
        msg.target.dispatchMessage(msg);  // 实际处理
        
        // 处理完成后
        Printer.println("<<<<<< Finished to " + msg.target + " " + msg.callback);
    }

BlockCanary 通过 setMessageLogging() 安装自定义 Printer：
  - 记录每条 Message 处理前后的时间差
  - 超过阈值 → 判定为卡顿
  - 采集主线程堆栈，定位问题代码
```

### 3. 完整检测流程

```
BlockCanary.install(context, blockCanaryContext).start()
        ↓
  ① 创建 LooperMonitor
        ↓
  ② Looper.getMainLooper().setMessageLogging(looperMonitor)
        ↓
  每条 Message 处理时：
        ↓
  ③ LooperPrinter.println(log)
        ├─ 以 ">>>>>>" 开头 → 记录开始时间 + 堆栈采集开始
        └─ 以 "<<<<<<" 开头 → 计算耗时
        ↓
  ④ 检查耗时：
        ├─ 耗时 < 阈值 → 正常，不处理
        └─ 耗时 >= 阈值 → 判定为卡顿
        ↓
  ⑤ 卡顿处理：
        ├─ 停止堆栈采集
        ├─ 收集卡顿期间的主线程堆栈
        ├─ 生成 BlockInfo（耗时、堆栈、时间戳等）
        ├─ 写入日志文件
        └─ 发送通知
```

### 4. Looper Printer 机制详解

```kotlin
// Looper.loop() 源码（简化版）
public static void loop() {
    final Printer logging = me.mLogging;
    
    for (;;) {
        Message msg = queue.next();
        ...
        if (logging != null) {
            logging.println(">>>>>> Dispatching to " + msg.target + " " + msg.callback);
        }
        
        long slowDispatchThreshold = ...;
        long start = SystemClock.uptimeMillis();
        
        msg.target.dispatchMessage(msg);  // 实际处理消息
        
        long end = SystemClock.uptimeMillis();
        long duration = end - start;
        
        if (logging != null) {
            logging.println("<<<<<< Finished to " + msg.target + " " + msg.callback);
        }
    }
}
```

**关键点**：
- 每条 Message 处理前后都会调用 Printer.println()
- 通过两次 println 的时间差计算耗时
- 超过阈值即判定为卡顿

### 5. 堆栈采集原理

```kotlin
class LooperPrinter(val threshold: Long) : Printer {
    private var startTime = 0L
    private var sampler: Sampler? = null

    override fun println(log: String) {
        if (log.startsWith(">>>>>>")) {
            // 消息处理开始
            startTime = SystemClock.uptimeMillis()
            sampler = Sampler()
            sampler?.start()  // 开始采集堆栈
        } else {
            // 消息处理结束
            val duration = SystemClock.uptimeMillis() - startTime
            if (duration >= threshold) {
                // 卡顿，停止采集
                sampler?.stop()
                // 获取堆栈
                val stackTrace = sampler?.stackTrace
                // 上报卡顿信息
            }
            sampler = null
        }
    }
}

class Sampler : Thread() {
    private var running = true
    private val stackTraces = mutableListOf<String>()

    override fun run() {
        while (running) {
            // 定期采集主线程堆栈
            val stackTrace = Looper.getMainLooper().thread.stackTrace
            stackTraces.add(stackTraceToString(stackTrace))
            Thread.sleep(200)  // 每 200ms 采集一次
        }
    }
```

## 十二、Realm 数据库

> **一句话总结**：零拷贝架构，数据直接存储在 mmap 内存映射文件中，RealmObject 直接指向映射内存中的位置，读写无需序列化/反序列化，性能远超 SQLite；支持响应式自动更新（RealmResults）、事务安全、AES-256 加密。

### 1. 核心架构

Realm 是一个**移动端嵌入式数据库**，采用 **零拷贝 + 响应式 + 跨平台** 设计，核心架构如下：

| 组件 | 职责 |
|------|------|
| **Realm** | 数据库实例，管理事务和查询 |
| **RealmObject** | 数据模型基类，映射到数据库表 |
| **RealmResults** | 查询结果集，支持响应式更新 |
| **RealmList** | 列表类型字段，支持关联关系 |
| **RealmConfiguration** | 数据库配置（路径、加密、迁移等） |
| **RealmQuery** | 查询构建器，支持链式调用 |
| **RealmChangeListener** | 数据变化监听器 |
| **RealmSchema** | 数据库 Schema 定义 |

### 2. 核心特性

| 特性 | 说明 |
|------|------|
| **零拷贝架构** | 数据直接存储在内存映射文件中，无需序列化/反序列化 |
| **响应式更新** | RealmResults 自动更新，无需手动刷新 |
| **跨平台** | 支持 Android/iOS/React Native/Xamarin 等 |
| **事务安全** | 所有写操作必须在事务中执行 |
| **线程安全** | 每个线程有自己的 Realm 实例 |
| **加密支持** | 支持 AES-256 加密 |
| **迁移支持** | 支持数据库版本迁移 |

### 3. 零拷贝架构（核心重点）

Realm 与传统数据库（SQLite）的核心区别：

```
传统数据库（SQLite）：
  磁盘存储 → 读取到内存 → 反序列化为对象 → 使用
  写入：对象 → 序列化为字节 → 写入内存 → 刷入磁盘
  每次读写都有序列化/反序列化开销

Realm 零拷贝架构：
  数据直接存储在内存映射文件中
  查询：直接返回内存中的对象引用，无需拷贝
  写入：直接修改内存映射，自动持久化
  无序列化/反序列化开销
```

#### 内存映射文件

```
Realm 数据库文件（.realm）
        ↓
  通过 mmap 映射到进程地址空间
        ↓
  RealmObject 直接指向映射内存中的位置
        ↓
  访问对象属性 = 直接读取内存，无拷贝
```

### 4. 核心 API 使用

```kotlin

```

## 十三、主流数据库框架对比

### 1. 综合对比表

| 维度 | Room | GreenDAO | ObjectBox | Realm |
|------|------|----------|-----------|-------|
| **定位** | Android 官方 SQLite 封装 | Android 专用 ORM | 高性能 NoSQL 对象数据库 | 零拷贝移动数据库 |
| **底层存储** | SQLite | SQLite | 自定义二进制格式（FlatBuffer） | 自定义二进制格式（内存映射） |
| **API 风格** | 注解 + DAO + 抽象类 | 注解 + DAO + 生成代码 | 注解 + Box 实体管理 | 注解 + RealmObject 继承 |
| **查询方式** | SQL / @Query 注解 / 支持 Flow | QueryBuilder 链式调用 | QueryBuilder 链式调用 | 链式 API（类 LINQ 风格） |
| **协程支持** | **原生支持**（suspend DAO + Flow） | 不支持 | 不支持 | 不支持（有 RxJava 支持） |
| **响应式** | Flow / LiveData 原生支持 | 需手动封装 | RxJava 支持 | RealmResults 自动更新 |
| **数据库迁移** | 手动编写 Migration | 手动编写 Migration | 自动迁移（基于注解） | 手动编写 RealmMigration |
| **代码生成** | 编译期 APT（生成 Impl 类） | 编译期 APT（生成 DaoSession） | 编译期 APT（生成 Entity_） | 无代码生成（运行时反射） |
| **包体积** | ~100KB | ~200KB | ~2MB | ~2MB |
| **初始化速度** | 快（无代码生成开销） | 中（需生成代码） | 中 | 中 |
| **查询性能** | 中（SQLite 标准性能） | 中（SQLite + ORM 开销） | **极高**（无序列化） | **极高**（零拷贝） |
| **写入性能** | 中 | 中 | **极高** | **极高** |
| **跨平台** | 仅 Android | 仅 Android | **多平台**（Android/iOS/Desktop/Flutter） | **多平台**（Android/iOS/Flutter/.NET） |
| **加密支持** | 需集成 SQLCipher | 需集成 SQLCipher | 内置加密 | 内置加密 |
| **维护状态** | **Google 官方维护**，活跃 | 基本停止更新 | 活跃维护 | 活跃维护 |
| **学习成本** | 中（需理解 SQLite + 注解） | 中 | 低 | 低 |

### 2. 各框架核心特点

**Room**：
- Google 官方推荐，Jetpack 组件之一，与 Android 生态深度集成
- 底层基于 SQLite，稳定性与兼容性有保障
- 编译期 APT 校验 SQL 语句，避免运行时 SQL 错误
- 原生支持 Kotlin 协程（suspend DAO）和 Flow，与 ViewModel/Lifecycle 无缝配合
- Paging 3 的数据源直接对接 Room，适合大列表分页场景
- 缺点：API 相对繁琐（需要定义 Entity + DAO + Database 三层），查询能力受限于 SQL
- 适合绝大多数 Android 项目的标准选择

**GreenDAO**：
- 早期 Android 最流行的 ORM 框架，基于 SQLite 封装
- 通过 APT 生成 DAO 代码，避免运行时反射
- QueryBuilder 链式查询 API 简洁易用
- 缺点：**基本停止维护**，不支持协程，不支持 Flow，社区活跃度下降
- 适合维护老项目，新项目不推荐

**ObjectBox**：
- 高性能 NoSQL 对象数据库，底层使用 FlatBuffer 二进制存储
- 无序列化/反序列化开销，读写性能极高
- 支持多平台（Android/iOS/Desktop/Flutter）
- 内置自动迁移，无需手动编写 Migration
- 缺点：包体积较大（~2MB），社区相对小众，调试工具不如 SQLite 成熟
- 适合对性能要求极高 + 需要跨平台的场景

**Realm**：
- 零拷贝架构，数据直接存储在内存映射文件中，无序列化开销
- 查询性能极高，RealmResults 自动更新（响应式）
- 面向对象 API，无需写 SQL，代码可读性高
- 支持多平台（Android/iOS/Flutter/.NET）
- 缺点：包体积大（~2MB），RealmObject 需要继承 RealmObject 类（侵入性较强），加密会影响性能
- 适合复杂数据模型 + 大量读写的高性能场景

### 3. 选型建议

```
新项目？
    ├─ 是 → Room（首选，官方支持）
    └─ 否 → 老项目用的什么就继续用什么

需要跨平台（Android + iOS + Flutter）？
    ├─ 是 → ObjectBox 或 Realm
    └─ 否 → Room

对读写性能要求极高？
    ├─ 是 → ObjectBox 或 Realm
    └─ 否 → Room

需要 Kotlin 协程 + Flow 深度集成？
    ├─ 是 → Room（唯一原生支持）
    └─ 否 → 按上面规则选
```

> **结论**：现代 Android 开发中，**Room** 是标准选择，官方维护、协程友好、与 Jetpack 生态无缝集成。GreenDAO 已停止维护，不建议新项目使用。ObjectBox 和 Realm 适合对性能有极致要求或需要跨平台的场景。

## 十四、主流跨进程通信方式对比

### 1. 综合对比表

| 维度 | Binder | AIDL | Messenger | ContentProvider | Socket |
|------|--------|------|-----------|-----------------|--------|
| **定位** | Android 底层 IPC 机制 | Binder 的接口定义语言 | 基于 Message 的 IPC 封装 | 数据共享组件 | 通用网络 IPC 机制 |
| **底层实现** | 内核驱动（/dev/binder） | 基于 Binder | 基于 Binder | 基于 Binder | TCP/UDP |
| **性能** | **极高**（一次拷贝） | **极高**（同 Binder） | 低（串行处理 + 两次拷贝） | 中（数据共享，非实时） | 低（网络开销） |
| **并发能力** | 支持多线程并发 | 支持多线程并发 | **串行处理**（单 Handler） | 支持（通过 Cursor） | 支持多线程 |
| **数据传输** | 内存映射（零拷贝/一次拷贝） | 内存映射（同 Binder） | 序列化/反序列化（Message） | 文件描述符共享 | 网络流传输 |
| **使用复杂度** | 高（需理解底层） | 高（需写 .aidl 文件） | 低（Message + Handler） | 中（CRUD 接口） | 中（网络编程） |
| **实时性** | **极高** | **极高** | 低（异步消息队列） | 中（观察者模式） | 低（网络延迟） |
| **适用场景** | 系统服务、高性能 IPC | 复杂 IPC 接口定义 | 简单消息传递 | 数据共享（通讯录、媒体） | 跨设备/跨服务器通信 |
| **安全控制** | 权限验证（UID/PID） | 权限验证（同 Binder） | 权限验证（同 Binder） | URI 权限控制 | 自定义安全策略 |
| **连接方式** | 系统自动管理 | Service 绑定 | Service 绑定 | 系统自动管理 | 手动连接管理 |
| **跨设备** | 不支持（仅本机） | 不支持（仅本机） | 不支持（仅本机） | 不支持（仅本机） | **支持** |

### 2. 各方式核心特点

**Binder**：
- Android 最核心的 IPC 机制，系统服务（AMS、WMS、PMS 等）全部基于 Binder
- 性能极高：内存映射机制，数据只需**一次拷贝**（传统 IPC 需要两次）
- 支持多线程并发调用，实时性极强
- 底层通过 `/dev/binder` 内核驱动实现，用户空间与内核空间共享内存
- 缺点：直接使用复杂，通常通过 AIDL 封装
- 适合系统级服务、对性能要求极高的场景

**AIDL**：
- Android Interface Definition Language，Binder 的接口定义语言
- 通过 `.aidl` 文件定义 IPC 接口，编译期自动生成 Stub/Proxy 代码
- 支持复杂数据类型（基本类型、String、List、Map、Parcelable）
- 支持单向/双向调用，支持多线程并发
- 缺点：API 较底层，需要手动管理 Service 连接、线程切换、异常处理
- 适合需要高性能 + 复杂接口的 IPC 场景

**Messenger**：
- 基于 Message 的 IPC 封装，底层也是 Binder，但做了简化
- 使用简单：客户端绑定 Service，通过 Message 传递数据
- 串行处理：所有消息在 Service 端的单个 Handler 中依次处理，无需考虑线程安全
- 缺点：**性能低**（串行 + 序列化开销），不支持并发，只能传递 Message 支持的数据类型
- 适合简单的 IPC 场景（如通知 Service 执行某个操作）

**ContentProvider**：
- Android 四大组件之一，专门用于**数据共享**（而非实时通信）
- 提供统一的 CRUD 接口，通过 URI 访问数据
- 支持权限控制（URI 权限），可跨应用共享数据
- 底层基于 Binder，但数据通过文件描述符共享，适合大数据量
- 典型应用：通讯录、媒体库、应用间数据共享
- 缺点：不适合实时通信，数据变化通知有延迟
- 适合应用间数据共享场景

**Socket**：
- 通用网络通信机制，支持跨设备、跨服务器通信
- 支持 TCP/UDP，可传输任意格式的数据
- 缺点：性能低（网络开销），需要手动管理连接、线程、安全
- 适合跨设备通信、与服务器长连接、非 Android 进程间通信
- 不适合本机内高性能 IPC

### 3. 选型建议

```
本机内进程间通信？
    ├─ 是 → 性能要求高？
    │       ├─ 是 → AIDL（复杂接口）或 Binder（简单场景）
    │       └─ 否 → Messenger（简单消息）
    └─ 否 → Socket（跨设备/跨服务器）

应用间数据共享？
    ├─ 是 → ContentProvider
    └─ 否 → 按上面规则选

需要实时双向通信？
    ├─ 是 → AIDL
    └─ 否 → Messenger 或 ContentProvider
```

> **结论**：Android 本机 IPC 首选 **AIDL**（复杂接口）或 **Messenger**（简单消息），底层都是 Binder，性能有保障。数据共享用 **ContentProvider**。跨设备通信用 **Socket**。Binder 是 Android IPC 的基石，理解其原理对掌握所有 IPC 方式至关重要。
